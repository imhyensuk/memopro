**Running Unmodified Programs in Half Their Memory: Feasibility and Limits of Disk-Free, Lossless Compressed User-Space Paging**

## 요 약

메모리가 작은 개인 기기에서 데이터 분석·영상 처리 프로그램은 메모리 부족(OOM)으로 강제 종료되거나 운영체제 스왑으로 크게 느려진다. 본 논문은 프로그램을 고치지 않고 `LD_PRELOAD`로 4MiB 이상의 모든 할당을 Linux userfaultfd 기반 사용자 공간 페이저에 넣고, 쉬는 메모리 조각을 **디스크에 쓰지 않고 무손실 압축만으로** 줄여 **프로세스 전체 메모리 상한**을 지키는 방식을 구현하고, 사전 등록한 기준으로 평가하였다. 원래 최대 메모리의 1/2 한도에서 NumPy 영상 처리와 scikit-learn 분류는 결과가 비트 단위로 같게 완주하였고(그냥 실행은 강제 종료), 영상 처리는 같은 한도의 OS 스왑보다 3.3배 빨랐다. 반면 무작위 접근이 많은 pandas 데이터프레임은 되읽기 폭주로, 압축 후에도 한도보다 큰 시뮬레이션 기록은 정보량 한계로 실패하였다. 이 결과로 디스크 없는 압축 페이징이 유효한 작업의 조건(순차적 접근, 높은 압축률)을 제시한다.

## 1. 서론

8~16GB 메모리의 노트북에서 메모리보다 큰 작업을 돌리는 일반적인 방법은 운영체제 스왑이다. 그러나 스왑은 응용의 접근 형태를 모르고 4KiB 쪽 단위로 저장 장치에 쓰기 때문에 느리고, SSD 수명을 소모한다. 커널 압축 스왑(zswap, zram)[5]과 데이터센터의 투명 메모리 오프로딩(TMO)[4]은 압축 계층을 두지만 시스템 전체 설정이 필요하고 프로세스 단위 상한을 보장하지 않는다. 사용자 공간 페이징(UMap[2], ExtMem[1])은 응용이 정책을 정할 수 있게 하지만 데이터를 파일·저장 장치로 내보낸다.

본 논문은 다음 질문을 다룬다. **"프로그램을 고치지 않고, 디스크에 쓰지 않고, 결과를 바꾸지 않고(무손실), 프로세스 전체 메모리를 정해진 상한 안에 두면서 메모리 절반으로 실행할 수 있는 작업은 어떤 것인가?"** 기여는 다음과 같다.

1. `LD_PRELOAD` 할당 가로채기 + userfaultfd 페이저 + 무손실 압축만 사용 + 프로세스 전체 상한을 결합한 구현(오픈 소스 memopro의 일부).
2. 성격이 다른 수정하지 않은 프로그램 4종에 대한 사전 등록 평가: 2종 성공, 2종 실패.
3. 실패 원인 분석으로 이 방식이 유효한 작업 조건을 정리.

개별 기법(할당 가로채기[3], userfaultfd 페이징[1][2], 압축 메모리[4][5])은 기존에 있으며, 본 논문은 이들의 조합과 그 한계의 측정에 초점을 둔다.

## 2. 설계

**할당 가로채기.** 공유 라이브러리를 `LD_PRELOAD`로 적재하여 `malloc`, `calloc`, `realloc`, `free`, `posix_memalign`, `aligned_alloc`, `memalign`, `malloc_usable_size`를 가로챈다. 4MiB 이상의 할당은 페이저 영역에서, 작은 할당은 원래 할당기에서 준다. NumPy 배열뿐 아니라 scipy·pandas 등 C 확장이 직접 잡는 큰 버퍼도 페이저에 들어간다. 페이저 스레드 안의 할당(압축 라이브러리 등)은 스레드 지역 표시로 원래 할당기에 보내 재귀를 막는다.

**페이저.** 페이저 영역은 userfaultfd에 MISSING·쓰기 보호(WP) 모드로 등록한 익명 메모리다. 프로그램은 일반 읽기·쓰기를 하고, 처음 닿은 1MiB 조각은 0으로, 내보낸 조각은 압축본을 풀어 `UFFDIO_COPY`로 채운다. 내보낼 때는 조각을 쓰기 보호한 뒤 원소 크기 단위 바이트 셔플 + zstd[6]로 압축하고 `MADV_DONTNEED`로 실제 메모리를 돌려준다. 압축 이득이 15% 미만인 조각은 내보내지 않는다. 데이터는 디스크에 쓰지 않는다.

**프로세스 전체 상한.** 사용자가 프로세스 예산 T를 주면 페이저 한도는 T − (프로세스 RSS − 페이저 보유량) − 여유로 정하고, 페이지 폴트마다 `/proc/self/statm`으로 다시 계산한다. 페이저 밖 메모리(작은 할당, 인터프리터)가 늘면 페이저가 더 내보낸다.

**구현상 주의.** NumPy는 큰 배열에 `MADV_HUGEPAGE`를 요청하는데, userfaultfd 영역에서 이것이 폴트를 페이저에 전달하지 못하게 하여 프로그램이 멈췄다. 페이저 영역에 `MADV_NOHUGEPAGE`를 걸고 그 영역에 대한 `MADV_HUGEPAGE` 요청을 무시하여 해결하였다.

## 3. 실험 방법

**환경.** GitHub Actions Linux 실행기(커널 6.17, x86_64 2 vCPU, 메모리 7.75GiB, 스왑 3GiB 파일, zswap 꺼짐), Python 3.12, NumPy 2.5.3, pandas 3.0.6, scikit-learn 1.9.1.

**작업**(모두 결정적이며 결과의 SHA-256을 출력, 코드 수정 없음):

| 작업 | 내용 |
|---|---|
| 영상 | NumPy: 512×512 16비트 영상 2,048장(1GiB)의 장별 평균, 문턱 화소 수, 배경 빼기, 전체 통계(배열 전체 연산 4회) |
| 분류 | scikit-learn: 문서 40만 × 단어 20만 희소 특징, `SGDClassifier` 5에폭 |
| 데이터프레임 | pandas: 1,600만 행 판매 표의 집계·상위 100·정렬 |
| 시뮬레이션 | NumPy 4096×4096 float32 열 확산 300단계, 10단계마다 장면 저장 |

**경우.** 각 경우를 cgroup(`MemoryMax=L`)에서 실행하였다. ① 그냥 실행(한도 없음)으로 최대 메모리 P 측정, ② 한도 L = P/2·스왑 없음, ③ 본 방식(한도 L, 스왑 없음), ④ 한도 L·OS 스왑 사용.

**사전 등록 기준**(실행 전 고정, 결과 뒤 변경하지 않음): T1 ③의 출력이 ①과 같다, T2 ②는 끝나지 못한다, T3 ③이 L 안에서 끝나고 상한 초과(overrun) 0회. 제한 시간은 15분이다. 개발 측정에 근거해 영상·분류는 성공, 데이터프레임·시뮬레이션은 실패를 미리 예상으로 기록하였다.

## 4. 결과

**표 1.** 메모리 절반(L = P/2)에서의 결과

| 작업 | P (MiB) | L (MiB) | ① 그냥 | ③ 본 방식 | ④ OS 스왑 | 판정 |
|---|---|---|---|---|---|---|
| 영상 | 1,578 | 788 | 5.2초 | **21.2초** (4.1배) | 69.5초 | 통과 |
| 분류 | 2,409 | 1,204 | 11.3초 | **39.8초** (3.5배) | 28.3초 | 통과 |
| 데이터프레임 | 1,589 | 794 | 5.8초 | 15분 초과 | 27.3초 | 실패 |
| 시뮬레이션 | 2,208 | 1,103 | 14.6초 | 15분 초과 | 73.1초 | 실패 |

②(한도만, 스왑 없음)는 네 작업 모두 OOM으로 강제 종료되었다.

**표 2.** 본 방식의 페이저 통계

| 작업 | 페이저 밖 최대 | 폴트 | 압축 전 → 후 (GB) | 압축비 | overrun |
|---|---|---|---|---|---|
| 영상 | 65MiB | 7,485 | 7.56 → 3.42 | 2.2 | 0 |
| 분류 | 426MiB | 9,842 | 8.02 → 1.53 | 5.3 | 0 |
| 데이터프레임 | 263MiB | 195,123 | 202.8 → 69.1 | 2.9 | 0 |
| 시뮬레이션 | 87MiB | 371,804 | 361.7 → 161.6 | 2.2 | 279,314 |

**성공한 작업.** 영상과 분류는 출력 해시가 그냥 실행과 같았고 상한 초과 없이 완주하였다. 영상의 프로세스 최대 RSS는 726MiB로 한도 788MiB 안이었다. 영상은 같은 한도의 OS 스왑보다 3.3배 빨랐다. 분류는 페이저 밖 메모리가 426MiB로 컸지만 프로세스 전체 상한이 페이저 몫을 줄여 맞추었다. 다만 분류는 OS 스왑보다 1.4배 느렸다. 희소 행렬이 5.3배 압축되어 한 번에 다룰 양은 작았지만, 반복 에폭마다 모든 조각을 다시 풀어야 했기 때문으로 본다.

**실패 1: 무작위 접근(데이터프레임).** 정렬·그룹 집계는 메모리 곳곳을 몇 바이트씩 읽는다. 1MiB 조각 단위에서는 몇 바이트를 위해 1MiB를 풀고 다시 압축하므로, 15분 동안 약 19.5만 번의 폴트에 압축 입력 203GB가 발생하였다(되읽기 폭주). 조각을 64KiB로 줄인 개발 측정에서도 폴트 수가 약 206만 번으로 늘어 제한 시간을 넘었다. 같은 조건의 OS 스왑은 4KiB 단위와 빠른 저장 장치로 27.3초에 끝났다.

**실패 2: 정보량 한계(시뮬레이션).** 저장한 30개 장면(약 1.9GB)은 무손실로 약 42%만 줄어 압축본만 약 1.1GB이며, 프로세스 상한을 맞추려 줄어든 페이저 한도(약 1.0GB)보다 크다. 디스크에 쓰지 않는 무손실 방식으로는 원리적으로 들어갈 수 없으며, overrun 27.9만 회가 이를 보인다.

## 5. 논의 및 결론

본 방식이 유효한 작업의 조건은 (1) **접근이 순차적이거나 조각 단위 국소성이 있고**, (2) **쉬는 데이터의 압축률이 메모리 부족분을 덮을 만큼 높을 때**다. 영상 처리처럼 두 조건을 만족하면 디스크를 쓰지 않고도 OS 스왑보다 빠르며, 결과가 바뀌지 않고, 프로세스 메모리가 상한 안에 머문다. 무작위 접근 작업은 조각 크기를 접근 형태에 맞추는 적응형 조각, 시뮬레이션처럼 비슷한 장면이 이어지는 데이터는 장면 간 차분 압축이 후속 과제다.

**한계.** 실험은 단일 실행기·작업 4종·각 1회 측정이며, userfaultfd가 없는 macOS·Windows에는 적용되지 않는다. 같은 한도에서 zswap과의 비교는 영상 작업 한 종에서만 하였다(본 방식 22.6초, zswap 53.0초, 단 zswap 실제 사용은 확인하지 못함).

모든 코드, 실험 스크립트, 원시 결과는 공개 저장소에 있다(심사 후 공개 예정).
