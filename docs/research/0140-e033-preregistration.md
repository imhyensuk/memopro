# 0140. E033 사전 등록: 관문 G4-E4 — 3B bf16 생성을 상주 int4 초안으로 2.5배 이상, 출력은 그대로

- **날짜**: 2026-10-03
- **유형**: experiment (사전 등록)
- **상태**: 확정. 실행 전
- **관련 기록**: 0139 (E4 제작, 개발 확인), 0138 (G4-B1), 0127 (int4 초안 근거)

## 질문

8GB M1에서 그냥은 GPU에 올릴 수 없는 Qwen2.5-3B(bf16 5.75GiB)를 흘려 쓰며 생성할 때, 상주 int4 초안이 출력을 바꾸지 않고 토큰당 시간을 크게 줄이는가?

## 설계

- **환경**: E028c와 같다.
  - `MallocLargeCache=0`, `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.1`, 오프라인.
  - 경우마다 새 프로세스. 스왑 오염 규칙도 같다(스왑 > 64MiB면 한 번 반복, 첫 시도만 따로 남김).
  - footprint는 `proc_pid_rusage` V4 생애 최대값.
- **대상**: `stream_model("Qwen/Qwen2.5-3B-Instruct", budget=1GiB, device="mps")`.
- **프롬프트**: 채팅 형식 4개(설명, 코드, 산수, 이야기). 각각 정확히 64토큰(`min_new_tokens` = `max_new_tokens` = 64), 탐욕.
- **경우**

| 경우 | 초안 | 역할 |
|---|---|---|
| P | 없음(대상 단독) | 기준 |
| S15 | Qwen2.5-1.5B int4 (`draft_model`) | **판정 대상** |
| S3 | Qwen2.5-3B int4 (자기 초안) | 보고 |

- 시간은 `generate` 호출 한 번(프리필 포함)이다. 초안 변환 시간은 따로 기록한다.
- 대상의 forward 호출 수(검증 횟수)를 센다.
- **명령**: `caffeinate -i .venv/bin/python -m experiments.e033_spec_decode.run --all`
- **결과 위치**: `docs/research/data/e033/`

## 기준 (관문 G4-E4 = X1·X2·X3)

| # | 기준 |
|---|---|
| **X1** 출력 동일 | 4개 프롬프트 모두 S15의 64토큰이 P와 토큰 단위로 같다 |
| **X2** 속도 | S15의 토큰당 시간(4개 합) ≤ P의 1/2.5(**2.5배 이상**) |
| **X3** 메모리 | S15 footprint 증가 ≤ 예산 + 초안 바이트 + 512MiB, **그리고** ≤ 3B bf16 크기의 절반(2,943MiB). 스왑 증가 ≤ 64MiB, 런타임 최대 계상 ≤ 한도 |

- **X1의 진단**
  - 원리상 보조 생성의 각 토큰은 대상이 고른 것이다. 하지만 검증은 여러 행을 한 번에 계산한다. bf16 MPS 행렬곱이 행 수에 따라 마지막 비트가 다를 수 있다.
  - 그래서 어긋남이 생기면 그 위치를 기록하고, 실패로 판정한다(기준은 완화하지 않는다).
- 실패하면 멈추고 보고한다.

## 논문 매핑

- **Evaluation (G4 추론)**: 흘려 쓰는 무손실 3B 생성의 토큰당 시간. 초안 없음 / 1.5B int4 / 3B int4. 출력 동일성, 메모리(예산 + 초안), 검증당 토큰.
