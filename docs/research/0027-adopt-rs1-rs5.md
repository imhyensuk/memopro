# 0027. Rust 코어 설계 규칙 RS1~RS5 채택, RS6~RS8 보류

- **날짜**: 2026-09-25
- **유형**: decision
- **상태**: 확정 — 설계 v0.3.5, 계획 v0.3.4에 반영
- **관련 기록**: 0025 (RS1~RS8 제안, E008·E008b), 0026 (최소 Python 3.11, RS2 전제), 0022 (R1: Rust 코어 v0.1 범위), 0013 V6 (동면 중 순간 메모리 상한)

## 사용자 결정

> "RS1~RS5 승인할게"

| 규칙 | 결정 | 근거 종류 |
|---|---|---|
| RS1 파이프라인 전체를 Rust가 소유 | ✅ 채택 | 실측 (E008 C4 복사 2배, E008b 방출 −18%) |
| RS2 입력은 복사 없이 빌림 | ✅ 채택 | 실측 + 설계 규칙 (E008 C4, 0013 V6) |
| RS3 스레드별 상태 재사용 + 상주 스레드 풀 | ✅ 채택 | 실측 (E008b v1 → v2 2.1배) |
| RS4 메모리 상한을 구조로 보장 | ✅ 채택 | 실측 (E008 C4 실패, E008b 367MiB로 목표 미달) |
| RS5 연산과 I/O 중첩 | ✅ 채택 | 실측 (E008b) |
| RS6 특화 커널·SIMD | ⏸ 보류 | 승인하지 않음 |
| RS7 GIL과 무관한 백그라운드 서비스 | ⏸ 보류 | 승인하지 않음 (실측 없음) |
| RS8 free-threaded Python 대비 | ⏸ 보류 | 승인하지 않음 |

해석: 실측 근거가 있는 다섯 규칙만 설계 규칙으로 올린다. 보류한 규칙은 구현 근거로 쓰지 않는다. 필요해지면 새 기록으로 다시 제안한다.

## 채택 규칙의 확정 문구와 검증 방법

제안 단계(0025)에는 검증 방법이 없었다. 규칙마다 **테스트로 확인할 수 있는 완료 조건**을 붙여 확정한다.

| # | 규칙 (확정) | 완료 조건 (A1에서 테스트로 확인) |
|---|---|---|
| RS1 | 방출(텐서 → 셔플·압축 선택 → 파일)과 복원(파일 → 해제 → 텐서 저장공간)은 **하나의 Rust 호출** 안에서 끝난다. 데이터 크기만 한 Python 객체를 만들지 않는다. | 방출·복원 중 Python 할당량(tracemalloc 최대치)이 청크 1개 크기 미만. 복원은 미리 할당한 텐서 저장공간에 직접 쓴다 |
| RS2 | 공개 바인딩은 **buffer protocol**로 입력을 빌린다. `bytes` 입력은 받지 않는다. bf16처럼 numpy가 모르는 형식은 `tensor.view(torch.uint8)` 뷰로 넘긴다 | 입력 버퍼 주소 = 텐서 `data_ptr()` (복사 없음). 호출 전후 RSS 증가가 RS4 상한 이내 |
| RS3 | zstd 문맥과 작업 버퍼는 **작업자 스레드마다 한 번** 만든다. 스레드 풀은 프로세스에 하나를 두고 계속 쓴다 | 두 번째 호출부터 스레드 수와 문맥 생성 횟수가 늘지 않음 |
| RS4 | 추가 메모리 상한 = **버퍼 수 × 청크 크기 + 상수**. 버퍼는 고정 크기 풀에서 빌리고, 쓰기가 밀리면 용량 제한 채널로 앞 단계를 멈춘다(백프레셔) | 입력 크기를 두 배로 늘려도 RSS 증가량이 늘지 않음. 증가량이 공식의 상한 이내 |
| RS5 | 방출은 압축 ↔ 쓰기를, 복원은 읽기 ↔ 해제를 겹친다 | 파이프라인 시간 < 단계별 순차 시간의 합. 성능 우위의 확정은 E009에서 판정 |

## 이 결정이 바꾸는 것

1. **A1 Rust 코어의 중심 = "방출 엔진"**(0022 R1 구체화). 구성은 상주 풀(RS3), 고정 버퍼 풀과 용량 제한 채널(RS4), 파이프라인 방출·복원(RS1·RS5), buffer protocol 입력(RS2)이다. `hwinfo`(cgroup 포함)와 `census` 커널은 계획대로 A1에 남는다.
2. **기존 프로토타입 바인딩은 RS2 위반이다.** `codec_compress`, `codec_decompress`, `codec_compress_reuse_size`, `codec_spill_to_file`는 모두 `bytes`를 받는다.
   - 이들은 E008·E008b 측정용이며, 실험 스크립트가 이를 호출한다.
   - 방출 엔진이 들어오면 **공개 API에서 제거**한다. E008 재현은 커밋 `9fd9bd3`을 체크아웃해서 한다. 제거 시점에 기록을 남긴다.
3. **RS4의 미해결 문제가 A1의 첫 과제가 된다.** E008b 파이프라인의 메모리 증가는 367MiB로, 설계 목표 약 160MB를 넘었다. 원인 후보는 두 가지이다(0025).
   - rayon `map_init`이 스레드가 아니라 작업 단위로 초기화된다.
   - 할당자가 메모리를 늦게 반환한다.
   - 새 엔진은 `map_init` 대신 **고정 버퍼 풀**을 쓰므로 구조적으로 제거된다. RSS 테스트로 확인한다.
4. **E009(압축 방출 확인 실험)는 방출 엔진 뒤에 한다.** E009는 엔진 자체를 평가한다. 그래서 순서는 방출 엔진 구현 → E009 사전 등록 → 실행 → 압축 방출을 기본값으로 올릴지 판정이다. 그때까지 β 방출 기본값은 **무압축**을 유지한다(0025 C5).
5. **RS6~RS8 보류의 영향.**
   - `codec.rs`에 이미 있는 2·4바이트 전용 셔플(E008b 프로토타입)은 그대로 둔다. 다만 규칙으로 요구하지 않으며, SIMD 작업은 하지 않는다.
   - γ·census 백그라운드 스레드(RS7)는 N3(v0.3) 설계 때 다시 판단한다.
   - `gil_used = false` 선언(RS8)은 하지 않는다. PyO3 기본값을 유지한다.

## 한계

- RS1~RS5의 근거는 **한 기기**(M1 MacBook Air 8GB, 내장 SSD)와 **한 종류 데이터**(GPT-2 가중치)이다. E008b는 사전 등록되지 않은 탐색이다.
- 규칙 자체는 성능 수치가 아니라 구조에 관한 것이다. 따라서 채택은 E009 결과와 무관하게 유지한다. 다만 "압축 방출이 더 빠르다"는 주장은 E009 전까지 하지 않는다.
- CUDA에서의 GPU → 호스트 복사 중첩(RS5 후반부)은 외부 GPU 환경이 필요하다. v0.1에서는 CPU 경로만 검증한다.
