# 0134. E028b 사전 등록: G4-B1 다시 — E3 뒤, 메모리 기준을 "예산 + 512MiB"로 엄격하게

- **상태**: 확정. 실행 전

## 바꾼 것과 그대로인 것

- **그대로**: 경우(L15 1.5B 768MiB, L3a 3B 1GiB, L3b 3B 768MiB), LoRA·데이터·단계 수, 환경 변수, 새 프로세스, 스왑 기록, 오염 규칙(첫 시도만 따로 남김), footprint 지표.
- **E3 적용**: 단계마다 `enable_checkpointing`, `causal_lm_loss(chunk=32)`, `finish()`(GPU 대기, 고정 반환, MPS 캐시 반환).
- **기준**
  - B1·B2는 E028과 같다.
  - B3는 **footprint 증가 ≤ 예산 + 512MiB**로 E028(+1GiB)보다 엄격하게 한다. 사용자가 고른 선택지의 "작은 여유"다.
  - 스왑 증가 ≤ 64MiB, 런타임 최대 계상 ≤ 한도는 같다.

| # | 기준 |
|---|---|
| **B1** 속도 | L15 정상 단계 시간(단계 2~5 평균) ≤ 25.7초(E026 CPU 257.2초의 1/10) |
| **B2** 완주·무손실 | L3a·L3b가 5단계 완주, 단계별 손실이 두 예산에서 비트 동일 |
| **B3** 메모리 | 모든 경우 footprint 증가 ≤ 예산 + 512MiB, 스왑 증가 ≤ 64MiB(오염 규칙 뒤), 런타임 최대 계상 ≤ 한도 |

- **관문 G4-B1** = B1, B2, B3. 실패하면 멈추고 보고한다.
- **명령**: `caffeinate -i .venv/bin/python -m experiments.e028b_mps_lora_e3.run --all`. 결과는 `docs/research/data/e028b/`.
