## 해석

1. **복귀가 빠른 이유.**
   - OS에 맡긴 가중치는 압박 중에 거의 모두 밀려났다. cpu/anon에서 상주 페이지는 0%였고 상주 크기는 57MB였다. 그래서 첫 순전파가 흩어진 페이지를 하나씩 스왑에서 되읽는다. 복귀할 때 디스크에서 약 498MB를 읽었고, 3.9초가 걸렸다.
   - `source`는 원본 파일을 큰 단위로 순차적으로 읽는다(RS1, 약 504MB). 그래서 1.3초에 끝나고 해시 확인도 한다.
   - MPS에서도 같은 차이가 났다(3.16초 대 1.41초). MPS 버퍼도 OS가 밀어낸다. os 방법에서 footprint는 1358MB인데 상주 크기는 147MB였다.
2. **다른 작업이 빨라지지 않은 이유.**
   - 첫째, 해제한 메모리가 libmalloc 캐시에 남는다(F-E011-1). 압박 알림이 오면 libmalloc이 캐시를 비워서, 압박 중 A 사용량은 312MB로 os 방법(778MB)보다 작았다. 그러나 그 시점에는 이미 B가 메모리를 채우고 있다.
   - 둘째, 캐시 문제를 없앤 `source_nocache`(즉시 회수 0.97)조차 B 채우기가 0.90×에 그쳐 기준(0.8×)에 못 미쳤다. 4GiB 압박에서 0.5GB 모델은 12%에 불과하다. OS는 어차피 다른 앱의 메모리 약 3.5GB를 밀어내야 했으므로, 모델을 먼저 비워도 전체 비용이 크게 줄지 않는다.
   - 따라서 D2가 실패한 원인에는 **효과 크기의 한계**도 있다. 모델이 압박에서 차지하는 비율이 클 때(예: 8GB 기기의 3B 모델)는 따로 재야 한다.
3. **mmap 조건은 예상과 달랐다.** 0058에서는 OS가 깨끗한 페이지를 공짜로 버리므로 β에 이득이 없을 것으로 예상했다. 실제로는 OS 방법도 복귀에 2.17초가 걸렸고, 두 번째 순전파도 1.30초로 느렸다. 매핑된 파일을 작은 단위로 흩어서 다시 읽기 때문이다. `source`는 0.90초였다. 다만 β를 거친 뒤에는 가중치가 익명 메모리로 바뀐다. 파일 페이지였으면 OS가 공짜로 버릴 수 있었는데, 이제는 압축하거나 스왑해야 한다.
4. **`compress`는 비율은 좋지만 macOS에서 실익이 없다.**
   - 비율은 페이지 단위 LZ4보다 좋았다(파라미터만: fp32 0.84 대 1.00).
   - 그러나 압축본을 담은 메모리와 원래 텐서가 해제된 캐시가 겹쳐서 즉시 footprint가 모델의 85~124%만큼 늘었다.
   - 압박이 오면 압축본 자체가 스왑으로 밀려나서 복귀가 os 방법보다 느렸다(cpu/anon 4.21초 대 3.86초).
   - F-E011-1을 고치기 전까지 macOS에서 `compress`가 OS보다 낫다고 말하지 않는다.
5. **`del`로 해제한 메모리도 같다.** reload(`del model; gc.collect()`)의 즉시 회수는 0이었다. 이것은 PyTorch를 CPU에서 쓰는 모든 macOS 사용자에게 해당하는 현상이다.

## 결함 F-E011-1: macOS에서 해제한 CPU 메모리가 OS로 돌아가지 않는다

- **원인**
  - macOS libmalloc은 해제된 큰 블록을 `MALLOC_LARGE (empty)` 캐시에 둔다. 커널은 이 블록을 더러운 페이지로 취급한다.
  - `malloc_zone_pressure_relief`로는 비워지지 않는다(0바이트). 압박 알림이 올 때만 비워진다.
  - memopro `source`는 텐서마다 원본을 대조할 크기의 버퍼를 잡는다. 이 버퍼들도 캐시에 쌓여서 footprint를 모델의 34%만큼 늘린다. MPS에서는 CPU 사본까지 더해 62%다.
- **확인된 사실**: 프로세스를 `MallocLargeCache=0`으로 시작하면 즉시 회수가 0.97이 된다.
- **해결 선택지** (사용자 결정 필요, 0058의 조치 규칙)

| # | 방법 | 효과 | 위험·비용 |
|---|---|---|---|
| F1 | 원본 대조를 Rust에서 파일을 조금씩 읽으며 해시로 한다. 크기의 버퍼를 잡지 않는다 | `source`로 늘어나는 34~62%가 사라진다. RS1(한 번의 Rust 호출)에 맞다 | 낮음. 동면 전 대조 방식만 바뀐다 |
| F2 | memopro가 만드는 버퍼(깨운 텐서, 압축본)를 malloc 대신 mmap으로 잡는다 | 한 번 깨운 텐서는 다음 동면 때 즉시 OS로 돌아간다 | 중간. 사용자 텐서의 저장공간 할당 방식이 바뀐다 |
| F3 | 해제 직전, 텐서가 혼자 쓰는 페이지를 새 익명 페이지로 덮는다(`mmap MAP_FIXED`) | 첫 동면부터 즉시 반환 | 높음. 저장공간의 실제 소유자를 확인해야 하고(numpy 공유 등), 저수준 조작이다. 별도 탐색과 결정이 필요하다 |
| F4 | macOS에서 doctor와 README로 `MallocLargeCache=0`을 안내하고, `memopro run`은 이 설정으로 자신을 다시 실행한다 | 사용자가 켜면 즉시 반환. `run`에서는 자동 | 낮음. 노트북 커널에는 사용자가 설정해야 한다 |
| F5 | 고치지 않고 한계로 적는다. 같은 프로세스 안에서는 재사용되고, 압박이 오면 비워진다 | 없음 | 없음 |

- **추천**: F1 + F4를 먼저 하고 다시 잰다. F2·F3은 그 결과를 보고 정한다.

## 조치

- README β 절: "OS 대비 이득은 주장하지 않는다"를 다음으로 바꾼다. "macOS M1, GPT-2 기준으로 OS에 맡길 때보다 2~3배 빨리 돌아오고(비트 동일), 다른 작업이 메모리를 얻는 속도에는 차이가 없으며, 해제한 CPU 메모리는 압박이 올 때까지 프로세스에 남는다(F-E011-1)."
- 논문 B에 "메모리 회수"를 주장하려면 F-E011-1을 고친 뒤 다시 재야 한다.

## 한계

- 기기 1대, 모델 1개(0.5GB), 압박 1가지(4GiB)다. 모델이 압박에서 차지하는 비율이 작아서 D2의 검출력이 낮다. 큰 모델 조건이 필요하다.
- 시작할 때부터 스왑을 많이 쓰고 있었고(6.6GB), 다른 앱도 함께 돌았다. 조건 사이의 변동이 크다(B 채우기 3.4~8.5초). 판정은 중앙값으로 했다.
- 잠자기로 8개 시행을 다시 돌렸다. 재실행은 원래 순서가 아니라 연속으로 돌았으므로, 순서를 돌려서 흐름을 섞는 효과는 그 8개에서 약하다.
- 커널 압축기의 비율은 대용 측정이다.

## 논문 매핑

- **논문 B Evaluation**: 표 3개와 판정표. 핵심 문장: "On an 8 GB M1 under 4 GiB of competing pressure, restoring hibernated GPT-2 weights from their source file took 0.33–0.45× the time of letting macOS page them back in, bit-exact; it did not speed up the competing process."
- **논문 B Discussion**: 기대했던 이득(메모리를 다른 앱에 돌려줌)이 할당기 수준의 현상(libmalloc 캐시) 때문에 실현되지 않았다. 할당기와의 상호작용은 텐서 수준 메모리 도구의 숨은 변수다. mmap된 가중치와 익명 가중치의 구분도 다룬다.
- **Threats to Validity**: 효과 크기(모델/압박 12%), 잠자기 사건과 재실행, 단일 기기.
- **연구 방법론**: 실행 중 사건을 결과를 보기 전에 규칙으로 고정한 과정.
