# 0058. E011 사전 등록: β 대 macOS 스왑·압축기

- **날짜**: 2026-09-26
- **유형**: experiment (사전 등록)
- **상태**: 확정 (결과는 다음 기록)
- **관련 기록**: 0022 R3 (E011 제안), 0032 (채택), 0036 (배포 전 검증으로 이동), 0039·0040 (β, "OS 대비 이득은 주장하지 않는다"), 0057

## 배경

> "E011 실험을 진행해."

E011은 0022 R3에서 제안했다. β의 가장 가까운 경쟁자는 OS다. 쓰지 않는 메모리는 OS도 압축하고 스왑으로 내보낸다. β만의 이득으로 가정한 것은 세 가지다: 객체 단위로 동작하고, 복원 시간을 예측할 수 있고, 압축해서 내보낸다. 이 이득은 측정한 적이 없다. 그래서 0036부터 "OS 대비 이득은 주장하지 않는다"는 제한을 두었다. 이 실험은 그 제한을 풀지 유지할지를 정한다.

원래 측정 항목(0022 R3)은 네 가지다: 회수량, 복원 지연, 시스템 반응성, 실제 macOS 압축기의 fp32 압축률.

## 1. 파일럿 (판정에 쓰지 않음)

도구를 확인하려고 파일럿을 두 번 돌렸다. 데이터는 `docs/research/data/e011/pilot.json`, `pilot2.json`에 있다. 파일럿에서 나온 사실 가운데 설계를 바꾼 것은 다음과 같다.

1. **상주 페이지 조사가 모델을 깨웠다.** 조사에 `model.parameters()`를 썼는데, 이것은 가드가 걸린 경로다(0048). 그래서 1차 파일럿의 β 복원 시간은 무효다. 이제는 시작할 때 파라미터 목록을 잡아 두고 조사한다.
2. **CPU의 fp32 가중치는 파일에서 mmap된다.** transformers 5는 CPU에서 dtype을 바꾸지 않을 때 safetensors 파일을 그대로 매핑한다. 불러온 직후 프로세스의 물리 사용량(phys_footprint)은 3MB만 늘었다. 이 페이지들은 깨끗한 파일 페이지라서 OS가 압축이나 스왑 없이 버리고 나중에 다시 읽는다. 학습·dtype 변환·제자리 갱신 뒤의 가중치는 익명 메모리라서 OS가 압축하거나 스왑해야 한다. **두 경우를 나눠 잰다**(`mmap`, `anon`).
3. **macOS에서는 해제한 CPU 메모리가 OS로 바로 돌아가지 않는다.**
   - GPT-2 크기의 텐서 49개(525MB)를 해제해도 phys_footprint는 683MB 그대로였다.
   - `vmmap`을 보면 이 메모리가 libmalloc의 `MALLOC_LARGE (empty)` 캐시에 남아 있다. 내용은 쓰레기지만 커널에는 더러운(dirty) 페이지이므로, 압박이 오면 커널은 이것도 압축하거나 스왑한다.
   - `MallocLargeCache=0`으로 시작한 프로세스에서는 해제 즉시 156MB로 줄었다. `malloc_zone_pressure_relief`는 0바이트를 돌려주었다.
   - 이 현상은 memopro만의 것이 아니다. `del model`에도 똑같이 적용된다.
   - 2차 파일럿(1GiB 압박)에서는 압박 알림이 오자 libmalloc이 캐시를 비웠다(β 984MB → 320MB, `del` 814MB → 303MB).
   - 이를 재려고 진단용 방법 `source_nocache`(캐시를 끈 프로세스의 `source`)를 넣는다. 이것은 **판정 대상이 아니며**, 캐시 문제를 고쳤을 때의 상한을 보여 준다.
4. `source` 동면 직후에는 phys_footprint가 오히려 늘었다(815MB → 984MB). 원본과 대조하려고 텐서마다 잡은 버퍼가 위의 캐시에 남기 때문이다. 살아 있는 추가 메모리는 텐서 하나 이하이지만, 캐시에 남는 양은 그보다 크다.

## 2. 설계

### 조건과 방법

| 조건 | 가중치 | 방법 |
|---|---|---|
| cpu/mmap | transformers가 불러온 그대로(파일 매핑) | os, source, compress, reload |
| cpu/anon | 익명 메모리로 복사 | os, source, compress, reload, source_nocache(진단) |
| mps/anon | MPS 장치 메모리 | os, source, compress, reload |

- **os**: 아무것도 하지 않는다. 메모리 처리를 macOS에 맡긴다.
- **source / compress**: `memopro.hibernate.now(model, mode=...)`.
- **reload**: `del model; gc.collect()`(MPS는 `empty_cache`). 돌아올 때 `from_pretrained`로 다시 불러온다. 사람들이 흔히 쓰는 수동 방법이다.

`host`는 뺀다. 통합 메모리에서는 아무것도 해제하지 않기 때문이다(0039). `spill`도 뺀다. 이 Mac의 디스크 여유가 7.8%로 20% 하한 아래라서 memopro가 쓰지 않기 때문이다(0032 H4, 설계대로 동작). 방출 비교는 E009에서 한다.

### 한 번의 시행 (`experiments/e011_os_swap/run.py`)

1. 프로세스 A가 GPT-2 fp32(497,759,232바이트)를 불러오고, 예열 순전파를 3번 하고, 기준 출력의 해시를 기록한다.
2. A가 해당 방법으로 쉰다. A의 phys_footprint를 **즉시 회수량**으로 잰다.
3. 프로세스 B(다른 작업)가 압축되지 않는 난수 P바이트를 64MiB씩 채운다. **B의 채우기 시간**이 다른 작업의 반응성이다.
4. 5초 뒤, B가 메모리를 잡고 있는 동안 A의 phys_footprint·상주 크기와 가중치 페이지의 상주 비율(`mincore`)을 잰다. vm_stat 압축기 변화량도 기록한다.
5. A가 돌아온다(깨우기, 다시 불러오기, 또는 그대로). 첫 순전파가 끝날 때까지가 **복귀 지연**이다. 출력이 기준 해시와 같은지 확인하고, 두 번째 순전파 시간과 A의 page-in·디스크 읽기 양도 기록한다.
6. B가 자기 버퍼의 모든 페이지를 1바이트씩 읽는다. **B의 재접근 시간**은 A의 복귀가 다른 작업에 준 비용이다.
7. 두 프로세스를 끝내고 15초 쉰다.

- **압박 크기 P**는 실행을 시작할 때 한 번 정하고 모든 시행에 똑같이 쓴다. 값은 OS 추정 가용량(kernel available)에 모델 크기를 더한 것이고, 4GiB를 넘지 않는다. 이만큼이면 OS가 파일 캐시만 버려서는 모자라고 익명 메모리를 압축하거나 스왑해야 한다.
- **반복**은 5회다. 반복마다 방법의 순서를 돌리고 조건도 번갈아 해서, 기기 상태의 흐름이 모든 방법에 고르게 섞이게 한다.

### 압축률 (`experiments/e011_os_swap/ratio.py`)

GPT-2 가중치(fp32와 bf16 사본)를 두 방식으로 압축해 비교한다.
- libcompression LZ4·LZFSE로 16KiB·4KiB 페이지마다 따로 압축한다. 커널 압축기도 페이지 단위로 동작하므로 그 대용이다. 커널 압축기(WKdm/LZ4 혼합)를 직접 부를 수는 없다.
- memopro `compress`(바이트 셔플 + zstd, 수준 1·3).

## 3. 판정 기준 (실행 전 고정)

지표는 조건마다 5회의 중앙값이다. 최솟값과 최댓값도 함께 보고한다.

| # | 질문 | 기준 |
|---|---|---|
| D0 | 정확성 | 모든 조건·방법에서 복귀 후 출력이 기준과 비트 단위로 같다. 하나라도 다르면 β 결함이다 |
| D1 | OS로 돌려주는가 | cpu/anon과 mps에서, `source`를 적용한 직후 A의 phys_footprint가 모델 크기의 80% 이상 줄면 "돌려준다", 아니면 "돌려주지 않는다" |
| D2 | 다른 작업의 반응성 | B의 채우기 시간이 `source` ≤ 0.8 × `os`이면 β가 유리하다 |
| D3 | 복귀 지연 | `source` ≤ 0.8 × `os`이면 더 빠르다, ≥ 1.25 × `os`이면 더 느리다, 그 사이면 같다. `reload`와도 같은 규칙으로 비교한다 |
| D4 | 압축률 | 같은 dtype에서 memopro 비율 ≤ LZ4 16KiB 페이지 비율 − 0.05이면 memopro `compress`가 OS 압축기보다 낫다 |
| D5 | 복귀가 다른 작업에 준 비용 | B의 재접근 시간. 보고만 한다 |

cpu/mmap은 D1·D2의 판정 대상이 아니다(보고만 한다). **예상**: 이 조건에서는 OS가 이미 깨끗한 페이지를 공짜로 버릴 수 있으므로 β에 이득이 없고, 오히려 β는 복원한 가중치를 익명 메모리로 바꾼다.

### 결론과 조치

- D0이 실패하면 β 결함으로 기록하고 먼저 고친다.
- D1이 cpu/anon에서 실패하면 결함 F-E011-1로 기록한다. 고치고 다시 잴 때까지 "macOS에서 β가 CPU 메모리를 다른 앱에 돌려준다"고 말하지 않는다. 고치는 방법은 사용자 결정으로 올린다.
- D2나 D3에서 적어도 한 조건(cpu/anon 또는 mps)이 D0과 함께 유리하게 나오면, 그 조건에 한정해 이득을 보고할 수 있다.
- 두 조건 모두 D2·D3에서 이득이 없으면 README와 논문 B에 이렇게 적는다: "macOS 통합 메모리에서는 OS 스왑 대비 측정된 이득이 없다. β의 가치는 제어(명시적 시점, 비트 동일 확인)와 OS 스왑이 없는 CUDA VRAM에 있다."
- D4의 결과로 macOS에서 `compress`의 쓸모를 정한다.

## 한계 (미리 적어 둠)

- 기기는 한 대이고 이미 스왑을 많이 쓰고 있다. 다른 앱(데스크톱 앱 등)도 함께 돈다. 순서를 돌리는 것으로 흐름만 줄인다.
- 모델은 GPT-2(0.5GB) 하나다. 압박 P는 기기 상태에 따라 정해지므로 다른 날 재현하면 P가 달라진다.
- 커널 압축기의 실제 비율은 페이지 단위 대용 측정으로만 본다. vm_stat 변화량은 다른 프로세스의 영향을 받으므로 참고로만 쓴다.
