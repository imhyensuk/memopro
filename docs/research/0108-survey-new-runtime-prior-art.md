# 0108. 선행 연구 조사: "버퍼마다 저장·압축·원본 재읽기·재계산·이동을 고르는 Rust 런타임"의 새로움 판정

- **날짜**: 2026-09-29
- **유형**: survey
- **상태**: 확정 (조사). 새로움은 "조사 범위에서 발견되지 않음" 수준의 판정이다
- **관련 기록**: 0107 (목표 재정의), 0006·0007 (초기 새 기법 탐색), 0029 (중복성 검사 3차), 0011·0060 (β·E011), 0067~0072 (F 등급, E015·E016), 0080 (MPS 힙), 0102·0105 (CUDA 캐시 조각)

## 목적

0107의 G3 후보 아키텍처가 기존 연구와 얼마나 겹치는지 확인한다. 이 결과로 무엇을 새로 만들 가치가 있고 무엇을 새롭다고 주장할 수 있는지 정한다.

**조사 대상 후보 (C-R: Recipe Runtime)**
- 큰 버퍼 하나하나를 "만드는 법(원본 파일, 계산 계보, 시드) + 현재 상태"로 다루는 사용자 공간 런타임이다. 핵심은 Rust이고, C ABI와 Python에서 쓴다.
- 메모리가 부족하면 버퍼마다 다섯 가지 가운데 가장 싼 것을 실측 비용으로 고른다.
  - 그대로 두기
  - 무손실 압축(RAM)
  - 버렸다가 원본에서 다시 읽기(해시 확인)
  - 버렸다가 계보로 재계산
  - SSD로 이동
- 접근 순서를 알면 미리 가져와 계산과 겹친다.
- 메모리 상한을 보장하고, 실행 전에 느려질 정도를 예측한다.
- 한 대의 개인 기기(노트북 SSD, 압축 RAM, Apple 통합 메모리)가 대상이다. AI와 비AI를 가리지 않는다.

## 판정

### 이미 있는 것 (새롭다고 주장하지 않음)

- 재계산 자체(Chen, Checkmate, DTR).
- **텐서 단위 스왑 대 재계산 선택**(Capuchin), **재계산 + 페이징 공동 최적화**(POET).
- 객체 단위 원격 메모리 런타임과 미리 읽기(AIFM, Mira, Atlas).
- userfaultfd 사용자 공간 페이징과 out-of-core(UMap, ExtMEM).
- 커널 압축·SSD 오프로드(TMO, zswap).
- **계보 기반 재사용 + 메모리 관리 결합**(MEMPHIS, 선언형 ML 시스템 안).
- 플래시에서 LLM 가중치 가져오기(LLM in a flash), 온디바이스 LLM 탄력 방출·복원(mzCache).
- 압축된 채 계산(CLA), 단편화 제거 할당기(Mesh).

### 조사 범위에서 발견되지 않은 것 (C-R의 새로움 후보)

아래를 **한 런타임에서 함께** 하는 것은 조사 범위에서 발견되지 않았다.

1. **다섯 선택지의 통합**: 그대로 두기 / 무손실 압축 / 원본 재읽기(해시 확인) / 계보 재계산 / SSD 이동. 버퍼마다 **실측 비용**으로 고른다.
   - 가장 가까운 Capuchin은 둘(스왑·재계산), POET도 둘(재계산·페이징), MEMPHIS는 재사용 중심이다.
   - **"원본에서 다시 읽기"를 검증된 선택지로 두는 것**(β `source`, F 등급)은 위 시스템들의 선택지에 없었다. LLM in a flash는 원본 읽기를 하지만 LLM 한정이고 선택 구조가 없다.
2. **분야 무관**: DL 텐서와 비AI 버퍼(NumPy 배열, 이미지, 데이터프레임 열)를 같은 런타임이 관리한다. Python과 C ABI 양쪽에서 쓴다.
   - 앞의 DL 시스템들은 DL 한정이고, 원격 메모리 런타임들은 선택지가 위치뿐이다.
3. **개인 기기 계층**: 노트북 SSD, 압축 RAM, Apple 통합 메모리가 대상이다.
   - 원격 메모리 연구는 데이터센터 RDMA, TMO는 서버 군이 대상이다.
   - Mac에는 userfaultfd가 없어 명시적 핸들 방식이 필요하다는 제약도 다룬다.
4. **메모리 상한 보장 + 실행 전 느려짐 예측**: 예산을 넘지 않음을 보장하고 예상 속도를 먼저 알린다.
   - POET·Checkmate는 계획 시점의 최적화이고, 실행 중 상한 보장과 사용자 보고는 초점이 아니다.

### 새로움의 성격과 위험

- **조합의 새로움**이다. 개별 기법은 모두 선행 연구에 있다. 따라서 "새로운 기법"이 아니라 **"새로운 런타임 구조와 그 달성(격차 해소율)"**으로 주장해야 한다.
  - 검토자는 "엔지니어링 통합"으로 볼 위험이 있다.
  - 이를 덮으려면 두 가지가 필요하다: (a) 통합했기 때문에 가능해지는 결과(OS 스왑·Dask·UMap·Capuchin 단독으로는 안 되는 작업을 1/2~1/4 메모리로 구동), (b) 비용 모델과 선택 정책 자체의 분석.
- **재계산의 적용 한계**: 임의 프로그램의 계보는 알 수 없다. 재계산은 다음 경우에만 가능하다.
  - DL 자동미분 그래프.
  - 런타임 API로 만든 버퍼.
  - 파일에서 읽은 데이터(재읽기).
  - 이 범위를 논문에 분명히 적는다.
- **2026년 신규 연구가 빠르게 나오고 있다**: mzCache(2026-09), "Beyond Storage: State as a Runtime Control Problem"(arXiv 2607.16836, 2026-07, 개념 정리 조사 논문). 제출 전에 다시 조사한다.

## 설계에 주는 함의

1. **실측 비용 기반 선택**: Capuchin(첫 반복 측정)과 memopro의 기존 실측을 비용 모델의 초기값으로 쓴다(E011 복원 속도, E015 재읽기 0.28GB/s 대 큰 읽기, E008 압축 속도).
2. **플랫폼별 두 모드**
   - Linux: userfaultfd 투명 모드(UMap·ExtMEM이 실현 가능성을 보였다).
   - macOS: 명시적 핸들(β처럼).
   - Mac에서의 투명 모드는 연구 과제로 둔다.
3. **관리 버퍼 전용 할당기(아레나)**: MPS 힙·CUDA 조각 같은 할당기 낭비를 런타임이 직접 통제한다(Mesh 계열 발상, RS4 상한과 결합).
4. **OS 압박 신호에만 기대지 않는다**: γ(E013a)와 달리 TMO는 PSI로 성공했다. 차이는 응용 지식 없이 서버 군 단위로 조절한 데 있다. 새 런타임은 자기 예산과 실측 상주량으로 결정한다.
5. **비교 대상(실험)**
   - OS 스왑(macOS 압축기, Linux zswap/zram).
   - Dask 방출(비AI).
   - UMap(비AI out-of-core, Linux).
   - DTR·Capuchin 류 재계산(AI).
   - accelerate/DeepSpeed 오프로드(AI).
   - 온디바이스 LLM의 LLM in a flash·mzCache.
