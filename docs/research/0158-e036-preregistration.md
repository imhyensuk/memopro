# 0158. E036 사전 등록: 성공 기준 S1 — 8GB M1에서 Qwen2.5-7B 16비트 LoRA를 한 줄 API로

- **날짜**: 2026-10-05
- **유형**: experiment (사전 등록)
- **상태**: 확정. 실행 전
- **관련 기록**: 0148 (S1), 0138 (G4-B1: 3B), 0151 (E034: mlx-tune은 3B에서 메모리 부족), 0157 (체크포인팅 항상 켬), 0125 (Unsloth: 7B 16비트 LoRA 약 19GB)

## 사용자 지시와 내려받기

- "디스크 비웠어, S1 진행해." 디스크 여유가 25GiB였다.
- `Qwen/Qwen2.5-7B-Instruct`를 리비전 `a09a35458c702b33eeacc393d103063234e8bc28`로 고정해 내려받았다.
  - 받은 파일: safetensors 4개(14.2GiB), 설정, 토크나이저.
  - 0126의 허락("7B 이상은 사용자가 디스크를 비운 뒤")에 따른 것이다. 받은 뒤에도 10GiB 넘게 남는다(안전 조건).
- **판단**(사용자가 "필요한지 판단해서 진행해"라고 함, 앞 대화)
  - S1은 남은 핵심 성공 기준이다. Unsloth가 19GB를 요구하는 바로 그 과제다(0125).
  - 16GB Mac은 없다. 하지만 memopro의 메모리는 모델 크기가 아니라 예산이 정한다. 그래서 8GB M1에서 완주하면 16GB 기기에서의 완주를 더 강하게 보인다.
  - E034에서 mlx-tune은 3B도 시작하지 못했으므로, 7B 비교는 돌리지 않는다.

## 설계

- **모델**: Qwen2.5-7B-Instruct bf16(28층, hidden 3,584, MLP 18,944, 어휘 152,064, 임베딩과 출력 머리가 묶여 있지 않음 — 각 1,039MiB가 가장 큰 텐서).
- **API**: `rtt.stream_model(MODEL, budget, device="mps", revision=고정)` → `memopro.finetune(model, texts, seq_len=129)`.
  - 기본값 그대로다: LoRA r 8, alpha 16, q·k·v·o, AdamW 2e-4, 재진입 체크포인팅, 조각 손실.
- **데이터**: E034의 `texts.json` 앞 5개. 128토큰 + 끝 토큰 = 129토큰이 한 단계라서 5단계다.
- **경우**: L7a 예산 2GiB, L7b 예산 1.5GiB. 각각 새 프로세스. 스왑 오염 규칙(> 64MiB면 한 번 반복, 첫 시도는 따로 남김).
- **환경**: E028c와 같다(`MallocLargeCache=0`, `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.1`, 오프라인). 전원과 저전력 모드는 `env.json`에 기록한다.
- **명령**: `caffeinate -i .venv/bin/python -m experiments.e036_7b_lora.run --all`. 결과는 `docs/research/data/e036/`.

## 기준 (S1 판정)

| # | 기준 |
|---|---|
| **K1** 완주 | 두 예산 모두 5단계를 끝낸다 |
| **K2** 무손실 | 단계별 손실이 두 예산에서 비트 동일 |
| **K3** 메모리 | 두 경우 모두 footprint 증가 ≤ 예산 + 512MiB, 스왑 증가 ≤ 64MiB(오염 규칙 뒤), 런타임 최대 계상 ≤ 한도 |

- **보고**: 단계 시간, 토큰/초(단계 2~5), 실행 전체의 다시 읽은 바이트.
- 실패하면 멈추고 보고한다.
