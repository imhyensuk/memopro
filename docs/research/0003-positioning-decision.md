# 0003. 포지셔닝 전환: 기법 구현 → 메모리 플래너

- **날짜**: 2026-09-24
- **유형**: decision
- **상태**: 대체됨(→ 0005: 사용자가 기법 구현 노선 선택) — 범위 조정 권고(→ 0004)
- **관련 기록**: 0001, 0002

## 배경 / 동기

초기 논의에서는 첫 버전(MVP)으로 **mmap 제로카피 텐서 저장소 + 블록 양자화**를 추천했다
(CPU만으로 개발 가능, 세 목표를 모두 시연, 효과가 수치로 드러남).
그러나 0002 조사 결과 두 기능 모두 safetensors, bitsandbytes, torchao 등과 거의 완전히 겹친다.

## 고려한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 개별 기법 재구현 (mmap, 양자화 등) | 구현 범위 명확, 벤치마크 쉬움 | 성숙한 대형 프로젝트와 정면 경쟁, 학술적 기여 약함 |
| B. 특정 하드웨어 전용 커널 (예: Apple Silicon 양자화 커널) | 틈새 존재 가능 | 범위 협소, 하드웨어 종속, G1(전 단계) 목표와 거리 |
| **C. 메모리 플래너 (예측 → 설계 → 적용)** | 빈 자리, 기존 도구를 부품으로 활용(경쟁 대신 보완), 연구 질문 명확 | 예측 정확도 확보가 어려움, 다양한 모델 구조 대응 필요 |

## 결정

**선택지 C 채택.** memopro는 딥러닝 워크로드의 **메모리 플래너**가 된다.

```
estimate  →  plan  →  apply
(예측)       (설계)     (적용)
```

- `estimate(model, config)` — 실행 없이 피크 메모리와 구성요소별(params/grads/optimizer/activations) 내역 예측.
- `plan(model, budget, config)` — 예산 제약을 만족하면서 비용(속도 저하·정확도 손실)을 최소화하는 기법 조합 탐색.
- `apply()` — 선택된 조합을 기존 도구(bitsandbytes, torchao, torch.utils.checkpoint, 오프로딩 등)로 적용.

첫 버전(v0.1)은 **`estimate`**.

## 근거

1. **공백**: 예측·자동 설계 분야는 대표 라이브러리가 없고, 기존 추정기의 정확도 한계가 보고됨 (0002).
2. **목표 정합성**
   - G1: 실행 전 예측으로 개발·학습·활용 전 단계의 OOM 시행착오 제거.
   - G2: 예산 기반 설계로 더 작은 메모리에서 구동.
   - G3: 메모리 계층(GPU / 통합메모리·RAM / SSD) 간 이동 비용을 비용 모델에 포함.
3. **Rust의 역할이 분명함**: liveness 분석, 조합 탐색 등 계산량이 큰 부분을 Rust 코어가 담당.
   Python은 그래프 추출과 프레임워크 연동에 집중.
4. **연구 가능성**: RQ1(예측 정확도), RQ2(자동 설계 효과), RQ3(하드웨어 차이)가 정량 평가 가능.
5. **점진적 확장**: estimate만으로도 독립적 가치가 있어 v0.1 조기 배포 가능.

## 설계상 핵심 가정 (검증 필요)

- PyTorch 모델은 meta device / FakeTensor / torch.fx로 **가중치를 올리지 않고** 연산 그래프와 텐서 shape을 추출할 수 있다.
- 텐서 생존 구간(liveness) 분석으로 피크를 근사할 수 있으며, 할당자(CUDA caching allocator, MPS) 오버헤드는 보정항으로 모델링 가능하다.
- 기법 조합의 메모리 효과는 대부분 합성 가능(composable)하다. 상호작용이 있는 경우는 실험으로 확인한다.

## 위험

- 동적 제어 흐름(데이터 의존 분기)이 있는 모델은 정적 추출이 어렵다 → 대표 입력 기반 트레이싱으로 대응.
- 백엔드(CUDA / MPS / CPU)별 할당자 동작 차이 → 백엔드별 보정 및 실측 검증 필요.
- 개발 기기가 M1 8GB라 CUDA 실측 검증은 외부 GPU 환경(예: Colab, 클라우드) 필요.
