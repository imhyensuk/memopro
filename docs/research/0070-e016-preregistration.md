# 0070. E016 사전 등록: RCR 추론 시제품(F 등급) 대 E014 방법

- **날짜**: 2026-09-28
- **유형**: experiment (사전 등록)
- **상태**: 확정 (결과는 다음 기록)
- **관련 기록**: 0066 (RCR), 0068 (E015: G-F·G-P 통과), 0069 (MPS int4 백엔드), 0062·0063 (E014)

## 배경

> "PR #10 병합하고 int4 백엔드 교체 후 E016 진행해"

0066의 가설 H-RCR은 이렇다. 가중치를 F 등급(OS가 쓰기 없이 버리고 다시 읽는 깨끗한 파일 페이지)으로 쥐면, 모델이 여유 메모리보다 커도 스왑 쓰기가 거의 없고, 압박에서 멈추지 않고 서서히 느려진다. E015에서 두 전제(G-F, G-P)가 성립했으므로, 이제 **모델 전체**로 E014와 같은 조건에서 잰다.

## 1. 시제품 (`experiments/e016_rcr/fclass.py`)

- **`load_bf16`**
  - 원본 safetensors 파일을 **그대로** 읽기 전용으로 매핑하고, 파일마다 무복사 Metal 버퍼 하나를 만든다.
  - 모든 가중치는 그 버퍼의 uint8 텐서를 오프셋으로 자른 보기(view)다. 변환도, 추가 디스크도 없다.
  - 골격은 `accelerate.init_empty_weights`로 만든다. 생성 설정(`generation_config.json`)은 `from_pretrained`처럼 읽는다.
- **`build_int4` / `load_int4`**
  - 0069 경로(torch int4pack)로 **한 번** 변환해, 텐서마다 16KiB 정렬한 F 파일과 JSON 목록을 쓴다.
  - 크기는 1.5B 1.15GiB, 3B 2.08GiB이고, scratchpad에 둔다(디스크 동의·20% 하한은 실험 도구라 적용하지 않음).
- **`Prefetcher`**: 디코더 층 i가 시작될 때 층 i+1, i+2의 파일 범위를 8MiB 단위로 읽어 페이지 캐시를 데운다(E015 Q1).

## 2. 파일럿 (판정에 쓰지 않음; `data/e016/pilot.json`, 1.5B, 1회)

- **정확성**
  - rcr_bf16 출력이 `naive`와, rcr_int4 출력이 memopro_int4와 모두 **토큰 단위로 같았다**(따로 확인한 32토큰 비교 포함).
  - 처음에는 골격이 `generation_config`를 읽지 않아 출력이 달랐다. 고친 뒤 같아졌다.
- **결과**

| 방법 | A tok/s | A 최대 footprint | A 스왑 증가 | A 탐침 p95 | B tok/s | B 탐침 p95 |
|---|---|---|---|---|---|---|
| naive | 11.6 | 3.63GB | +1.44GB | 238ms | 2.4 | 8ms |
| memopro_int4 | 13.9 | 2.48GB | 0 | 24ms | 7.6 | 55ms |
| rcr_bf16 | 10.0 | 0.54GB | 0 | 7ms | 4.1 | **450ms** |
| rcr_int4 | 17.7 | 0.53GB | 0 | 0.5ms | 15.0 | 0.5ms |
| rcr_int4_nopf | 19.6 | 0.52GB | 0 | 0.6ms | 14.8 | 7.8ms |

- **관찰**
  - rcr_bf16은 압박 중(B) 파일의 67%를 잃었다가 매 토큰 다시 읽었다. 디스크 경합으로 탐침이 450ms가 됐다. 스왑 쓰기는 없지만 **I/O가 시스템을 느리게 한다**.
- **탐침 기준의 수정**
  - 이번 유휴 탐침 p95는 0.72ms로 E014(12.1ms)보다 훨씬 한가했다. "유휴의 2배" 기준(1.4ms)은 잡음에 좌우된다.
  - 그래서 탐침 기준을 **max(유휴 p95의 2배, 24.1ms)**로 정한다. 24.1ms는 E014에서 쓴 값이며, 실험 사이의 비교 가능성을 위해 쓴다.
  - 이 수정은 파일럿을 본 뒤 정했다.

## 3. 설계 (`experiments/e016_rcr/run.py`)

- 경우마다 새 작업 프로세스를 쓴다. 조율 스크립트가 밖에서 footprint(0.2초 간격 최대), 시스템 스왑 증가, 반응성 탐침(E014 `probe.py`)을 단계별로 잰다.
- **A 단계**: 불러오기, 예열 4토큰, 첫 토큰 시간, 64토큰 생성.
- **B 단계**: E011 압박 프로세스가 P 바이트(시작 시 OS 추정 가용량 + 1GiB, 4GiB 상한)를 채우고 5초 뒤 64토큰을 다시 생성한다. 같은 토큰인지와 파일 상주 비율의 전후도 기록한다.
- **모델**: Qwen2.5-1.5B-Instruct, Qwen2.5-3B-Instruct.
- **방법**: `naive`, `memopro_int4`(int4에 딱 맞는 강제 예산), `rcr_bf16`, `rcr_int4`, `rcr_int4_nopf`.
- 반복 3회, 순서 회전. 한 단계의 제한 시간은 10분이고, 넘긴 방법은 이후 반복을 건너뛴다(0062와 같음). 디스크 여유가 5GiB 미만이면 건너뛴다. `caffeinate -is`로 실행한다.

## 4. 판정 기준 (실행 전 고정)

지표는 3회 중앙값이다.

| # | 질문 | 기준 |
|---|---|---|
| E1 | 정확성 | 모든 반복에서 rcr_bf16의 A 토큰 = naive의 A 토큰(같은 모델), rcr_int4·rcr_int4_nopf의 A 토큰 = memopro_int4의 A 토큰 |
| C2 | 쾌적한가 (A 단계) | 네 가지를 모두 만족: 생성 ≥ 5 tok/s, 불러오기 ≤ 120s, 스왑 증가 ≤ 1GiB, 탐침 p95 ≤ max(유휴 p95 × 2, 24.1ms) |
| H1 | 메모리 | A 단계 최대 footprint가 rcr_bf16 ≤ 0.25 × naive, rcr_int4 ≤ 0.25 × memopro_int4 |
| H2 | 스왑 쓰기 | A 단계 스왑 증가가 RCR 세 방법 모두 ≤ 0.1GiB |
| H3 | 압박에서의 우아함 (B 단계) | rcr_int4의 B tok/s ≥ 0.5 × 자신의 A tok/s이면서 ≥ memopro_int4의 B tok/s. rcr_bf16의 B tok/s ≥ naive의 B tok/s(naive가 B를 끝내지 못하면 성립) |
| P | 선읽기 효과 | rcr_int4 대 rcr_int4_nopf의 B tok/s와 B 탐침 p95. 보고만 한다 |

## 결론 규칙

- **E1·H1·H2가 두 모델에서 성립하면**: RCR F 등급을 memopro 기능으로 만드는 **결정 기록을 연다**(사용자 결정). 후보는 `load`의 새 후보 또는 설정이다.
- **rcr_int4가 두 모델에서 C2를 만족하면**: "M1 8GB에서 1.5B·3B int4 추론을 쾌적하게"를 이 조건에 한정해 보고할 수 있다. E014에서는 어떤 방법도 C2를 만족하지 못했다.
- **H3이 실패하면**: 압박 대응은 쾌적 제어기(E017)의 과제로 넘긴다.

## 한계 (미리 적어 둠)

- 기기 1대, 프롬프트 하나, 64토큰이다.
- 탐침 기준과 시제품 수정(`generation_config`)은 파일럿을 본 뒤 정했다.
- F 파일은 scratchpad에 둔 실험용이다. 제품에서는 디스크 동의와 예산을 따른다.
- P 등급(purgeable KV 등)과 쾌적 제어기는 이번 범위가 아니다.
- 한 모델의 방법들은 같은 원본 파일을 읽는다. 앞선 경우가 페이지 캐시를 데워 둘 수 있으므로, 순서를 회전해 섞는다.
