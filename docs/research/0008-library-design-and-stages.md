# 0008. 라이브러리 설계 및 개발 단계 구조화

- **날짜**: 2026-09-24
- **유형**: design + decision
- **상태**: 대체됨(→ 0010: 범용성 중심 설계 v0.2)
- **관련 기록**: 0006, 0007
- **설계 문서**: [docs/design/architecture.md](../design/architecture.md), [docs/design/development-plan.md](../design/development-plan.md)

## 배경 / 동기

0006(후보 α·β·γ)과 0007(관찰 우선 방법론)의 결과를 실제 개발 가능한 구조로 옮긴다.
핵심 제약은 두 가지다. 주력 후보 α가 **미검증**이라는 점, 그리고 최종 목표가 **crates.io·PyPI 배포**라는 점이다.

## 주요 설계 결정

| # | 결정 | 이유 | 대안 |
|---|---|---|---|
| D1 | 기법은 독립 모듈, Rust 코어는 공용 | 한 기법의 실패가 전체를 막지 않음 | 단일 기법 라이브러리 |
| D2 | Rust 코어는 프레임워크 비의존 (바이트·dtype·shape만) | crates.io 단독 가치, 테스트 용이 | Rust에서 tch-rs로 torch 직접 사용 (빌드 복잡도 큼) |
| D3 | 뜨거운 경로는 장치(torch 연산), 차가운 경로는 Rust | GPU/MPS 텐서를 CPU로 복사하면 α의 이득이 사라짐 | 전부 Rust (0004에서 지적한 Rust 필요성 약점을 정직하게 반영) |
| D4 | α는 블록 단위 `autograd.Function` + `RFCChain` | 블록 간 의존성(x_{l+1} → x_l)을 표현해야 함 | `saved_tensors_hooks` (텐서 단위라 부적합) |
| D5 | 연구 트랙과 엔지니어링 트랙 병렬 + 관문 | 미검증 가설이 일정 전체를 막지 않음 | 순차 진행 |
| D6 | 첫 배포(v0.1.0)는 β | α 결과와 무관하게 사용자 가치를 먼저 전달하고 배포 파이프라인을 조기 검증 | α 우선 배포 |
| D7 | 관문 판정 기준은 실험 **전에** 기록 | 사후 기준 조정(p-hacking) 방지, 논문 신뢰성 | 결과 보고 판단 |
| D8 | census를 연구 도구이자 사용자 기능으로 | 0007 방법론 실행과 G1(개발 단계 메모리 가시화)을 동시에 충족 | 연구 전용 스크립트 |

## 개발 단계 요약

S1 기반 구축 → [R1 α 검증 · R2 센서스] ∥ [E1 Rust 코어 → E2 β → v0.1.0] → 관문 Gα → E3 α → v0.2.0 + 논문 초안 → 관문 Gβ → E4 γ → v0.3.0 → S5 → v1.0.0
