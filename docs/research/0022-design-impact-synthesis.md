# 0022. 종합: 조사·검증·실험이 초기 라이브러리 설계에 준 영향

- **날짜**: 2026-09-25
- **유형**: survey (종합) + decision(제안)
- **상태**: 확정 (종합) / 제안 R1~R5는 사용자 승인 대기 / R1·R2·R3 채택(→ 0032), R4·R5 대기
- **관련 기록**: 0001~0021 전체

## 배경 / 동기

사용자 요청: "지금까지 진행한 내용을 기반으로, 초반 라이브러리 설계에 어떤 영향을 주는지 정리하라."
초기 설계의 각 요소를 **증거(조사·검증·실험)**와 연결해, 무엇이 유지·변경·폐기되었는지 추적한다.

## 2. 설계 영역별 영향

### A. 가치 제안의 무게중심 이동

- 초기에는 **"새로운 기법으로 메모리를 줄인다"**였다.
- 지금은 **"PyTorch 개발자의 메모리 회수·진단 + 기존 기법의 쉬운 적용 + 일부 고유 기능"**이다.
- 연구 코어의 학술적 무게가 줄었다. 남은 고유 기능의 성격은 다음과 같다.
  - β: 적용 설정의 새로움, 학술 가치 낮음
  - census 중복도: 측정 연구
  - γ: 중간 수준 중복
- α는 "메모리 → 연산 치환"으로 G3에 답하려던 유일한 기법이었다. 그 축이 사라졌다.

### B. Rust 코어의 역할 (0004에서 제기된 약점이 재부상)

- 처음에 Rust의 몫으로 꼽은 계산량이 큰 부분은 α의 복원 반복(장치 경로)과 플래너 탐색이었다. 둘 다 사라졌다.
- E005에서 **Python + numpy + zstandard(C 라이브러리)로도 셔플 + zstd가 단일 스레드에서 초당 102~544MB** 나왔다.
  → 압축 **속도 자체만으로는** Rust가 필수가 아니다.
- Rust가 여전히 제값을 하는 곳:
  - ① 대용량 방출에서 **여러 스레드 압축 + 비동기 I/O + GIL 해제**(2GB 모델 방출 시 단일 스레드 약 5초 → 병렬화로 단축)
  - ② 프로세스 수준 환경 감지(cgroup, OS 메모리 신호)
  - ③ crates.io 단독 사용

### C. β (동면) 설계

| 항목 | 초기 (0006) | 현재 | 근거 |
|---|---|---|---|
| 실행 방식 | 자동·투명 | **제안 + 명시 실행**, 자동은 선택 | 0013 V4~V8, 0014 P4 |
| CPU 기본 모드 | RAM 안 무손실 압축 | **압축 SSD 방출** | 0019: fp32 무손실 약 1.16배 |
| 1순위 환경 | 명시 없음 | **CUDA VRAM, 스왑 없는 환경** | 0014 P3 |
| OS 대비 이득 | 가정 | 압축 측면에서는 OS 방식(LZ4 페이지)이 fp32를 **전혀 줄이지 못함**(1.00배) → β가 우위 | 0019 (대리 지표) |
| 남은 경쟁자 | — | **OS 스왑**: 방출 자체는 OS도 한다. β의 이득(객체 단위, 예측 가능한 복원, 압축된 방출)은 **미측정** | — |

### D. census 설계

- 빠른 모드(무손실 엔트로피)는 fp32 학습 상태에서 **13~22% 중복**만 보여준다. 이것만으로는 기존 프로파일러와 차별화가 약하다.
- 큰 중복은 **정밀도**에 있다: bf16 변환 후 압축으로 2.75~3.8배, 4비트 체크포인트로 그래디언트 코사인 0.997(0018).
- 실험에서 census가 보고할 가치가 있는 현상이 새로 드러났다.
  - **거대 활성값**: 3층부터 위치 0 토큰의 노름 약 3,000(보통 60~220)
  - **이상치 때문에 블록 양자화 오차가 큼**: 4비트 약 22%
  - **LayerNorm 게인 그래디언트의 정밀도 민감성**: 전체 코사인 0.997일 때도 텐서별 최소 0.555
  - **활성값이 가중치보다 큼**: GPT-2 small, 배치 2×256에서 저장 활성값 859MiB 대 가중치 475MiB

### E. 범용 접근 계층 (v0.2)

- α와 무관하다. 0009의 관찰("LoRA 이후 병목은 활성값")은 E005에서도 확인되었다(활성값 > 가중치). 기존 기법(체크포인팅·오프로드)으로 대응한다.
- **실측으로 확인된 설계 입력**:
  - M1 8GB의 MPS 권장 한도는 **5.33GB(물리 RAM의 약 67%)**이다. 풀별 예산에서 MPS 한도를 반영해야 한다는 0011 L1 수정이 옳았다.
  - transformers 5.x에서는 **블록을 직접 호출하면 인과 마스크가 빠진다**. 블록을 감싸는 기능(체크포인팅 래퍼 등)은 라이브러리 버전별 동작을 반드시 검증해야 한다(0014 P10 호환성 정책의 근거).

### F. 원칙과 프로세스

- **측정 우선(P1)과 사전 등록이 효과를 입증했다.** 설계를 네 번 바꾸는 동안 풀리지 않던 α 문제가, 구현 전 하루 분량의 실험으로 판정되었다. 몇 주 규모의 N2(α 구현)를 쓰지 않고 피했다.
- `Technique` 인터페이스, 충실도 3분류, fail-open, 풀별 예산 등 **구조적 원칙은 영향을 받지 않았다**. 기법 하나가 빠져도 구조가 유지된다는 D1(0008) 설계 의도가 실제로 작동했다.

## 4. 실험에서 얻은 설계 규칙 (향후 기능에 적용)

| # | 규칙 | 근거 |
|---|---|---|
| K1 | 손실 저장(양자화) 기능은 **이상치 채널·토큰을 별도로 처리**해야 한다(블록 absmax만으로는 오차 22%) | 0018 E002 |
| K2 | 손실 기능은 **LayerNorm 관련 저장 텐서를 보호하거나 제외**해야 한다(게인 그래디언트가 가장 민감) | 0018 E003 |
| K3 | 전체 지표(전체 코사인 등)만 보지 말고 **텐서별 최악값**을 보고한다 | 0018 E003 |
| K4 | 역순으로 서로 의존하는 복원은 오차가 누적된다. 복원은 **독립적**이어야 한다(k=0 힌트는 평탄, 체인은 선형 누적) | 0018 E002 |
| K5 | 풀별 예산에서 통합 메모리는 **MPS 권장 한도**(8GB에서 5.33GB)를 상한으로 쓴다 | S1 환경 측정 |
| K6 | 외부 라이브러리 내부(블록 직접 호출 등)에 의존하는 기능은 **버전별 동작 검증 테스트**를 둔다 | transformers 5.x 인과 마스크 |
