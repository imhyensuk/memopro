## 결론 규칙에 따른 조치

- **C1에서 기본 설정이 두 모델 모두 실패했다.** 0062 규칙에 따라 기본값 문제로 결정 기록을 연다(아래 "기본값 문제", 사용자 결정 대기).
- **C2를 만족한 경우가 없다.** 따라서 이렇게 적는다: "이 기기(M1 8GB, 이미 스왑 5~10GB 사용)에서 1.5B·3B 모델의 추론은 memopro로도 쾌적하지 않다."
- **C5는 성립하지 않았다.** β의 "한 커널에서 여러 모델" 가치는 다음 범위로만 보고한다. 둘 다 올려 두면 멈추는 상황을 막는다. 다시 불러오기보다는 10~15% 빠르다(불러온 뒤 사용만 보면 23~27%).
  - 파일럿에서는 다시 불러오기가 181초였다. 본 실행에서는 108~115초였는데, 파일 캐시가 데워진 차이로 보인다.

## 해석

1. **"가능하게 만드는 것"은 확인됐다.** 일반 학습 루프는 MPS 한도에서 매번 실패했고, `train_session`은 결과를 바꾸지 않고 매번 완주했다. 번갈아 쓰기에서 둘 다 올려 두면 10분 안에 끝나지 않았고, β와 다시 불러오기는 1분 반 안팎에 끝났다.
2. **"쾌적하게 만드는 것"은 확인되지 않았다.** 이 기기는 시작부터 스왑을 5~10GB 쓰고 있었다. 3GB짜리 bf16 모델을 올리는 순간 다른 작업이 느려진다(탐침 61~202ms). memopro가 줄일 수 있는 것은 그 정도뿐이고, 없앨 수는 없다.
3. **기본 설정이 거부만 하는 문제가 가장 크다.**
   - 보수적 가용량(압축·스왑 없이 얻는 양)은 이 기기에서 1.3~1.9GiB였다. `balanced` 품질에서는 int4를 쓰지 않으므로 1.5B조차 들어갈 구성이 없다.
   - 사용자는 `naive`로 하면 돌아가는 모델을 memopro가 거절하는 것을 보게 된다.
   - `budget_basis="os"`도 도움이 되지 않았다. 이 순간 OS 추정 가용량도 작았다(E011 때 4.9GB, 이번에는 약 2.4GB).
4. **예상하지 못한 이득: memopro의 불러오기는 부담이 작다.** 같은 bf16 구성인데도 `memopro_4gb`는 불러오기가 2.5배 빠르고, 스왑 증가와 탐침이 약 3분의 1이었다. `naive`는 CPU에 올렸다가 `.to("mps")`로 옮기므로 잠시 두 벌을 쥔다. memopro는 transformers의 `device_map`으로 장치에 바로 올린다. 이것은 기존 기능(accelerate 경로)을 고른 결과이며 신규성은 없다. 다만 사용자가 보는 차이는 크다.
5. **β의 이득은 다시 불러오기 대비 작다.** 같은 체크포인트를 다시 읽는 것은 파일 캐시 덕분에 빠르다. β(`source`)도 결국 같은 파일을 다시 읽으므로 차이는 모델 생성 비용 정도다. β가 크게 앞설 조건은 두 가지다. 다시 불러오기가 비싼 경우(양자화·변환이 들어간 모델, 원격 체크포인트)이거나, 원본이 없어 `source`가 아닌 방법을 쓰는 경우다. 재지 않았다.
6. **MPS의 반환 문제**(그래픽 드라이버가 해제된 Metal 메모리를 붙잡음)는 여전하다. F4의 대상이 아니다.

| # | 선택지 | 효과 | 대가 |
|---|---|---|---|
| D-a | `BudgetExceeded` 메시지에 **실제로 될 설정을 계산해 제시**. 예: "`budget='4GB!'`면 bf16으로, `quality='low'`면 int4로 들어간다(스왑 예상 X GB)" | 거부가 안내로 바뀐다. 기본 동작은 그대로 | 사용자가 한 번 더 호출해야 한다 |
| D-b | 통합 메모리(MPS)의 기본 기준을 "보수적"에서 **"OS 추정과 보수적의 중간"**으로 바꾼다 | 더 많이 불러온다 | 스왑이 생긴다. 0035 원칙 변경 |
| D-c | 기본 품질을 `balanced`에서 `low`로 바꿔 int4를 허용한다 | 1.5B가 int4로 들어간다(4.9 tok/s) | 출력이 달라진다. 품질 원칙 변경 |
| D-d | 들어갈 구성이 없을 때 **경고하고 원래 형식으로 불러오기**(`naive`와 같은 결과, 단 장치에 바로 올림) | 사용자가 보는 결과가 `naive`보다 나빠지지 않는다(E014 4번 관찰) | "예산을 지킨다"는 약속이 깨진다. `strict=True`로 되돌릴 수 있게 해야 한다 |

- **추천**: D-a는 반드시 한다. 여기에 D-d를 **명시적 선택**(`fallback="stored"` 같은 설정)으로 추가한다. 기본값(D-b, D-c)은 사용자 데이터(E010) 없이 바꾸지 않는다.

## 한계

- 기기 1대이고, 이미 스왑을 많이 쓰는 상태였다. 스왑이 없는 8GB 기기라면 결과가 다를 수 있다.
- 3B는 int4와 강제 예산을 함께 준 조합(`quality="low"` + `"4GB!"`)을 사전 등록하지 않아 재지 않았다.
- 프롬프트 하나, 64토큰이다.
- 번갈아 쓰기는 같은 체크포인트의 두 인스턴스라서 다시 불러오기에 유리하다.
- 탐침은 체감의 대리 측정이다.

## 논문 매핑

- **논문 B Evaluation (사용성)**
  - 표 3개와 판정표.
  - 핵심 문장: "On an 8 GB M1 already using 5–10 GB of swap, memopro turned an out-of-memory fine-tuning run into a completing one and kept alternating two 1.5B models from stalling; no inference configuration met our comfort criteria, and memopro's conservative defaults refused both models."
- **논문 B Discussion**: 보수적 기본값의 역설. 예산을 지키는 도구가 사용자가 이미 스왑으로 감수하던 일을 거부하게 된다. 같은 구성에서도 불러오는 경로에 따라 부담이 3배 달라진다.
- **Threats to Validity**: 기기 상태(기존 스왑), 같은 체크포인트 두 인스턴스.
