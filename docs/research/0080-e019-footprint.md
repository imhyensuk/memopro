# 0080. E019 footprint 조사: 1GB는 PyTorch MPS 할당기의 1GiB 힙이다 — 저수위 비율 0.1로 없어지고 속도·출력은 그대로

- **날짜**: 2026-09-28
- **유형**: experiment (원인 조사, 사전 등록 없음)
- **상태**: 확정. 원인은 memopro가 아니라 PyTorch에 있다. 라이브러리 반영 방식은 사용자 결정 대기
- **관련 기록**: 0074 (E017: 모든 방법의 A footprint가 약 1.5GB로 E016의 0.53GB보다 큼), 0078 (3B 제어기 방법만 0.49GB, 재정착 비용도 작음), 0072 (`residency="file"`)

## 배경

> "PR #14 병합하고 P1+P3 적용 후 footprint 조사 진행해."

- E017 계열의 A 단계 최대 footprint는 거의 모든 방법에서 약 1.5GB였다.
- 예외는 3B 제어기 방법(bf16 매핑 → int4 매핑 순서로 불러옴)으로, 0.49GB였다.
- 0078은 이 1GB가 압박 때 재정착 비용도 키운다고 보고 조사 우선순위를 올렸다.

## 방법 (`experiments/e019_footprint/`)

- 압박 프로세스는 쓰지 않았다(스왑·SSD 쓰기 없음). 캐시는 E017의 int4 F 캐시다. 실행마다 새 프로세스로 돌렸다.
- **1. `stages.py`**: 불러오기 순서(`int4` / `bf16,int4`)와 프롬프트(짧은 문장 / E017 채팅 템플릿, `--chat`)를 바꿔 가며 단계별 footprint를 쟀다.
  - 잰 값: footprint, 5ms 간격 최대값, MPS 드라이버 할당량.
  - 명령: `.venv/bin/python -m experiments.e019_footprint.stages --model Qwen/Qwen2.5-3B-Instruct --order int4 --cache-dir <E017 캐시> [--chat] [--no-mps-stats]`
- **2. `prompt_len.py`**: 한 번의 순전파 뒤 늘어난 메모리를 쟀다.
  - 바꾼 조건: 길이, KV 캐시 사용, `logits_to_keep`, attention 구현(`--attn eager`), `lm_head` 가중치를 일반 텐서로 복제(`--clone-head`).
  - `--hooks`로 드라이버 할당을 50MiB 넘게 늘린 층을 찾았다.
- **3. `speed.py`**: E017 작업 프로세스의 A 단계(평온, 64토큰)를 `PYTORCH_MPS_LOW_WATERMARK_RATIO` 유무로 번갈아 돌렸다.
  - 바깥에서 20ms 간격으로 footprint를 쟀다. 3회 반복했다.
  - 이어서 비율 0.1·0.01을 2회씩 돌렸다.
  - 결과: `docs/research/data/e019/speed.json`, `speed_low_ratio.json`, `env_speed.json`.
- 1·2의 결과는 콘솔 출력이고 파일로 저장하지 않았다. 아래 수치는 그 출력이다.

## 결과

### 1. 재현 조건 (3B int4, `stages.py`)

| 조건 | 불러온 직후 | 예열 4토큰 뒤 | `empty_cache` 뒤 |
|---|---|---|---|
| int4, 짧은 프롬프트(약 10토큰) | 471MiB | 499MiB | 460MiB |
| int4, 채팅 템플릿(약 40토큰) | 471MiB | **1,490MiB** (드라이버 +1,030) | 460MiB |
| bf16 → int4, 채팅 템플릿 | 472MiB | 496MiB (드라이버 +20) | 484MiB |

- E017 작업 프로세스를 바깥에서 재 봐도 같았다. int4는 불러온 뒤 약 7.4초부터 끝까지 1.5GB였고, 제어기 방법은 0.5GB였다.
- E016(0.53GB)과 E017(1.5GB)의 차이는 프롬프트 형식 차이일 가능성이 높다(E016 스크립트는 다시 확인하지 않았다).

### 2. 늘어나는 곳 (`prompt_len.py`, 3B int4)

- KV 캐시 prefill의 길이별 증가: 8토큰 +34MiB, **40토큰 +1,026MiB**.
- KV 캐시 없이 한 번 돌리면: 64토큰까지 +41MiB, 128토큰 +1,057MiB.
- 층별로 보면 40토큰에서 **`lm_head` 한 층이 +1,030MiB**를 만들었다.
  - `lm_head`의 출력(40 × 151,936 어휘)은 10MiB를 넘는다.
  - attention 구현을 eager로 바꿔도, `lm_head` 가중치를 파일 매핑이 아닌 일반 MPS 텐서로 복제해도 같았다. **즉 F 등급(무복사 매핑) 탓이 아니다.**
- `logits_to_keep=1`(마지막 위치만 로짓 계산, HF `generate()`의 기본 동작)이면 40토큰에서 +2MiB였다.
  - 그러나 512토큰에서는 첫 `down_proj`에서 정확히 +1,024MiB가 생겼다. 긴 프롬프트면 결국 생긴다.

### 3. 원인: PyTorch MPS 할당기의 XLARGE 힙 (torch 2.14.0, `ATen/mps/MPSAllocator.h`)

- **힙 선택 규칙**
  - 할당 하나가 10MiB 이상 512MiB 미만이고 할당기가 "메모리 압박 없음"으로 판단하면, 버퍼를 **1GiB 힙(`kXLargeHeap`)**에 넣는다.
  - 힙 전체가 프로세스 footprint에 잡힌다. 힙이 완전히 비었을 때 `empty_cache()`를 불러야만 돌아간다. 디코딩 중에는 작은 할당이 남아 있어 계속 유지된다.
- **"압박"의 판단**
  - 기준은 저수위선(`PYTORCH_MPS_LOW_WATERMARK_RATIO` × `recommended_max_memory`)이다.
  - 이 기기의 `recommended_max_memory`는 5,461MiB이고, 기본 비율은 통합 메모리에서 약 1.4다.
  - 드라이버 할당량이 저수위선을 넘으면 압박으로 보고, 힙 대신 크기에 맞는 버퍼(2MiB 올림)를 쓴다.
- **bf16 → int4 순서에서 1GB가 생기지 않은 이유**
  - 3B bf16 무복사 매핑(5.9GB)이 드라이버 할당량에 들어가 합계가 8GB가 된다. 이것이 저수위선을 넘어 할당기가 압박 상태가 됐기 때문이다.
  - 0078의 "3B 제어기 방법의 작은 재정착 비용"도 제어기가 아니라 이 할당기 상태 때문일 가능성이 높다.
- **비율별 확인 (3B int4, 40토큰)**
  - 비율 1.0·0.5·0(0은 제한 없음으로 보임): 그대로 +1,038MiB.
  - 비율 0.3·0.1: **+26MiB.**

### 4. 속도·출력 비용 (`speed.py`, 평온, 64토큰, 중앙값)

| 모델·방법 | 기본 | 비율 0.3 | 비율 0.1 (2회) | 비율 0.01 (2회) |
|---|---|---|---|---|
| 3B int4 tok/s / 최대 footprint | 7.39 / 1,507MiB | 7.43 / **497MiB** | 6.34 / **497MiB** | 6.43 / 497MiB |
| 1.5B int4 | 14.08 / 1,502MiB | 13.76 / 1,503MiB (효과 없음) | 13.39 / **492MiB** | 11.35 / 493MiB |
| 1.5B bf16 | 10.99 / 1,516MiB | 10.92 / **507MiB** | — | — |

- 비율 0.1·0.01은 별도 실행이다. 그 실행의 기본 설정 값은 3B 5.42, 1.5B 12.95 tok/s였다.
- 같은 실행 안에서 비교하면 0.1은 속도가 같거나 더 빨랐다(3B 6.15·6.53 대 기본 4.52·6.32, 1.5B 13.9·12.9 대 13.85·12.04).
- **0.3은 1.5B int4에서 효과가 없었다.** 매핑 1.2GB가 저수위선 1.6GB(0.3 × 5,461MiB)보다 작아 압박 상태가 되지 않았기 때문이다.
  - 비율은 매핑된 가중치보다 낮은 값을 가리켜야 한다. 0.1(546MiB)은 두 모델 모두에서 작동했다.
- **0.01은 1.5B에서 느려지는 경향이 있었다**(11.0·11.7 대 기본 13.85·12.04).
- **출력 토큰은 모든 비율에서 같았다**(모델마다 한 가지 수열).

## 해석

1. 0074·0078의 footprint 1GB 차이는 **memopro 결함이 아니라 PyTorch MPS 할당기의 정상 동작(1GiB 힙 예약)**이다.
   - MPS를 쓰는 모든 PyTorch 코드에 해당한다. 긴 프롬프트나 전체 로짓 계산처럼 10MiB 넘는 임시 버퍼가 한 번이라도 생기면 1GiB가 잡힌다.
2. 8GB 기기에서 1GiB는 크다. 쾌적 우선 모드의 1.5B int4 footprint를 1.5GB에서 0.49GB로(약 3분의 1로) 줄일 수 있다.
3. 비율을 낮추면 할당기가 큰 버퍼를 딱 맞는 크기로 잡는다. 이번 추론 시험에서는 속도·출력 비용이 없었다(0.1). 학습처럼 큰 임시 버퍼가 매 단계 반복되는 경우의 비용은 재지 않았다.
4. 이 환경변수는 **MPS 할당기가 처음 만들어지기 전에** 설정돼야 한다(첫 MPS 사용 전).
   - `import memopro`는 부작용이 없어야 하고, `load` 시점에는 이미 MPS가 쓰였을 수 있다. 그래서 memopro가 실행 중에 바꿀 수는 없다.
   - `torch.mps`에는 저수위를 바꾸는 공개 API가 없다(`set_per_process_memory_fraction`은 고수위).

## 라이브러리 반영 선택지 (사용자 결정 대기, 적용하지 않음)

| # | 방법 | 비고 |
|---|---|---|
| W1 | `memopro run`이 macOS MPS에서 `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.1`로 자신을 다시 실행한다(사용자가 이미 정했으면 두고, `--keep-mps-heap`으로 끔) | F4(`MallocLargeCache=0`)와 같은 방식 |
| W2 | doctor와 `load(residency="file")` 보고에 안내를 넣는다: "MPS 할당기가 1GiB 힙을 잡는다. torch를 import하기 전에 `PYTORCH_MPS_LOW_WATERMARK_RATIO=0.1`을 설정하면 약 1GiB 줄어든다"(한 번만) | 노트북 사용자에게 필요 |
| W3 | 쾌적 제어기 재측정(0079의 짧은 재측정)에서 이 설정을 기본 조건으로 쓴다 | 압박 때 재정착 비용이 줄었는지 확인. SSD 쓰기가 있으므로 시행 수를 줄인다 |
| W4 | 학습 경로(`train_session`)에서 이 설정의 비용을 따로 잰다 | W1을 학습에도 적용할지 판단 근거 |

- **추천**: W1 + W2를 적용하고, W3에서 효과를 확인한다. 학습은 W4 전까지 안내만 한다.

## 한계

- 사전 등록 없는 원인 조사다. 1·2의 콘솔 결과는 파일로 남기지 않았다(스크립트와 명령으로 재현 가능).
- 비율 0.1·0.01은 2회씩이다. 속도는 시기에 따른 변동이 크다(기본 설정도 실행마다 1.5B 12.0~14.1 tok/s).
- 추론, 평온 조건만 쟀다. 압박 중 효과와 학습 비용은 재지 않았다.
- 기기 1대(M1 8GB), torch 2.14.0. 할당기 상수는 torch 버전에 따라 바뀔 수 있다.

## 논문 매핑

- **논문 C Evaluation / Threats to Validity**: 측정한 footprint에 프레임워크 할당기의 1GiB 힙이 섞인다. E017 계열의 방법 간 footprint·재정착 비교 해석을 이것으로 고친다.
- **논문 C System**: 저메모리 기기에서 할당기 설정(저수위 비율)이 모델 가중치 크기와 맞먹는 효과를 낸다. 8GB 기기에서 1.5B int4 footprint가 약 3분의 1이 된다.
- **논문 B**: `memopro run`의 환경 설정 기능(F4, W1)의 근거.
