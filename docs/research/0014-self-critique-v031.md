# 0014. 설계 v0.3.1 자기 비판: 남은 개선점

- **날짜**: 2026-09-25
- **유형**: survey + decision(제안)
- **상태**: 확정 (비판) / P1~P4 채택(→ 0015), P5~P10 보류 / P5·P6·P8 채택, P7 census 부분 채택(→ 0032), P9·P10 대기 / P9 채택(→ 0033: 논문 A 주력)
- **관련 기록**: 0012, 0013 (검증 대상 v0.3.1)

## 배경 / 동기

사용자 질문: "분석할 때 개선점이 없어 보이는가?"
0011·0013은 **수정안 내부의 모순**을 찾는 검증이었다. 이번에는 범위를 넓혀 ① 진행 방식 ② 기능의 가치 논리 ③ 연구 체계 ④ 기술 세부를 비판적으로 점검한다.

## 가장 큰 문제: 경험적 근거 없이 문서만 반복하고 있다

- 0001~0013까지 **설계를 네 번 바꿨지만, 코드 한 줄도 실행하지 않았고 실험도 하나도 하지 않았다.**
- 남은 핵심 불확실성은 모두 **경험적**이어서, 문서를 더 다듬어도 풀리지 않는다.
  - α가 수렴하는가? (H1~H3)
  - 실제 노트북에 유휴 메모리가 얼마나 있는가? (β의 수요, RQ4)
  - 실제 텐서의 중복도는 얼마나 되는가? (census의 가치)
  - OS 기본 기능 대비 β의 이득은 얼마인가? (아래 P3)
- 설계 반복의 한계 효용이 떨어졌다. 다음 정보는 **측정**에서 나온다.

## 개선 제안

### A. 진행 순서

**P1. 정보 가치가 가장 큰 실험을 먼저 한다**
- S1 직후, v0.1 기능 구현 **전에** 저비용 결정적 실험 두 가지를 먼저 한다.
  1. **α E001~E003** (Python 프로토타입, 며칠 규모): 논문의 핵심 기여가 성립하는지 조기에 판정한다. 결과에 따라 연구 서사가 달라진다.
  2. **β·census 수요 측정**: 실제 노트북 표본(본인·동료)에서 유휴 텐서의 양과 유휴 시간, 텐서 중복도를 계측한다.
- 현재 계획은 R1을 "병렬"로 두었지만, 1인 개발에서 병렬은 사실상 후순위를 뜻한다.

**P2. v0.1 범위를 더 줄이고 "걷는 뼈대"부터**
- 0.0.x에서 **빌드 → wheel → 배포 파이프라인**을 먼저 끝까지 관통시킨다. 배포 문제는 늦게 발견할수록 비싸다.
- v0.1에서 미룰 것: census 정밀 모드(비용 큼), 한국어 문서(영어 우선, 한국어는 v0.1.x), 모든 플랫폼 wheel(macOS arm64·Linux x86_64 우선).

### B. β의 가치 논리 빈틈

**P3. OS 기본 기능과의 관계를 검토하지 않았다** (가장 중요한 논리 빈틈)
- **macOS**는 유휴 메모리를 자동으로 압축하고(메모리 압축기) 스왑한다. **Linux**도 스왑(배포판에 따라 zram·zswap)이 있다.
- 따라서 **CPU에 있는 유휴 텐서**는 OS가 이미 어느 정도 처리한다. β의 이득은 다음 경우에만 분명하다.

| 환경 | OS가 처리하는가 | β의 이득 |
|---|---|---|
| **CUDA GPU 메모리(VRAM)** | ❌ OS가 스왑하지 않음 | **큼**: 유휴 VRAM 회수가 유일한 방법 |
| **스왑이 없는 환경** (많은 컨테이너 환경, 클라우드 노트북 일부 — 환경별 확인 필요) | ❌ | **큼**: 없으면 OOM 강제 종료 |
| Apple Silicon MPS 텐서 | 불확실 (GPU가 사용 중인 메모리의 압축·스왑 여부 확인 필요) | 측정 필요 |
| macOS·Linux CPU 텐서 (스왑 있음) | ✅ 페이지 단위 압축·스왑 | **측정 필요**: 부동소수 인식 압축률, 스왑 폭주 방지 효과가 OS보다 나은지 |

- 조치: β의 우선 환경을 **CUDA VRAM과 스왑 없는 환경**으로 명시한다. **OS 스왑·압축을 기준선**에 포함한다. Mac CPU 텐서의 이득은 측정 후 주장한다.

**P4. 기본 동작을 "자동·투명"에서 "제안 + 명시 실행"으로 바꾼다**
- 자동 프록시 방식은 투명성 한계(0013 V8)와 오동작 위험이 남아 있다.
- 기본값: census가 "유휴 객체와 회수 가능량"을 보여주고, 사용자가 한 줄로 실행한다(예: `%hibernate model_a`). **자동 모드는 선택 사항**으로 둔다.
- 신뢰성(U3)이 올라가고, 가장 위험한 경로(자동 프록시 재바인딩)를 선택 사항으로 격리할 수 있다. 명시 실행도 기존 도구에는 없는 기능이므로 고유성은 유지된다.

**P5. 방출 파일의 안전성이 설계에 없다**
- 방출 파일에는 모델 가중치나 사용자 데이터가 들어갈 수 있다. 다음을 요구 사항으로 둔다.
  - 파일 권한 0600, 정상·비정상 종료 시 정리, 다음 실행 시 남은 파일 청소
  - 디스크 예산(예산 벡터의 disk 풀) 준수
  - pickle을 쓰지 않고 원시 버퍼 + 메타데이터로 저장 (역직렬화 코드 실행 위험 방지)

### C. census의 가치 논리

**P6. 중복도를 측정해도 사용자가 할 수 있는 행동이 없다**
- "활성값이 40% 중복"이라는 결과만으로는 사용자가 무엇을 해야 할지 모른다. v0.1에는 중복을 줄이는 수단이 없다.
- 조치: 중복도 결과를 **행동 가능한 권고**로 연결한다. 예: "옵티마이저 상태의 실제 정보량은 원소당 약 k비트 → 8비트 옵티마이저 적용 시 약 X GB 절감 예상(수치 변경 등급)".
- 권고는 memopro 기능(v0.2 예고 포함)이나 일반 기법명으로만 표현한다. 외부 도구로 안내하지 않는다(S2 기각 준수).

### D. 연구·검증 체계

**P7. v0.1의 평가 설계(기준선)가 없다**
- β 기준선: 아무것도 안 함 / 수동 `del` + `gc.collect()` + `empty_cache()` / OS 스왑·압축 / pytorch_memlab의 CPU 이동 기능
- census 정확성: 알려진 합성 텐서(엔트로피를 아는 분포)로 측정값 검증, 할당자 통계와의 대조

**P8. 사용자 검증 계획이 없다**
- "누구나 쉽게"를 주장하려면 실제 사용자 근거가 필요하다.
- 노트북 표본 수집(P1-2와 같은 데이터)과 동료 3~5명의 사용 기록을 활용한다. RQ4 데이터이자 사용성 근거가 된다.

**P9. 논문 계획이 명시되어 있지 않다**
- 현재 기록은 "논문 매핑"만 있고 **어떤 논문을 몇 편, 어디에** 낼지가 없다. 후보:

| 논문 | 핵심 | 데이터 출처 | 게재처 유형 |
|---|---|---|---|
| ① α 방법 논문 | 잔차 고정점 체크포인팅 | R1, N2 | ML 시스템 학회·워크숍 |
| ② 메모리 센서스 측정 연구 | 학습·추론 텐서의 실제 정보량과 중복 | R2, census | 측정 연구 트랙, 국내 학술대회 |
| ③ memopro 도구 논문 | 2계층 구조, β, 사용자 검증 | v0.1~v0.2, P8 | 오픈소스 소프트웨어 저널 |

- 조치: 실험마다 어느 논문에 쓰이는지 표시하고, 사용자와 게재처를 협의한다.

### E. 기술 세부

**P10. 호환성 정책이 비어 있다**
- 지원 torch 범위: β 프록시(`__torch_function__`), bitsandbytes MPS(torch ≥ 2.9) 등에 따라 최소 버전이 달라진다.
- Python: 개발 환경은 3.14이다. **free-threaded 빌드(3.13t·3.14t)는 abi3 wheel을 쓸 수 없다**(확인 필요) → 별도 빌드 또는 미지원 명시.
- 멀티프로세스: DataLoader 워커(fork)에서 동면 프록시가 어떻게 동작하는지 정의해야 한다.

## 여전히 풀리지 않은 것

- **G3(하드웨어 병목 극복)**는 α(메모리 → 연산 치환)와 γ 외에 뚜렷한 대응이 없다. 센서스(R2)에서 대역폭 관련 중복이 발견되는지가 유일한 단서이다.
