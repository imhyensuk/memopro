## 사전 조사 요약 (실행 전)

- **`torch.optim.Muon`이 PyTorch 2.9부터 내장**되어 있다(현재 2.14). 2D 파라미터 전용이며 상태는 `momentum_buffer` 하나이다. MPS에서 API 동작을 확인했다(결과 측정 아님).
  → memopro에서 Muon은 **재구현 대상이 아니라 연동 대상**이다(0010 재구현 금지).
- 8비트 Muon: AdamW-32 대비 옵티마이저 상태 최대 86% 절감(arXiv 2509.23106). MuonQ(2605.11396).
- **ICML 2026 "Can Muon Fine-tune Adam-Pretrained Models?"(2605.10468)**: Adam으로 사전학습된 모델을 Muon으로 **전체 파인튜닝하면 성능이 떨어진다**(최적화기 불일치). LoRA에서는 손실 없이 옵티마이저 메모리 50% 절감. 학습률은 따로 조정해야 한다.
- bitsandbytes MPS 백엔드는 8비트 옵티마이저를 아직 지원하지 않는다(릴리스 노트).
  → Apple Silicon에서 옵티마이저 메모리를 줄이는 기존 수단이 제한적이다.
- **이론적 절감률**(Muon은 블록 2D 가중치, 나머지는 AdamW인 혼합 구성):

  | 모델 | Muon 적용 비율 | 옵티마이저 상태 절감 |
  |---|---|---|
  | GPT-2 small | 68.3% | **34.1%** (949 → 625 MiB) |
  | Llama-3.2-1B 근사 | 약 65% | 약 32% |
  | Llama-3.1-8B 근사 | 약 87% | 약 43% |

## E007 — Muon 타당성 (MPS, fp32)

| 부분 | 설정 |
|---|---|
| A. 메모리 | GPT-2 small, 1스텝 후 옵티마이저 상태 바이트 실측: AdamW 단독 대 혼합(Muon: `transformer.h.*`의 2D 가중치, AdamW: 나머지) |
| B. 사전학습 모델 전체 파인튜닝 | GPT-2 small(Adam으로 사전학습됨), WikiText-2 train, 배치 2×256, 60스텝. 학습률 {3e−5, 1e−4, 3e−4} × {AdamW, 혼합}. wd 0.01(양쪽 동일). Muon은 `adjust_lr_fn="match_rms_adamw"`, momentum 0.95, nesterov |
| C. 처음부터 학습 | 작은 GPT-2(4층, d=256, 헤드 4), 무작위 초기화, 배치 8×128, 300스텝. 학습률 {3e−4, 1e−3, 3e−3} × {AdamW, 혼합} |
| 평가 | 검증 손실: WikiText-2 validation의 고정 시퀀스 16개(B는 256, C는 128 토큰). 학습률별 최종값 중 최적값으로 비교. 스텝 시간: 처음 5스텝 제외 평균 |

**판정 기준**
- M1 메모리: 실측 절감률이 이론값 34.1% ± 2%p 이내 (회계 검증)
- M2 호환성: 모든 실행이 MPS에서 오류 없이 유한한 손실로 종료
- M3a 처음부터 학습: 혼합 최적 검증 손실 ≤ AdamW 최적 × 1.02
- M3b 사전학습 모델 전체 파인튜닝: 기술 통계만 보고 (문헌은 불일치로 인한 열세를 예측)
- M4 속도: 혼합의 스텝 시간 ≤ AdamW × 1.25

**판정 규칙**
- M2·M3a·M4 통과 → `train_session` 후보 기법에 **"의미 변경(SEMANTICS) 등급 제안"**으로 추가한다(자동 적용 금지).
  적용 맥락: 처음부터 학습 또는 LoRA. Adam으로 사전학습된 모델의 전체 파인튜닝에는 경고한다. Apple Silicon 메모가 추가된다.
- M3a 또는 M4 실패 → 기록만 하고 후보에서 제외한다.

## E008 — Rust 병렬 방출 코덱 벤치마크

**질문**: β 방출 경로(바이트 셔플 + zstd)에서 Rust 병렬 구현이 "Python + C 라이브러리"보다 의미 있게 빠른가? 압축이 방출 시간을 줄이는가, 늘리는가?

| 항목 | 설정 |
|---|---|
| 데이터 | GPT-2 small fp32 파라미터를 이어 붙인 버퍼(약 475MiB), bf16 변환본(약 237MiB) |
| 코덱 | 바이트 셔플 + zstd, 레벨 {1, 3}, 청크 4MiB (독립 청크) |
| B0 | 단순 메모리 복사 (대역폭 기준선) |
| B1 | Python 단일 스레드: numpy 셔플 + python-zstandard |
| B2 | Python 스레드 풀(8): B1을 청크별 병렬 실행 (GIL 해제 여부 확인) |
| B3 | 셔플(numpy 단일 스레드) + python-zstandard 내장 멀티스레드(threads=8) |
| R1 | **Rust**: rayon으로 청크별 셔플 + zstd 병렬 실행, GIL 해제 |
| 복원 | 해제(decompress) + 역셔플 처리량: B1 방식 대 R1 방식 |
| 방출 전체 | ① 무압축 쓰기 + fsync ② R1 압축 + 쓰기 + fsync (임시 디렉터리, 측정 후 삭제) |
| 반복 | 워밍업 1회 후 5회 측정, 중앙값 |

**판정 기준**
- C1 정확성: Rust 왕복이 비트 단위로 동일. 압축률이 같은 알고리즘의 Python 결과와 1% 이내
- C2: R1 처리량 ≥ 3 × B1
- C3: R1 처리량 ≥ 1.3 × max(B2, B3). **미달이면** "코덱 속도"를 Rust 채택 근거로 쓰지 않는다(근거를 파이프라인·메모리 상한·안전성으로 한정)
- C4 메모리 상한: R1 실행 중 RSS 증가 ≤ 출력 크기 + 스레드 수 × 2 × 청크 + 64MiB
- C5 방출 기본값: ② 시간 < ① 시간이면 "압축 방출" 기본 유지(0021 D2). 아니면 무압축 방출 또는 백그라운드 압축으로 변경
