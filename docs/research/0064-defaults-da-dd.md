# 0064. 기본값 문제 대응: D-a(될 설정 안내, 항상)와 D-d(`fallback="stored"`, 선택)

- **날짜**: 2026-09-28
- **유형**: decision + milestone (구현)
- **상태**: 확정
- **관련 기록**: 0063 (E014: 기본 설정이 1.5B·3B를 모두 `BudgetExceeded`로 거부, 선택지 D-a~D-d), 0059 (예산 형식), 0052 E3 (접근 계층)

## 배경

> "D-a는 필수 옵션, D-d는 선택 옵션으로 추가해."

E014에서 확인한 사실은 이렇다. 이 Mac(M1 8GB, 스왑 사용 중)에서 memopro 기본 설정은 `from_pretrained`로는 돌아가는 1.5B 모델을 거부했다. 거부 메시지는 "품질을 낮추거나, 디스크 오프로드를 허락하거나, 예산을 늘려라"라는 일반적인 안내뿐이었다. 사용자는 무엇을 얼마나 바꿔야 하는지 알 수 없었다. 예를 들어 `budget="4GB!"`면 bf16 그대로 들어가고, 그냥 불러오기보다 부담이 3분의 1이라는 것은 E014에서만 드러났다. 사용자는 두 가지를 골랐다.

- **D-a (필수)**: 들어갈 구성이 없을 때 **실제로 불러와지는 설정을 계산해** 보여 준다.
- **D-d (선택)**: 들어갈 구성이 없어도, 사용자가 원하면 경고하고 원래 형식으로 불러온다.

기본값(보수적 가용량, 품질 `balanced`)은 바꾸지 않는다(D-b·D-c는 E010 사용자 데이터 없이 하지 않음).

## 결정

### D-a: 검증된 설정 제안 (`access/_suggest.py`)

- 제안은 추측이 아니다. 후보 설정마다 **같은 메타데이터로 계획을 다시 세워**(가중치를 읽지 않음) 실제로 어떤 구성이 선택되는지 확인한 것만 낸다. 시도하는 설정 변경은 다음과 같다.
  1. `budget_basis="os"`
  2. 지금보다 낮은 품질 각각(`quality="low"` 등), 그리고 그것과 `budget_basis="os"`의 조합
  3. `disk_writes="allow"` (디스크 오프로드)
  4. 거부된 구성마다, 그 구성이 들어갈 **정확한 강제 예산**(`budget="3.5GB!"`, 0.1GB 단위로 올림). 필요하면 그 구성을 허용하는 최소 품질을 함께 준다.
- 제안마다 두 가지를 적는다.
  - 선택될 구성과 필요량
  - **압축·스왑 없이 쓸 수 있는 양을 넘는 정도**(보수적 가용량 기준). 넘으면 "약 X GB가 압축되거나 스왑될 수 있다"
- CUDA에서 드라이버 여유량을 넘는 강제 예산은 OOM이 나므로 제안하지 않는다.
- **순서**: 빈 메모리 안에 들어가는 것 먼저(손실이 적은 것 → 빠른 것 → 바꿀 설정이 적은 것). 그다음은 **스왑이 적은 것부터** 낸다. 처음에는 손실 순으로 정렬했는데, 3B에서 스왑 4.7GB짜리 원래 형식을 맨 위에 올렸다. E014에서 같은 구성은 10분 넘게 멈췄으므로 순서를 바꿨다. 구성마다 가장 단순한 설정 하나만 남기고, 최대 4개를 낸다.
- `fallback`이 꺼져 있고 원래 형식 구성이 허용되면 마지막 줄에 `fallback="stored"`를 덧붙인다.
- **적용 대상**
  - `load`: `BudgetExceeded`의 메시지와 `.suggestions`(구조화된 목록).
  - `check`: 들어갈 구성이 없으면 요약과 JSON에 같은 제안을 담는다.
  - `optimize`: 단계가 단순하므로 같은 원칙(허용 품질, 정확한 강제 예산)으로 직접 계산한다.

### D-d: `fallback` 설정 (기본 `"none"`)

- 값은 `"none"`(기본: 지금처럼 `BudgetExceeded`)과 `"stored"`다.
- **`load`**: 들어갈 구성이 없고 `fallback="stored"`이면 원래 형식 구성을 **예산을 넘어도** 불러온다. 원래 형식 구성은 transformers `device_map`으로 장치에 바로 올린다. E014에서 같은 구성의 `from_pretrained().to()`보다 스왑과 반응 지연이 약 3분의 1이었다.
  - `report()`에 "fallback" 사유, 필요량, 예산, 스왑 예상량을 남기고 `UserWarning`을 낸다.
  - 원래 형식 구성이 허용되지 않거나(`deny`) 불러오기에 실패하면 D-a 제안과 함께 `BudgetExceeded`를 낸다.
- **`optimize`**: 들어갈 단계가 없고 `fallback="stored"`이면 모델을 **바꾸지 않고** 돌려준다. 이때도 경고와 보고를 남긴다.
- **`memopro run`**: 로딩 정책이 `load`를 쓰므로 설정을 그대로 따른다. CLI `--fallback`을 `run`과 `check`에 추가한다.
- **원칙과의 관계**: U3(fail-open)와 "조용한 대체 금지"를 모두 지킨다. 대체는 사용자가 **명시적으로** 켰을 때만 하고, 할 때는 경고와 보고를 남긴다.

## 구현과 검증

| 파일 | 내용 |
|---|---|
| `access/_suggest.py` | 시도할 설정 변경 생성, 계획 재실행, 스왑 예상량(`over_free`), 순위, 메시지 |
| `access/_load.py` | `plan_from_info`(메타데이터 재사용), `_nothing_fits`(표 + 제안 + `.suggestions`), `_fallback`, 경고와 보고 |
| `access/_check.py` | 제안·fallback을 JSON과 요약에 표시 |
| `access/_optimize.py` | 단계별 제안, `fallback="stored"`면 그대로 둠 |
| `_run.py` | 들어갈 구성이 없으면 보고서에 제안(스크립트 호출은 그대로) |
| `config.py`, `cli.py` | `fallback` 설정(`none`/`stored`), `--fallback`(`run`, `check`) |

- **구현 중 찾은 결함**
  - 제안에 나오는 `budget_basis`, `disk_writes`, `fallback`을 `memopro.load(...)`에 넘기면 memopro 설정이 아니라 `from_pretrained` 인자로 흘러갔다. 실제 Qwen 1.5B에서 `fallback="stored"`가 동작하지 않아 드러났다.
  - `load`와 `check`에 세 인자를, `optimize`에 `budget_basis`·`fallback`을 추가했다.
  - 제안을 실제 `load` 호출로 끝까지 확인하는 테스트를 넣었다.
- **실제 모델 (M1 8GB, 장치 예산 약 1.5GiB)**
  - Qwen2.5-1.5B 제안은 이렇다(메타데이터만 사용).

    | 설정 | 선택되는 구성 | 스왑 |
    |---|---|---|
    | `quality='low'` | int4 | 없음(빈 메모리 안) |
    | `budget_basis='os'` | int8 | 약 0.36GiB |
    | `budget='3.5GB!'` | 원래 형식 | 약 1.65GiB |

  - 마지막 줄에 `fallback='stored'`가 붙는다.
  - 3B는 모든 제안이 스왑을 동반한다. 새 순서에서는 int4(약 1GiB)가 먼저 나온다.
  - `fallback="stored"`로 1.5B를 6.6초에 MPS bf16으로 불러왔고 생성도 정상이었다. 경고에는 예산 1.41GiB와 스왑 예상 1.65GiB가 적혔다.
- **테스트** (`tests/test_defaults_da_dd.py` 12개)
  - 제안을 계획으로 다시 세운 결과와 실제 `load` 결과가 모두 제안과 같다.
  - 순위(빈 메모리 우선, 그다음 스왑이 적은 순), 제안이 없을 때의 문구.
  - `check`의 제안·fallback 표시, `run` 보고서의 제안.
  - fallback 기본값·검증·경고·실패 시 안내, `optimize`의 제안과 fallback, CLI `--fallback`.
- **전체**: Python 220개 통과.
