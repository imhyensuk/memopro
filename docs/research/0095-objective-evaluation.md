# 0095. 객관 평가: 모든 실험(E001~E021)을 근거로 한 memopro의 성능과 목적 달성률

- **날짜**: 2026-09-29
- **유형**: assessment (사용자 요청)
- **상태**: 확정. 수치는 각 기록의 측정값이다. 달성률(%)은 연구자가 아래 근거에 따라 매긴 판단이다
- **관련 기록**: 0090 (직전 평가), 0093 (Colab 7차), 0094 (D1~D4 수정), 0063·0068·0071·0078·0080·0084·0085·0088

## 요청

> "그럼 지금까지의 모든 실험 결과들을 기반으로 할때, memopro의 성능과 목적 달성률을 객관적으로 평가해."

## 정정 (과거 기록을 고치지 않고 여기서 바로잡음)

- 0090과 그 뒤 답변에서 "β는 del 후 다시 불러오기보다 느렸다(0.90배)"라고 적었다. 이는 방향이 틀렸다.
- **0063(E014, Mac)에서 β는 다시 불러오기 시간의 0.90배로, 10% 빨랐다.** 사전 등록 기준 0.8배에는 못 미쳤다.
- T4(0093)에서는 β가 다시 불러오기 시간의 2.1배로 느렸다. 이 값은 맞다.

## 평가 기준

- **목표** (CLAUDE.md): 메모리가 적은 **PyTorch 개발자가 훨씬 많은 메모리가 필요한 모델을** 자기 프로젝트·서비스·개발·학습에서 쓰게 한다.
- 영역을 다섯으로 나눈다. 각 영역을 **입증됨 / 부분 입증 / 미입증 / 반증**으로 판정한다.
- 비교 대상은 같은 기법을 사용자가 직접 쓰는 경우다(HF `device_map`, bitsandbytes, accelerate, gradient checkpointing). memopro는 기존 기법을 감싸는 층이므로, **"기존 도구로도 할 수 있는가"**를 함께 적는다.

## 1. 추론: 메모리보다 큰 모델 구동

| 근거 | 결과 |
|---|---|
| T4(15GB), E021 | 14B(fp16 28GB, 장치의 약 1.9배): memopro int4로 **9.0 tok/s**(HF bnb4 7.6). 7B: int8, PPL +0.8%, 5.6 tok/s(HF bnb8 4.0). **OOM 0회**, 들어가지 않으면 제안과 함께 거절 |
| T4, E021 | 같은 정밀도에서 디코딩이 HF `device_map="auto"`보다 18~40% 빠름(직접 배치) |
| T4, E021 | **결함**: bf16을 고르면 긴 프롬프트가 3.7~5.4배 느림(D2). bnb int8을 빠르다고 오판(D3). 0094에서 고쳤으나 재측정 전 |
| M1 8GB, E016~E020 | 3B: bf16은 0.24 tok/s로 붕괴 → int4 파일 기반 약 10 tok/s, footprint 0.5GB(할당기 설정 0081). 품질 비용: int4 g32 PPL +7.6%(3B), g64였던 이전 실험은 +21% |
| M1, E020·0085 | 1024토큰 프롬프트 29.2 → 8.7초(긴 입력 경로) |
| 미시험 | M1 8GB에서 7B 이상, T4에서 장치의 2배를 넘는 모델(32B 등, 오프로드 필요) |

- **판정: 부분 입증.**
  - 장치 메모리의 약 2배(fp16 기준)까지는 **자동으로, OOM 없이, 품질 비용을 알리며** 돌린다.
  - 이는 사용자가 bitsandbytes 4비트를 직접 써도 할 수 있는 일이다. memopro의 기여는 **자동 선택·안전·보고**와 약간의 속도(직접 배치)이지, 새로운 능력이 아니다.
  - 2배를 넘는 모델은 입증하지 못했다.
- **달성률: 약 60%.**

## 2. 학습: 메모리보다 큰 학습

| 근거 | 결과 |
|---|---|
| T4, E021 | 0.5B 배치 8: plain·AMP·ckpt 모두 OOM → memopro만 **배치 그대로** 완주(889 tok/s). GPT-2, 30% 상한(4.4GB): plain·ckpt OOM → memopro 완주, 속도 −2% |
| T4, E021 | 정확성: 정확한 전체 배치 방법과 손실 차이 ≤ 5.2e-6, 파라미터 차이 ≤ 3.3e-8. accelerate는 배치를 줄여 결과가 2.1% 달라짐 |
| M1, E014 | MPS OOM이 나던 GPT-2 학습을 완주 |
| Colab 4~6차 | `check` 학습 예측 −0.2~−1.2%(0056) |
| T4, E021 | **한계**: 가중치+기울기+옵티마이저가 메모리를 넘는 학습(1.5B 전체 미세조정)은 못 한다. 8비트 옵티마이저·LoRA를 **제안만** 한다(설계). QLoRA는 되지만 계획 결함(D1)이 있었다(0094 수정) |

- **판정: 부분 입증.**
  - **활성값이 메모리를 넘는 경우**(큰 배치·긴 시퀀스)는 정확하게, 거의 비용 없이 해결함이 입증됐다.
  - **파라미터가 메모리를 넘는 경우**(더 큰 모델 전체 학습)는 해결하지 않는다. 기존 도구(LoRA, 8비트 옵티마이저, DeepSpeed 오프로드)로 넘긴다.
  - gradient accumulation을 직접 쓰면 같은 일을 할 수 있다. memopro의 기여는 **크기를 자동으로 정하고 OOM 뒤 재시도하는 것**이다.
- **달성률: 약 55%.**

| **가중 합** | | **약 53%** |

- **한 문장 평가**: memopro는 **"메모리보다 큰 모델을 OOM 없이, 자동으로, 품질 비용을 알리며"** 쓰게 하는 접근 계층으로는 절반 넘게 왔다.
  - 추론은 장치의 약 2배까지, 학습은 활성값이 넘치는 경우까지다.
  - 그러나 **"훨씬 큰"**(2배 초과, 파라미터 초과 학습)은 아직 입증하지 못했다.
  - 고유 연구 코어(β·γ)는 정확하지만 기존 방법보다 낫다는 증거가 없다.
- **기존 도구 대비 순수한 새 능력은 없다.** 가치는 선택의 자동화, OOM 방지, 정확성 보장(accelerate와 달리 배치를 바꾸지 않음), 보고, 몇 가지 속도 이득에 있다. 이는 설계 원칙(0010: 기존 기법을 다시 구현하지 않고 감쌈)과 일치하는 결과다.

## 달성률을 가장 많이 올릴 다음 단계 (제안)

1. **0094 수정의 CUDA 재측정**(Colab 셀 ② ③ 재실행): D2·D3로 추론 속도가 기대만큼 오르는지, D4로 `memopro run` 7B가 정책을 적용하는지.
2. **"2배 초과" 시험**: T4에서 32B int4(약 18GB > 15GB)처럼 오프로드가 필요한 모델, M1 8GB에서 7B int4(약 4.5GB). 목표 문장의 "훨씬 큰"에 직접 답한다.
3. **파라미터 초과 학습**: 제안만 하는 8비트 옵티마이저·LoRA를 사용자가 한 줄로 켜는 경로를 만들지 결정(현재 설계는 제안만).
4. **E010 수집**: β의 가치를 판단할 유일한 근거.
