# 0066. 8GB에서 큰 모델을 쾌적하게: 방법론과 새 아키텍처 RCR(재구성 비용 기반 상주) 제안

- **날짜**: 2026-09-28
- **유형**: survey + design (제안, 사용자 결정 대기)
- **상태**: 초안 (채택 여부와 우선순위는 사용자 결정)
- **관련 기록**: 0006 (신규 기법 탐색: 비트플레인 탄력 정밀도는 🔴 중복 높음), 0011·0022 (γ 중복 중간), 0060 (E011), 0062·0063 (E014), 0064, 0065

## 1. 배경

> "8GB에서 어떻게 해야 큰 모델의 추론, 학습 등의 과정을 더 쾌적하게 만들 수 있을지 방법론을 세워봐. 굳이 기존에 있는 방법론뿐만 아니라 완전히 새로운 아키텍처 설계를 통해서 타개할 수 있으면 좋을 것 같아."

E014(0063)의 결론은 두 가지였다.
- memopro는 불가능하던 학습을 가능하게 하고, 여러 모델을 쓸 때 멈춤을 막는다.
- 그러나 8GB에서 1.5B·3B 추론을 **쾌적하게** 만들지는 못했다.

이 기록은 두 가지를 한다.
- 왜 쾌적하지 않은지를 측정값으로 분해한다.
- 기존 기법의 연결(1층)과 memopro 고유의 새 아키텍처(2층)로 나눈 방법론을 세운다.

새로움은 CLAUDE.md의 규칙대로 선행 사례를 조사한 뒤 "우리 조사에서 찾지 못함"으로만 표현한다.

## 2. 문제 분석: 무엇이 쾌적함을 막는가

### 2.1 이 기기의 자원 (실측)

| 자원 | 값 | 출처 |
|---|---|---|
| 물리 메모리 | 8GB 통합 메모리 | 하드웨어 |
| 압축·스왑 없이 얻을 수 있는 양(보수적) | 1.3~1.9GiB | E014 기간의 doctor |
| OS 추정 가용량 | 2.4~4.9GB (시점에 따라 크게 변함) | E011·E014 |
| 이미 쓰는 스왑 | 5~10GB | E011·E014 |
| MPS 권장 한도 / 오류 한도 | 5.33GiB / 9.07GiB | torch, E014 OOM 메시지 |
| 메모리 읽기 대역폭(MPS) | **60.3GB/s** | 2026-09-28 측정: 512MiB 텐서 합계 20회 |
| SSD 순차 읽기 | **2.45GB/s** | 2026-09-28 측정: 3GiB, `F_NOCACHE`, 64MiB 단위 |
| 스왑에서 흩어진 페이지 되읽기 | 약 498MB에 3.9초(약 0.13GB/s) | E011 cpu/anon os 방법 |
| 유효 추론 대역폭 | 1.5B bf16 3.09GB × 11 tok/s ≈ **34GB/s**(피크의 57%) | E014 |

메모리와 SSD의 차이는 약 25배다. 스왑에서 흩어진 페이지를 읽으면 차이는 다시 약 19배 벌어진다.

### 2.2 디코딩 속도 모델

토큰을 하나 만들 때는 가중치를 한 번씩 읽는다(디코딩은 메모리 대역폭에 묶인다).

```
t_token ≈ W_상주 / B_eff  +  W_부족 / B_ssd
W_부족 = max(0, W − R)   (R: 스왑 없이 상주할 수 있는 양; 최악의 경우 매 토큰 다시 읽음)
B_eff ≈ 34GB/s (E014 실측), B_ssd ≈ 2.45GB/s (순차), 흩어진 page-in ≈ 0.13GB/s
```

| 모델 (가중치 W) | R = 2.5GB | R = 1.5GB | 비고 |
|---|---|---|---|
| 1.5B int4 (≈1.0GB) | ≈ 34 tok/s | ≈ 34 tok/s | 전부 상주. E014의 bitsandbytes int4는 **4.9 tok/s**라서 병목은 **커널**이다 |
| 1.5B bf16 (3.1GB) | 순차 스트리밍이면 ≈ 3.5 tok/s | ≈ 1.4 tok/s | 실제로는 스왑의 흩어진 읽기라 스왑 폭주(E014: +3.2GB, 탐침 17배) |
| 3B int4 (≈2.1GB) | ≈ 16 tok/s | ≈ 3.3 tok/s | 상주 여부가 결정적 |
| 7B int4 (≈4.5GB) | ≈ 1.1 tok/s | ≈ 0.7 tok/s | 8GB에서는 스트리밍만 가능 |

이 표는 상한에 가까운 추정이다(가설, 측정 전).

### 2.3 우리 실험이 준 진단

| # | 진단 | 근거 |
|---|---|---|
| D1 | 불쾌함의 직접 원인은 **여유를 넘는 익명(anonymous) 메모리**다. OS가 그것을 압축·스왑으로 쓰고, 흩어진 page-in으로 되읽는다 | E014: `naive` 스왑 +3.2GB, 탐침 p95 17배. E011: 스왑 복귀 3.9s |
| D2 | **깨끗한 파일 페이지는 싸다.** OS가 쓰기 없이 버리고 다시 읽는다 | E011 cpu/mmap: 가중치 페이지가 압박에 자유롭게 밀려나고, `source` 복귀는 0.9s |
| D3 | 불러오는 경로가 부담을 3배 바꾼다(CPU를 거친 복사 대 장치 직행) | E014: 같은 bf16에서 스왑 0.30배, 탐침 0.30배 |
| D4 | 해제해도 할당기가 붙잡는다(libmalloc 캐시, Metal 드라이버) | E011, F4, 0062 §1 |
| D5 | PyTorch MPS의 저비트 커널이 느리다 | E014: int4 4.9 tok/s 대 bf16 11 tok/s |
| D6 | 쾌적함은 프로세스가 아니라 **시스템**의 성질이다(함께 도는 앱의 반응성) | E014 탐침 |

**요약**: 문제는 "용량이 모자라다"가 아니라 두 가지다. 하나는 **재구성 비용이 가장 비싼 형태(익명 메모리)로 메모리를 쥐고 있다**는 것이다. 다른 하나는 **모자란 부분을 가장 비싼 방법(흩어진 스왑 읽기)으로 메운다**는 것이다.

| # | 원칙 | 근거 |

## 5. 2층: 새 아키텍처 — RCR (Reconstruction-Cost-aware Residency, 재구성 비용 기반 상주) 런타임

### 5.1 핵심 아이디어

지금까지의 memopro(β·γ)와 기존 도구는 대부분 **"무엇을 내보낼지 런타임이 정하고 직접 옮기는"** 방식이다. RCR은 발상을 뒤집는다. **프로세스가 가진 모든 텐서 바이트를 "다시 만드는 비용"으로 등급을 매기고, 그 등급에 맞는 OS 메모리 종류에 담는다.** 그러면 압박이 올 때 **OS가 스스로 가장 싼 것부터 회수**한다. OS는 깨끗한 파일 페이지와 폐기 가능(purgeable) 페이지를 먼저 쓰기 없이 버리고, 익명 메모리는 나중에 압축·스왑한다. 런타임은 회수된 것을 **가장 싼 방법으로 다시 만든다**.

```
            재구성 비용: 낮음 ───────────────────────────────▶ 높음
 등급  F (파일과 같음)       P (다시 계산 가능)         C (압축 가능)          A (반드시 유지)
 예    가중치, 사전 변환     KV 캐시 일부, 체크포인트   유휴 텐서(β compress)  학습 중 파라미터,
       캐시(저비트·비트플레인) 활성값, 역양자화 캐시                          옵티마이저 상태, 그래디언트
 OS    읽기 전용 mmap        purgeable(macOS VM_PURGABLE  익명(압축 후 보관)     익명 (최소화)
       (깨끗한 페이지)       _VOLATILE·Metal purgeable,
                             Linux MADV_FREE)
 압박  쓰기 없이 버림 →      쓰기 없이 버림 →           OS 압축·스왑           OS 압축·스왑
       SSD에서 순차 재읽기   런타임이 감지해 재계산
                     ▲                         ▲
        쾌적 제어기(γ 후속): 목표 = tok/s 하한 · 반응성 상한 · 스왑 쓰기≈0
        손잡이 = 정밀도 단계, 상주 창(미리 읽기/버리기), KV 정밀도, 추측 깊이
        조치 = 토큰·스텝 경계에서만 (0052 E6과 같은 안전 지점 원칙)
```

**가설 H-RCR**: 같은 모델을 RCR로 돌리면 모델이 여유 메모리보다 커도 **스왑 쓰기가 거의 0**이다. 압박이 오면 생성 속도는 SSD 재읽기만큼 **서서히** 느려질 뿐, 시스템이 멈추지 않는다(쾌적 기준 C2의 반응성 조건을 지킨다).

### 5.2 선행 사례와의 관계 (2026-09-28, 웹 수준 조사)

| 가까운 연구 | 하는 것 | RCR과의 차이 |
|---|---|---|
| llama.cpp (mmap 가중치) | 가중치를 mmap해 OS가 버리고 다시 읽게 함 | **F 등급만** 해당. PyTorch 밖이다. P·C 등급과 제어기가 없다 |
| mzCache (Yu 외, 2026, 안드로이드) | 멀티태스킹 압박에서 가중치·KV를 탄력적으로 내보내고 통합 메모리로 복원 | **자체** 퇴출 정책(하이브리드 스왑)이다. OS 폐기 가능 메모리를 쓰지 않는다. 함께 도는 앱의 반응성을 목표로 두지 않는다(초록 기준) |
| vToken (Gao 외, 2026) | 서빙 GPU의 KV 캐시를 토큰 단위로 가상화 | 단편화 해결이 목적이다. OS 회수 메모리가 아니다 |
| PagedWeight (Yang 외, 2026) | KV 압박에 따라 MoE 전문가의 비트플레인을 줄여 CPU로 옮김 | GPU 서빙, 런타임이 직접 옮긴다. 0006에서 이미 중복 높음으로 판정 |
| Linux volatile ranges RFC(2013), `MADV_FREE` | OS가 쓰기 없이 버리는 메모리라는 기제 자체 | 기제는 오래됐다. **딥러닝 텐서의 재구성 비용 등급과 연결한 사례는 찾지 못했다** |
| LLM in a flash, PowerInfer-2 | 플래시에서 희소하게 읽기 | F 등급 읽기의 최적화로 흡수할 수 있다(희소성 전제) |

**판정**: "딥러닝 런타임이 텐서를 재구성 비용 등급으로 나눠 OS 메모리 종류(깨끗한 파일 페이지, OS 폐기 가능 페이지)에 사상하고, 시스템 쾌적함을 목표로 조절하는 구조"는 **우리 조사에서 찾지 못했다**(조합). 구성 요소 하나하나는 기존 기제다. 신뢰도는 중간이다. 만들기 전에 체계적 문헌 조사(0006의 주의와 같음)가 필요하다.

### 5.3 구성 요소

1. **F 등급 파일 (장치용 사전 변환 캐시)**
   - 원본이 bf16이더라도, 선택된 구성(int4·비트플레인 등)으로 **한 번 변환해 파일로 쓰고**, 이후에는 읽기 전용으로 매핑한다.
   - 레이어 실행 순서로 배치하고 16KiB 페이지에 정렬한다.
   - 쓰기에는 `disk_writes` 동의가 필요하고, 디스크 풀 예산(0059)을 지킨다.
   - 파일이 원본과 같으면(원래 형식 선택) 원본 safetensors를 그대로 쓴다. 이미 β `source`의 기반이다.
2. **무복사 매핑 (관문 G-F)**
   - MPS에서 mmap 영역을 Metal 버퍼(`newBufferWithBytesNoCopy`)로 감싸 PyTorch 텐서로 노출해야 한다.
   - PyTorch에는 이 API가 없다. MLX에서도 mmap 오프셋과 Metal 버퍼 오프셋 제약이 보고됐다.
   - **안 되면 대안이 둘이다.**
     - memopro 전용 Metal 커널이 mmap 버퍼를 직접 읽는다. 이는 보류 중인 RS6(전용 커널) 해제가 필요하다.
     - CPU 경로를 쓴다(느림).
3. **P 등급 할당기**
   - 폐기 가능 영역에 세대 번호를 둔다.
   - 쓰기 전에 "비휘발로 고정"하고, 이미 폐기됐으면 재계산 경로를 탄다.
   - 대상: 체크포인트 활성값(폐기되면 앞 체크포인트에서 다시 계산, 체크포인팅과 자연스럽게 맞음), KV 캐시의 오래된 구간(다시 prefill), 역양자화 캐시.
4. **미리 읽기 창 (R3)**
   - 다음 k개 레이어의 F 페이지를 미리 올리고(`madvise WILLNEED`), 압박 중에는 지난 레이어를 먼저 내려놓는다.
   - 흩어진 page-in(0.13GB/s)을 순차 읽기(2.45GB/s)로 바꾼다.
5. **쾌적 제어기 (γ 후속)**
   - 입력: 압박 수준, 자기 page-in·스왑 증가, 생성 속도.
   - 조치 순서: R4에 따라 정밀도 단계 → 상주 창 → KV 정밀도 → 추측 깊이.
   - 목표와 조치는 E013(γ 평가)의 설계로 검증한다.
6. **할당기 협력 (R5)**
   - F·P 등급은 malloc을 거치지 않으므로 libmalloc 캐시 문제(D4)가 원천적으로 없다.
   - Metal 드라이버의 붙잡기(0062 §1)는 P 등급의 Metal purgeable 상태로 회피할 수 있는지 E015에서 확인한다.

### 5.4 추론 경로와 예상치 (가설)

**3B int4, 8GB, R ≈ 1.5~2.5GB**

| 방식 | 스왑 쓰기 | 생성 속도(2.2 모델) | 쾌적 기준 |
|---|---|---|---|
| 지금(`naive` bf16) | 매우 큼 | 중단(E014 3B는 10분 넘어 중단) | ❌ |
| 지금(memopro 기본) | 없음 | 거부 → 안내(0064) | — |
| 1층만(빠른 int4 커널, 익명 메모리) | R을 넘으면 발생 | 3~16 tok/s | 여유에 좌우 |
| **RCR (F 등급 int4 + 미리 읽기)** | **≈ 0** | R = 2.5면 ≈16, R = 1.5면 ≈3~5 tok/s | 속도 조건은 R에 좌우, 반응성 조건 기대 |
| **RCR + 비트플레인 자기 추측(5.5)** | ≈ 0 | R = 1.5에서 ≈ 7 tok/s(수락 길이 3 가정) | 기대 |

### 5.5 비트플레인 자기 추측 (조합 후보, 중복 중간~높음)

- **아이디어**
  - 초안 모델은 목표 모델 가중치의 **상위 비트플레인**(상주, 예: 3B의 2비트 ≈ 1.05GB)이다. 따라서 초안이 **별도 메모리를 쓰지 않는다**.
  - 하위 비트플레인은 F 등급이라 압박 시 OS가 버릴 수 있다.
  - 검증은 한 번에 k개 토큰을 확인하므로, 하위 비트플레인을 k토큰에 한 번만 읽는다.
- **선행**: QuantSpec(같은 모델의 4비트 가중치·계층적 4비트 KV로 자기 추측), SubSpec(메모리를 넘는 모델에서 저비트 자기 초안을 GPU에 상주), ML-SpecQD, Any-Precision LLM(비트플레인 저장), SpecExec.
- **판정**: 가깝다. 초안과 목표가 **비트플레인을 공유**하고 하위 평면을 **OS가 회수 가능한 파일 페이지**로 둔 조합은 이번 조사에서 확인하지 못했다. **추가 조사 전까지 신규성 주장은 하지 않는다.**

### 5.6 학습 경로

| 구성 | 등급 | 효과 (3B QLoRA 추정, 가설) |
|---|---|---|
| 동결된 기반 가중치(사전 변환 int4) | F | 약 2.1GB를 OS가 쓰기 없이 버릴 수 있다. 익명 메모리 0 |
| LoRA 어댑터·옵티마이저 상태 | A | r=16이면 수백 MB. census가 잰 필요 비트로 옵티마이저 상태 정밀도를 제안 |
| 체크포인트 활성값 | P | 압박 시 폐기 → 앞 체크포인트에서 재계산. 스왑 대신 약간 느려짐 |
| 전체 파인튜닝(작은 모델) | BAdam·LISA처럼 블록을 순차로 학습 | 비활성 블록의 갱신된 가중치를 **파일로 한 번 쓰고 읽기 전용으로 다시 매핑**(A → F "청소"). ZeRO-Infinity의 NVMe 오프로드와 유사, SSD 쓰기 정책 적용 |

기대: 3B QLoRA의 익명 메모리는 1GB 미만이다. 기반 가중치는 F 등급이라 압박에 스왑 없이 대응한다.

## 6. 현실적 목표 (8GB, 가설)

| 작업 | 목표 | 근거 |
|---|---|---|
| 추론 ≤ 3B int4 | **쾌적**(C2 만족) | 전부 또는 대부분 상주 + F 등급 + 빠른 커널 |
| 추론 7B int4 | **쓸 수 있음**(1~3 tok/s, 시스템은 멈추지 않음) | 2.2 모델: 스트리밍이 필수. 쾌적은 목표가 아님 |
| 학습 LoRA/QLoRA ≤ 3B | 쾌적하게 완주 | 5.6 |
| 전체 파인튜닝 | ≤ 0.5B | 블록 순차 + 청소 |

8GB에서 7B를 "쾌적하게" 만든다고 약속하지 않는다. 물리적 한계(SSD 2.45GB/s)가 있다.

## 7. 검증 계획 (사전 등록 전 초안)

| 실험 | 질문 | 관문 |
|---|---|---|
| **E015 기초 측정** | ① 흩어진 page-in 대 순차 재읽기 비용 ② macOS가 압박 시 purgeable 페이지를 익명 메모리보다 먼저, 쓰기 없이 버리는가(`VM_PURGABLE_VOLATILE`, Metal purgeable) ③ PyTorch MPS 무복사 텐서 가능성(mmap → Metal 버퍼 → 텐서) ④ 빠른 MPS int4 커널의 가용성 | **G-P**: ②가 아니면 P 등급을 버린다. **G-F**: ③이 안 되면 전용 커널(RS6 해제 결정) 또는 CPU 경로 |
| E016 RCR 추론 시제품 | E014 조건(1.5B·3B)에서 F 등급 + 미리 읽기가 C2를 만족하는가(스왑 쓰기, 탐침, tok/s) | H-RCR |
| E017 쾌적 제어기 | 인위적 압박(E011 방식)에서 제어기가 반응성 상한을 지키며 속도를 서서히 낮추는가 | E013과 통합 |
| E018 학습 경로 | 3B QLoRA를 F 기반 + P 체크포인트로 돌리면 익명 메모리 1GB 미만, 스왑 쓰기 ≈ 0인가 | |

모든 실험은 E011·E014처럼 **사전 등록, 새 프로세스, `caffeinate`, 반응성 탐침**을 쓴다.

## 8. 사용자 결정 사항

1. 방법론(R1~R5, 1층·2층 구분)의 채택 여부와 우선순위.
2. **E015(기초 측정)** 진행 여부. 모든 2층 작업의 관문이다.
3. G-F 결과에 따라 **RS6(전용 Metal 커널) 보류 해제** 여부(0027에서 보류).
4. RCR 신규성의 체계적 문헌 조사 시점(논문화 전 필수).
5. 1층의 빠른 MPS 저비트 커널 백엔드 조사(E015 ④)를 먼저 할지 여부. 가장 빠른 체감 개선 경로다.

## 한계

- 2.2절과 5절의 수치는 모두 **가설 기반 추정**이다. 측정은 대역폭 두 개(60.3GB/s, 2.45GB/s)와 E011·E014의 값뿐이다.
- 선행 조사는 웹 검색 수준이다.

- SSD 쓰기(F 등급 사전 변환, 청소)는 SSD 수명과 디스크 여유(이 기기는 20% 하한 아래)의 제약을 받는다.
