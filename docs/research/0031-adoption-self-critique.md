# 0031. 자기 비판 2차: 개발자 채택 관점의 평가와 개선 방안 I1~I11

- **날짜**: 2026-09-25
- **유형**: survey+decision (자기 비판)
- **상태**: 확정 (평가) / 개선 방안 I1~I11은 사용자 승인 대기 / I1~I5·I7~I9·H1~H6 채택(→ 0032), I6·I10·I11 대기 / I10 채택(→ 0033)
- **관련 기록**: 0014 (자기 비판 1차, P1~P10), 0029 (중복성 검사 3차), 0028 (현황), 0020 (E006 계측 도구)

## 배경 / 동기

> "너가 개발자라면 이 라이브러리를 사용할 것 같아? 아주 객관적인 관점에서 평가해봐"
> "그럼 개선 방안을 정리해줘. 그리고 자기 비판용도로 연구 기록을 남겨줘."

1차 자기 비판(0014)은 **설계의 논리와 검증 체계**를 대상으로 했다. 이번 2차는 **채택**을 본다. "PyTorch 개발자가 실제로 설치하고 계속 쓸 것인가?"라는 질문이다.

**평가자**: Claude(개발 보조 AI)가 PyTorch 개발자 입장을 가정해 평가했다. 실제 사용자 조사가 아니므로 **가설**로 취급하고, 개선 방안 I1·I3으로 검증한다.

## 1. 평가 결론

> 지금 설계대로 v0.1이 나오면 **대부분의 개발자는 설치하지 않을 가능성이 높다.** 다만 좁은 사용자층(8~16GB 노트북이나 Colab에서 노트북으로 여러 모델을 실험하는 학생·연구자)에게는 β가 설치할 이유가 된다. 성패는 **수요 증명, 신뢰, CUDA 검증**에 달려 있다.

## 2. 기능별 채택 가능성

| 기능 | 채택 가능성 | 이유 | 현재 대안 |
|---|---|---|---|
| β `%hibernate` | 중간~높음 (조건부) | 노트북에서 여러 모델을 오가다 커널을 재시작하는 불편을 직접 겨냥한다. 한 줄 사용, SSD 쓰기 없음(H1 승인 시) | `del` + `gc.collect()` + `empty_cache()`, 커널 재시작 |
| census | 중간 (가끔) | OOM 디버깅 때 "어디에, 얼마나 낭비"를 보여 준다. 매일 쓰지는 않는다 | PyTorch 메모리 스냅샷, `memory_summary()` |
| `check` | 중간 (한두 번) | 편리하지만 정확도가 증명되기 전에는 신뢰하지 않는다 | 직접 실행, vram-check |
| `doctor` | 낮음 | 한 번 보면 끝나는 정보 | `nvidia-smi`, 활성 상태 보기 |
| `load` / `optimize` | 낮음~중간 | HF 옵션 몇 개로 이미 해결하는 사람이 많다. 초보자에게는 가치가 있다 | HF 옵션. Mac의 LLM 추론은 MLX·llama.cpp |
| `train_session` | 낮음 | 학습 설정은 직접 통제하려는 영역이다. 자동 선택이 더 낫다는 증거가 필요하다 | HF Trainer 옵션, Unsloth, ProTrain |
| γ / `memopro run` | 낮음 | 서비스는 예측 가능성을 원한다. 부하에 따른 구성 변경은 지연·품질 변동을 만든다 | 고정 설정, 여유 있는 인스턴스 |

## 3. 강점

1. **β는 실제 불편을 겨냥**하고, 조사 범위에서 같은 도구를 찾지 못했다(0029 D19).
2. **신뢰 설계**: 비트 단위 동일 복원, 오류가 나도 작업이 멈추지 않음(fail-open), 실측 보고, SSD 쓰기량 표시(H5 제안).
3. **보수적 기본값**: 명시 실행, 손실 모드는 명시할 때만, SSD 쓰기는 허락 후(H2 제안).
4. **정직한 연구 과정**: 사전 등록, 부정적 결과 보고, 중복성 공개.

## 5. 개선 방안 (제안 I1~I11)

### A. 수요와 검증 먼저

| # | 방안 | 해결하는 약점 |
|---|---|---|
| **I1** | **β 수요 측정을 구현보다 앞에 둔다.** E006 계측 도구로 사용자 본인과 동료 3~5명의 실제 노트북 세션을 수집한다(0014 P8, 원본이 있는 메모리 비율 측정은 H5 포함). 판정 기준을 사전 등록한다. 예: 세션 중 메모리 압박 빈도, 유휴 바이트 비율의 중앙값. 새 관문 **Gβ**를 두어 β의 우선순위와 범위를 이 데이터로 정한다 | W-a |
| **I2** | **CUDA 검증 경로를 일찍 확보한다.** Colab(T4)에서 β의 호스트 이동 모드를 먼저 시연·측정하는 노트북을 만든다 | W-e |
| **I3** | **공개 시연 시나리오와 수치를 완료 조건에 넣는다.** 예: "Colab T4 / M1 8GB에서 커널 재시작 없이 모델 3개를 오감: 회수 X GB, 복원 Y초, 기존 방법(`del`+`gc`) 대비". 0030 C4의 기존 도구 비교와 묶는다 | W-b, W-h |

### B. 신뢰

| # | 방안 | 해결하는 약점 |
|---|---|---|
| **I4** | **쓰지 않을 때 비용 0**. `import memopro`만으로는 전역 상태를 바꾸지 않고 무거운 모듈도 불러오지 않는다. import 시간과 부작용이 없음을 CI 테스트로 보장한다 | W-c, W-d |
| **I5** | **대리 객체 없는 명시 핸들 방식 제공.** `h = memopro.hibernate.now(model)` → `model = h.wake()`로, 변수를 바꿔 끼우지 않고 사용자가 직접 복원한다. 대리 객체 방식(`%hibernate`)은 편의 기능으로 두고, 한계를 문서화하며 HF `generate` 등 주요 사용 경로를 호환성 테스트한다 | W-c |
| **I6** | **유지보수 신호.** API 안정성 약속(β·census는 v0.1부터 하위 호환 정책), 호환성 매트릭스(0014 P10), 최소 의존성, 변경 기록(CHANGELOG), 알려진 한계 문서 | W-d |

## 7. 로드맵 영향 (제안, I1 승인 시)

현재 순서(0028 §4): 디스크 저장 엔진 → E009 → hwinfo → ledger → census → doctor → β
제안 순서:

```
① E006 실데이터 수집 시작 (동료 참여 필요, 며칠~몇 주 병행)
② β 수요와 무관한 것부터: hwinfo → doctor → census (+ HF 콜백, I8)
③ ◆ Gβ 판정 (I1): 수요 확인 시 → 디스크 저장 엔진(H1 원본 읽기 우선) → E009 → β
                  수요 미약 시 → β 범위 축소(CUDA 호스트 이동 중심), census 비중 확대
```

- doctor·census는 β 수요와 관계없이 쓸모가 있으므로 먼저 만들어도 버릴 것이 없다.

## 8. 함께 대기 중인 제안 (대화에서 제시, 결정 기록 전)

사용자와의 대화에서 제시했고 아직 승인되지 않은 제안이다. 승인되면 별도 결정 기록을 남긴다.

| # | 내용 |
|---|---|
| H1 | β 1순위를 "원본 파일에서 다시 읽기"(SSD 쓰기 0)로. 원본과 같은지는 해시로 확인한다. 텐서 버전 번호는 `.data`를 거친 수정을 잡지 못함을 확인했다(`0 → 1 → 1 → 1`) |
| H2 | 내장 SSD 쓰기는 기본으로 끄고, 명시적으로 허락할 때만. 제안 화면에 쓰기량 표시 |
| H3 | SSD를 쓸 때 쓰기 최소화: 바뀌지 않은 데이터는 다시 쓰지 않음, 반복 방지, 하루 한도, 압축으로 쓰기량 감소 |
| H4 | SSD 성능 보호: 낮은 I/O 우선순위, 여유 공간 20% 미만이면 쓰지 않음 |
| H5 | 측정: 유휴 메모리 중 원본이 있는 비율(E006 확장), E009 쓰기량 지표, `report()`에 SSD 쓰기량 |
| H6 | 사용자 선택 인터페이스: `--mode`(source·host·compress·bf16·spill), `--plan`(방법별 비교), `%wake`, 전체 정책(`configure`, `memopro.toml`, `--disk-writes never`). 선택해도 안전 검사는 우회할 수 없음 |

- I5(명시 핸들 방식)는 H6과 함께 구현하면 자연스럽다.
- I1(수요 측정)의 계측 항목에 H5(원본이 있는 비율)를 포함한다.
