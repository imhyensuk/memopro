# 0162. 긴 시퀀스의 메모리 상한: 흘려 쓰는 MPS 모델은 낮은 워터마크 비율 0.01을 기본으로

- **날짜**: 2026-10-05
- **유형**: implementation (+ 개발 측정)
- **상태**: 확정. E037(0163)로 검증
- **관련 기록**: 0136 (1GiB 힙, 손실 조각 8MiB, "긴 시퀀스에서 다시 생길 수 있음"), 0080·0081 (MPS 힙, `memopro run`의 0.1), 0161 (S1)

## 사용자 지시

"CI 통과하면 병합하고 다음 단계 진행해." PR #44는 CI 통과 뒤 병합했다.

- S4(게시)는 사용자 쪽 준비가 필요하다. 그래서 실사용에서 먼저 부딪힐 0136의 남은 한계를 확인했다.
- `memopro.finetune`의 기본 `seq_len`은 512다. 지금까지 측정은 모두 129토큰이었다.

## 개발 측정 (결과 아님, 3B, 1GiB, `seq_len=512`, E034 글이라 3단계)

| `PYTORCH_MPS_LOW_WATERMARK_RATIO` | footprint 증가(기준점은 MPS 시작 뒤) | 단계 시간(초) |
|---|---|---|
| 0.1(지금까지의 실험 환경) | +2,356MiB(예산 + 1,332MiB) | 16.5, 14.9, 9.6 |
| 0.01 | **+1,539MiB(예산 + 515MiB)** | 15.5, 15.0, 9.7 |
| 0.0(적응 관리 끔) | +2,318MiB | 16.3, 15.0, 9.8 |

- 512토큰에서는 3B의 MLP 중간값(512 × 11,008 × 2B = 11.3MB)이 10MiB를 넘는다.
- torch의 MPS 할당기는 자기 할당이 낮은 워터마크를 넘지 않으면 이런 요청에 1GiB 힙을 준다. 흘려 쓰는 가중치는 할당기 밖의 메모리라 워터마크 계산에 들어가지 않는다(0136의 진단과 같다).
- 비율 0.01(약 55MiB)이면 힙이 커지지 않는다. 속도는 같다.

## 제작

- `memopro.rt.torch.MPS_LOW_WATERMARK = "0.01"`.
- `stream_model(device="mps")`는 MPS를 건드리기 전에 `os.environ.setdefault("PYTORCH_MPS_LOW_WATERMARK_RATIO", "0.01")`을 한다.
  - 사용자가 정한 값은 그대로 둔다.
  - torch의 MPS 할당기가 이미 시작됐으면 효과가 없다. 그래서 스크립트에서 흘려 쓰는 모델을 MPS 사용보다 먼저 만들어야 한다(문서화).
  - `import memopro`는 여전히 부작용이 없다. 이 동작은 `stream_model` 호출 때만 일어난다.
- **남은 것(결정하지 않음)**: `memopro run`은 0081대로 0.1을 넣는다. 그래서 그 아래에서는 0.1이 유지된다. 바꿀지는 E037 뒤에 따로 정한다.
