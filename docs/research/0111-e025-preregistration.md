## 가설

런타임 C-R 1단계(원본 재읽기·압축, 입장 제어, 실측 비용과 재사용 거리 기반 선택)는 다음을 만족한다.
- 여러 번 훑는 큰 숫자 배열 작업을 필요 메모리의 1/2·1/4 예산에서 끝까지 돌린다.
- 예산을 넘지 않는다.
- SSD에 쓰지 않는다.
- 결과는 비트 단위로 같다.
- 사람이 짠 스트리밍 코드보다 느리지 않다.

## 환경

- MacBook Air M1, 8GB 통합 메모리, macOS 26.6.2.
- 측정 시점에 보수적 가용 메모리 약 2GB, 스왑 약 2.4GB가 이미 쓰이는 상태. 경우마다 다시 기록한다.
- Python 3.14, NumPy 2.5.3. memopro는 1단계 빌드(0112의 커밋).
- 모든 경우는 **새 프로세스**에서 하나씩 돈다. `MallocLargeCache=0`으로 해제한 메모리를 곧바로 돌려주게 하고(0060), `caffeinate -i`로 잠들지 않게 한다.

## 데이터 (새 파일을 쓰지 않음, N2)

이미 디스크에 있는 safetensors 파일의 **데이터 영역**(헤더 뒤, 모든 텐서가 이어진 부분)을 하나의 큰 숫자 배열로 본다. 파일 내용은 모델 가중치지만, 작업은 모델과 무관한 일반 배열 통계다.

| 이름 | 파일 | 원소 | 크기 W | 이 Mac에서 전부 올리기 |
|---|---|---|---|---|
| `gpt2` | GPT-2 `model.safetensors` | f32 | 약 523MiB | 가능(기준 측정용) |
| `q15` | Qwen2.5-1.5B-Instruct | bf16 | 약 2.88GiB | 불가능(가용 약 2GB) |
| `q3` | Qwen2.5-3B-Instruct 두 파일 | bf16 | 약 5.75GiB | 불가능 |

- 배열을 **16MiB 블록**으로 나눈다(마지막은 짧을 수 있음). 모든 방법이 같은 블록을 같은 순서로 처리한다.

## 작업: 3회 통계 (P3)

블록마다 4M 원소 조각으로 나눠 **고정된 정렬 작업 배열**에 float32로 복사한 뒤 계산한다. bf16은 `(u16 → u32) << 16`으로 float32로 바꾼다. 이렇게 하면 모든 방법에서 계산 순서와 메모리 정렬이 같아진다.

1. 1회: `s1 += Σx`, `s2 += Σx²` (float64 누적) → 평균 μ, 표준편차 σ.
2. 2회: z = (x − μ)/σ(float32). `c3 += #(|z| > 3)`, `a1 += Σ|z|`.
3. 3회: `m3 += Σz³`, `mx = max(mx, max|x|)`.

결과 (μ, σ, c3, a1, m3, mx)를 JSON으로 남기고, 방법 사이에서 **정확히 같은지** 비교한다.

## 방법

| 방법 | 설명 | 메모리 |
|---|---|---|
| `naive` | 데이터 영역 전체를 한 번 읽어 NumPy 배열로 들고 3회 반복 (`gpt2`만) | W |
| `stream` | 회마다 블록을 16MiB 버퍼에 다시 읽음(보통 읽기, 페이지 캐시 사용) | 블록 하나 |
| `stream_nc` | `stream`과 같되 `F_NOCACHE`(페이지 캐시 안 씀) | 블록 하나 |
| `memmap` | `numpy.memmap`으로 매핑하고 블록 조각을 봄(OS에 맡김) | OS가 정함 |
| `memopro` | `memopro.rt.Runtime(budget)`에 블록을 원본(Source) 버퍼로 등록하고, 회마다 블록을 고정(pin)해 봄 | 예산 |

- **`memopro` 예산**
  - `gpt2`: W/2 = 262MiB, W/4 = 131MiB.
  - `q15`: 1GiB(≈ W/2.9), 512MiB(≈ W/5.8).
  - `q3`: 1GiB(≈ W/5.7).
- **파생 데이터(압축) 경우 `derived`**
  - `q15`의 앞 256MiB(bf16)를 float32로 올린 512MiB를 **메모리 안에서** 만든다(런타임 소유 버퍼, 원본 없음). 이것을 16MiB 블록으로 두고 같은 P3를 돈다.
  - 방법은 `naive`(NumPy 배열로 들고 있음)와 `memopro`(예산 256MiB = 1/2, 압축만 가능).

## 측정

- 전체·회별 시간.
- 런타임 통계: 원본에서 읽은 바이트, 회별 재읽기 바이트, 압축·풀기 횟수와 바이트, 최대 계상 바이트, 쓴 바이트.

## 판정 기준 (실행 전 고정)

| # | 기준 |
|---|---|
| H1 상한 | 모든 `memopro` 경우에서 런타임 최대 계상 바이트 ≤ 예산, 그리고 (최대 RSS − 기준 RSS) ≤ 예산 + 96MiB(계산 작업 배열과 런타임 고정 비용) |
| H2 무손실 | 같은 데이터에서 돈 모든 방법의 결과가 정확히 같다 |
| H3 쓰기 없음 | `memopro`가 쓴 바이트 = 0, 그리고 경우 동안 스왑 증가 ≤ 64MiB |
| H4 못 돌던 것 | `q15`(1GiB, 512MiB)와 `q3`(1GiB)에서 `memopro`가 끝까지 돈다(`naive`는 가용 메모리를 넘어 돌리지 않음) |
| H5 수동 대비 속도 | 모든 `memopro` 경우의 전체 시간 ≤ 같은 데이터 `stream_nc` 시간의 1.1배 |
| H7 정책 | 2·3회에 `memopro`가 원본에서 다시 읽은 바이트 ≤ W − 0.8 × (예산 − 2 × 블록)(회마다). 순환 훑기에서 LRU처럼 전부 다시 읽지 않고 예산만큼은 붙잡아 둠을 뜻한다 |
| H8 압축 | `derived`에서 `memopro`가 끝까지 돌고, 결과가 `naive`와 같고, 압축을 한 번 이상 쓰고, H1과 같은 상한을 지킨다 |

- **관문 G-R1 = H1, H2, H3, H4, H5, H7, H8 모두 통과.**
- **실행 전 수정 2건 (결과를 보기 전, 같은 날, 이 기록을 커밋하기 전)**
  1. **H7 블록 단위 보정**: 처음에는 "W − 0.8 × 예산"이었다. 런타임은 고정 중인 블록 하나와 압축 여유분(약 4MiB)만큼은 붙잡을 수 없어서, 예산이 블록 8~16개뿐인 `gpt2` W/4에서는 최적 정책도 이 기준을 못 넘는다. 계산으로 확인했다(Belady 최적의 순환 적중 = 들어가는 블록 수 − 1). 그래서 "예산 − 2 × 블록"으로 바꿨다.
  2. **`q15`·`q3`에서 `stream`·`memmap` 제외**: 두 방법은 페이지 캐시를 쓴다. 수 GB 파일을 읽으면 페이지 캐시가 커지며 다른 앱의 메모리를 압박해 스왑(SSD 쓰기)을 부를 수 있다(0110 N2). 그래서 큰 데이터에서는 `stream_nc`와 `memopro`만 돌린다. `gpt2`(523MiB)에서는 다섯 방법을 모두 돈다.
- **보고만 하는 추가 경우**: `memopro_lru`(같은 예산, LRU 정책)를 `gpt2` W/2와 `q15` 1GiB에서 돌려 H7의 비교로 싣는다.
- **보고만 하는 가설 H6**: `gpt2`에서 `memopro` 시간 / `naive` 시간 ≤ 2.5(W/2), ≤ 3.0(W/4). 입출력 모형 기준 읽는 양이 naive의 2배, 2.5배이기 때문이다.
- **오염 규칙**: 한 경우에서 스왑이 64MiB 넘게 늘면 그 경우를 한 번 다시 돈다. 다시 돌아도 늘면 그대로 기록한다(다른 앱 영향과 구분할 수 없음).
- **실패 규칙**: 관문이 실패하면 멈추고 원인과 선택지를 보고한다(0110 N6).
