# 0112. 런타임 C-R 1단계 제작: 쓰기 없는 예산 상한 런타임(`memopro::rt`, `memopro.rt`)

- **날짜**: 2026-09-29
- **유형**: implementation
- **상태**: 확정. 관문 E025(G-R1, 0111) 실행 전
- **관련 기록**: 0109 (설계 초안), 0110 (SSD 쓰기 제외, RS7 해제, 이름), 0111 (E025 사전 등록), 0027 (RS1~RS5), 0038 (방출 엔진·코덱), 0060·0080·0105 (할당기 낭비)

## 무엇을 만들었나

### Rust (`crates/memopro/src/rt/`, 약 1,800줄 + 시험)

| 부분 | 내용 |
|---|---|
| `Region` (`region.rs`) | 런타임이 소유하는 메모리. 버퍼와 압축 조각 하나하나가 쪽 단위로 맞춘 익명 mmap이다. 해제하면 곧바로 OS에 돌아간다(할당기 캐시에 남지 않음, 0060·0080·0105의 교훈). `release(offset, len)`은 영역의 일부 쪽만 돌려준다(`MAP_FIXED`로 새 0 쪽으로 교체). Unix가 아니면 표준 할당기를 쓰고 일부 반환은 하지 않는다 |
| `SourceFile` (`source.rs`) | 원본 파일. macOS는 `F_NOCACHE`로 페이지 캐시를 쓰지 않고, Linux는 읽은 범위를 `POSIX_FADV_DONTNEED`로 캐시에서 뺀다. 방출 엔진의 병렬 조각 읽기(`read_region`, 4MiB 조각을 목적지에 바로 읽으며 xxh3 다이제스트)를 그대로 쓴다. 다시 읽을 때마다 크기·수정 시각과 다이제스트를 확인한다 |
| `Runtime` (`mod.rs`) | 버퍼 표와 상태 기계(상주 / 압축 / 버림(원본 있음) / 아직 안 읽음), 입장 제어, 선택 정책, 고정(pin), 통계 |
| 코덱 추가 (`codec.rs`) | `pack_chunk`·`unpack_chunk`: 조각 하나를 스레드별 문맥으로 압축·해제한다(RS3). 런타임이 조각 단위로 메모리를 돌려주기 위해서다 |
| 오류 (`error.rs`) | `Error::Budget`: 예산이 담을 수 없는 요청 |

**핵심 동작**

- **입장 제어(R2)**: 메모리를 쓰기 전에(`alloc`, 되돌리기) 먼저 자리를 만든다. 계상 바이트는 "예산 − 압축 조각 하나의 여유(약 4MiB)"를 넘지 않는다. 자리를 만들 수 없으면(모두 고정 중이거나, 원본도 압축 이득도 없을 때) `Error::Budget`을 낸다. 스왑으로 넘기지 않는다.
- **행동 둘(0110: 쓰기 없음)**: 원본이 확인된 버퍼는 **버린다**(쓰기 없이 다시 읽음). 메모리에서 만든 버퍼는 **압축한다**(1MiB 표본의 압축률이 15% 미만이면 압축할 가치가 없다고 표시). 압축은 조각마다 저장한 뒤 그 조각의 원래 쪽을 곧바로 돌려준다. 그래서 순간 여유는 조각 하나면 된다. 압축 중 오류가 나면 이미 압축한 조각을 풀어 원래대로 되돌린다(R5).
- **선택 점수**: (되돌리는 비용 / 풀리는 바이트) / 다음 사용까지의 예상 거리. 가장 작은 것부터 내보낸다.
  - 비용은 실측 처리량(읽기·압축·풀기, 지수 평활)으로 계산한다.
  - 거리는 버퍼마다 잰 **재사용 주기**(고정 사이의 고정 횟수)로 예측한다. 주기를 아직 모르면 다른 버퍼들의 평균 주기를 쓰고, 아무것도 모르면 경과 시간(LRU)을 쓴다.
  - 그 결과 순환 훑기에서는 방금 쓴 버퍼가 먼저 나간다(MRU). 이것은 Belady 최적과 같은 "들어가는 수 − 1개 적중"이다.
  - 비교용으로 `Policy::Lru`도 둔다.
- **고정**: 고정된 버퍼는 옮기지 않는다(I2).
  - `pin`은 배타적이다: 쓰기 고정은 혼자만, 읽기 고정은 쓰기 고정과 공존하지 않는다. Rust 슬라이스가 겹치지 않게 하기 위해서다.
  - `pin_shared`(unsafe)는 배타성 없이 메모리만 붙잡는다. Python 버퍼 프로토콜과 C ABI처럼 원시 주소로만 쓰는 쪽을 위한 것이다.
  - 쓰기 고정은 원본을 무효로 만든다(이후 버리지 않고 압축만).
- **동시성**: 읽기·압축·풀기는 잠금 밖에서 버퍼를 "작업 중"으로 표시하고 한다. 다른 스레드는 그 버퍼만 기다린다. 서비스 스레드는 아직 없다(2단계의 미리 읽기에서 쓴다, RS7 해제는 0110).

### Python (`memopro.rt`)

- `Runtime(budget="auto" | "2GB" | 0.5, policy="reuse" | "lru")`: `auto`는 보수적 가용 메모리의 절반(0035).
- `add_file(path, offset, nbytes, dtype, shape)`, `load_npy(path)`(C 순서 `.npy`, 헤더만 읽음), `alloc(...)`/`array(shape, dtype)`.
- `Buffer.view(write=False)`: 복사 없는 NumPy 배열을 준다. 버퍼 프로토콜을 쓰고, 읽기 고정이면 쓰기 불가다.
  - **배열이 살아 있는 한 고정이 유지된다**(메모리 안전). `with … as x` 뒤에도 `x`가 남는 Python의 성질 때문에, 곧바로 풀려면 `del x`나 `Buffer.apply(fn)`을 쓴다.
- `bfloat16`은 `uint16`으로 본다.
- 오류는 memopro 예외로 온다: `BudgetExceeded`, `IntegrityError`, `InvalidArgument`.
- `stats()`, `report()`: 읽은·다시 읽은 바이트, 압축, 최대 계상량, 기다린 시간, 디스크 쓰기(항상 0).

## 개발 중에 고친 것

- **주기를 모르는 버퍼의 거리 추정**
  - 처음에는 경과 시간만 썼다. 그러자 두 번째 훑기 후반에 곧 쓸 버퍼(첫 훑기 끝의 버퍼)가 경과 시간이 커져 내보내질 수 있었다.
  - 그래서 "다른 버퍼들의 평균 주기로 다음 사용을 예측"하도록 고쳤다.
- **Python 쓰기 뷰 뒤의 읽기 고정 거절**
  - `with b.view(write=True) as z:` 뒤에도 `z`가 살아 있어 쓰기 고정이 남았고, 다음 읽기 고정이 거절됐다.
  - 배타 규칙은 Rust 슬라이스용이므로, Python 연결은 `pin_shared`를 쓰도록 바꿨다.
- **clippy**: `from_file` → `add_file`로 이름을 바꿨다(`from_*` 관례).

## 시험

- **Rust 16개**(`rt::region`, `rt::source`, `rt::tests`)
  - 0 채움·쪽 정렬·일부 반환.
  - 파일 읽기와 다이제스트, 바뀐 파일 거절.
  - 쓰기·읽기 왕복.
  - 첫 고정에 읽기, 버림 → 다시 읽기가 비트 동일.
  - 무작위 400회 고정 중 계상량 ≤ 한도(I1)와 내용 동일(I4).
  - 고정 중인 버퍼는 남고, 고정이 넘치면 `Budget` 오류(I2).
  - 파일 없는 버퍼의 압축·복원이 비트 동일, 압축 안 되는 데이터는 오류로 거절.
  - 쓰기 뒤 버리지 않음, 바뀐 파일은 `Integrity`.
  - 순환 훑기에서 LRU는 20/20 다시 읽고, 재사용 거리 정책은 ≤ 15/20.
  - 3개 스레드 동시 사용.
- **Python 10개**(`tests/test_rt.py`): 예산 형식, 복사 없는 뷰와 쓰기 제한, 예산보다 큰 데이터의 비트 동일 복원, 남은 뷰의 고정 유지, 압축 왕복, `BudgetExceeded`, `IntegrityError`, `.npy`, bfloat16, 정책 선택.
- 전체: Python 290개 통과, Rust 44개 통과, clippy·fmt·ruff 통과.
- `import memopro`의 가벼움 유지: `memopro.rt`는 지연 이름(`_LAZY`)이고, NumPy는 함수 안에서만 가져온다.

## 한계

- **서비스 스레드·미리 읽기·재계산(계보)·느려짐 예측은 2단계다.**
- **이미 OS 페이지 캐시에 있는 페이지**: `F_NOCACHE` 읽기는 새로 캐시하지 않지만, 이미 캐시에 있는 페이지는 거기서 읽을 수 있다(E025 시험 실행에서 GPT-2 재읽기가 5GB/s로 SSD보다 빨랐음). 런타임이 만든 메모리는 아니지만, 측정에서는 캐시 상태를 적어야 한다.
- 버퍼 단위가 거칠면(예: 16MiB 블록) 예산 활용이 블록 하나 + 여유분만큼 줄어든다.
- Windows는 쪽 단위 일부 반환이 없어 압축 중 순간 메모리가 조금 더 크다(계상은 그대로).

## 논문 매핑

- **주 논문 Design/Implementation**: 쪽 단위 소유 메모리, 쓰기 없는 원본 재읽기(캐시 우회), 조각 단위 압축으로 순간 여유를 한 조각에 묶기, 재사용 주기 기반 선택 점수(순환 훑기에서 Belady 최적과 같은 적중).
