# 0075. E017b 사전 등록: 예열 오판을 고친 쾌적 제어기의 재측정

- **날짜**: 2026-09-28
- **유형**: experiment (사전 등록) + implementation (제어기 수정)
- **상태**: 확정 (결과는 다음 기록)
- **관련 기록**: 0073 (E017 사전 등록), 0074 (E017 결과: 예열 때 잘못 내려가는 결함, K3·K4 일부 실패)

## 배경

> "PR #12 병합하고 제어기 수정 후 E017b 진행해"

- 0074에서 제어기(bf16_ctl)는 6개 시행 모두 A 단계 전에 int4로 내려가 있었다. 불러온 뒤 예열에서 bf16 가중치를 **처음** 읽은 것을 **다시** 읽는 것(붕괴)으로 오판했기 때문이다.
- 이 때문에 K3("C ≥ 0.8 × A")와 K4("쉴 때 bf16과 같다")를 제대로 재지 못했다.
- 0073의 결론 규칙("K4가 실패하면 제어기 비용부터 고친다")에 따라 제어기를 고치고, 결함 때문에 재지 못한 것만 다시 잰다.

## 1. 제어기 수정 (`experiments/e017_controller/controller.py`, `workers.py`)

1. **시작 정밀도를 먼저 정한다** (`Controller.start()`).
   - 가중치를 하나도 읽기 전에 정한다. OS 추정 가용량이 bf16 가중치의 1.2배 이상이면 bf16, 아니면 int4다(복귀 규칙과 같은 기준).
   - 들어갈 수 없는 모델(3B bf16, 6.2GB)은 처음부터 차갑게 읽지 않는다.
2. **예열이 끝날 때까지 판단하지 않는다** (`Controller.arm()`).
   - 예열(4토큰)은 제어기 없이 시작 정밀도로 돌린다. 이때 모든 가중치가 한 번 읽힌다.
   - 그 뒤부터 판단하며, 그 전의 기록은 지운다.
3. **전환 직후 한 창은 우리 page-in을 신호로 쓰지 않는다.**
   - 다른 매핑을 처음 한 바퀴 도는 것은 첫 읽기다. 이는 우리 페이지가 버려졌다는 신호가 아니다.
   - 시스템 스왑 신호(①)는 그대로 쓴다.
- 신호, 문턱(20MB/s, 64MB, 10초, 1.2배, 200MB/s), 판단 간격(2토큰)은 E017과 같다.
- 보조 변경: `run.py --data`(결과 폴더), `analyze.py`의 E017b 판정(`verdicts_b`), 기록에 시작 정밀도(`start`) 추가.

**수정 확인 (판정에 쓰지 않음)**: 사전 등록 전에 압박 없이 A 단계만 한 번씩 돌렸다.
- 1.5B bf16_ctl: 시작 bf16, A 끝 bf16, 조치 없음, 11.7 tok/s.
- 3B bf16_ctl: 시작 int4, 조치 없음, 10.8 tok/s.

## 2. 설계 (`run.py --data e017b`)

- **단계**: E017과 같다.
  - A: 평온, 64토큰.
  - B: 압박 P = min(4GiB, OS 추정 가용량 + 1GiB). 5초 뒤 128토큰. 첫 3초와 나머지로 나눈다.
  - C: 해제 10초 뒤, 64토큰.
  - 새 작업 프로세스마다 돌리고, 반응성 탐침을 함께 쓴다.
- **시행**
  - Qwen2.5-1.5B: `bf16`(제어기 없음)과 `bf16_ctl`.
  - Qwen2.5-3B: `bf16_ctl`만 돌린다.
    - 3B bf16(제어기 없음)은 붕괴가 이미 4회 확인됐다(E016 3회, E017 1회). 한 시행에 15~18분 동안 기기를 끊기게 하므로 돌리지 않는다(`--skip`, skipped로 기록).
  - int4 방법은 이번 수정의 영향을 받지 않는다(전환 없음). E017 값을 그대로 둔다.
- 반복 3회, 순서 회전, `caffeinate -is`.
- **명령**:

  ```
  caffeinate -is .venv/bin/python -m experiments.e017_controller.run --data e017b --cache-dir <E017 캐시> --arms bf16,bf16_ctl --skip Qwen/Qwen2.5-3B-Instruct=bf16
  ```

  분석: `.venv/bin/python -m experiments.e017_controller.analyze docs/research/data/e017b/results.json`.

## 3. 판정 기준 (실행 전 고정, 중앙값)

| # | 질문 | 기준 |
|---|---|---|
| K0 | 수정이 작동하는가 | 1.5B bf16_ctl에서 A에 조치가 없고 A 끝이 bf16인 반복이 3회 중 2회 이상 |
| K1 | 정상 상태의 이웃 피해 | 1.5B B 정상 상태 스왑 증가 bf16_ctl ≤ bf16, 정상 상태 탐침 p95 bf16_ctl ≤ max(24.1ms, bf16) |
| K2 | 압박 중 쓸 만함 | 1.5B B tok/s bf16_ctl ≥ bf16 |
| K3 | 복귀 | 1.5B bf16_ctl C 끝 bf16이 2/3 이상, C tok/s ≥ 0.8 × 자기 A tok/s |
| K4 | 필요 없을 때 해가 없는가 | A에 조치가 없는 1.5B bf16_ctl 반복의 A 토큰이 bf16과 같고, A tok/s ≥ 0.9 × bf16 |
| S | 들어갈 수 없는 모델 | 3B bf16_ctl의 시작이 int4인 반복이 2/3 이상, A tok/s ≥ 3 × 0.27(E017 3B bf16) |
| R | 재정착 비용 | B 첫 3초의 스왑 증가와 탐침. 보고만 한다 |

## 결론 규칙

- **K0~K4와 S가 모두 성립하면**: 제어기를 memopro 기능으로 만드는 결정 기록을 연다. `residency="file"`에 선택형 정밀도 전환을 붙이는 형태이고, 사용자 결정이다.
- **K1만 실패하면**: 제어기의 가치를 "붕괴 방지, 압박 중 속도, 복귀"로 한정해 기능화를 제안한다. 이웃 피해를 줄인다고 주장하지 않는다.
- **K0이 실패하면**: 수정이 듣지 않은 것이다. 원인부터 찾는다.
- **K2~K4 중 하나가 실패하면**: 기능화하지 않고 원인을 기록한다.

## 한계 (미리 적어 둠)

- 수정 확인을 위해 A 단계를 한 번씩 본 뒤에 사전 등록했다(1절).
- 제어기 없는 3B bf16은 이번에 돌리지 않는다. 기준값은 이전 실험 값이다.
- 압박 단계(B)마다 약 30초씩 기기가 느려질 수 있다. E017 중단의 원인이었으므로 사용자에게 미리 알린다.
- 기기 1대, 프롬프트 하나, 탐욕 루프.
