# 0062. E014 사전 등록: 적은 메모리에서 "쓸 만한가" (끝에서 끝까지 벤치마크)

- **날짜**: 2026-09-27
- **유형**: experiment (사전 등록)
- **상태**: 확정 (결과는 0063)
- **관련 기록**: 0060 (E011), 0061 (F1·F4), 0054~0056 (A2), 0059 (예산 형식)

## 배경

> "실제적으로 메모리가 절약되거나 적은 메모리 환경에서 쾌적한 구동이 가능해?"
> "PR #6 병합하고 F1·F4 수정 후 벤치마크 진행해"

지금까지의 검증은 부분 검증이었다. 정확성(비트 동일, 학습 결과 동일), 예측 정확도(`check`), 실제 GPU에서의 완료 조건(A2)을 확인했다. **속도와 체감(쾌적함)은 한 번도 재지 않았다.** 이 실험은 개발 기기(M1 8GB) 자체에서 사용자가 실제로 하는 일을 끝에서 끝까지 재고, memopro 없이 했을 때와 비교한다.

## 1. 파일럿 (판정에 쓰지 않음)

데이터: `docs/research/data/e014/pilot*.json`. 설계를 바꾼 사실은 다음과 같다.

1. **F1·F4 확인** (GPT-2, 1회): 동면 직후 footprint 변화는 이렇다(양수가 반환).

   | | 캐시 켬 | 캐시 끔 |
   |---|---|---|
   | CPU | −0.15 (수정 전 −0.34) | **+0.965** |
   | MPS | −0.29 (수정 전 −0.62) | −0.014 |

2. **MPS는 캐시를 꺼도 돌아오지 않는다. 새 원인을 찾았다.**
   - 동면 후 `torch.mps.driver_allocated_memory()`는 1032MB에서 0이 된다.
   - 그러나 `footprint` 도구로 보면 `IOAccelerator (graphics)`의 dirty 1033MB가 그대로 남는다.
   - macOS 그래픽 드라이버가 해제된 Metal 메모리를 붙잡아 두는 것이다. libmalloc과는 별개라서 F4로 풀리지 않는다.
   - E011에서 압박이 오자 MPS의 `source` footprint가 328MB로 줄었으므로, 압박이 오면 풀린다.
3. **memopro 기본 설정은 이 Mac에서 Qwen2.5-1.5B를 불러오지 못한다.**
   - 장치 예산은 약 1.5~1.9GiB다.
   - int8 구성(2.00GiB)이 넘고, int4(1.46GiB)는 품질 `balanced`가 허용하지 않는다. 결과는 `BudgetExceeded`다.
   - `budget_basis="os"`와 `quality="low"`도 그 순간의 가용량으로는 거부됐다.
   - 그래서 사용자가 스왑을 감수하고 예산을 정하는 방법(`budget="4GB!"`)을 추가했다. 이때는 int8이 선택되어 10.7초에 불러왔다.
4. **그냥 불러오면 1.5B는 돌아간다.** 초당 9.6토큰이다. 그러나 스왑이 5.5GB 늘고, 반응성 탐침의 p95가 256ms로 유휴 때(9~13ms)의 약 20배가 됐다.
5. **학습**: GPT-2, MPS, 배치 8×512, AdamW.
   - 일반 루프는 MPS OOM(최대 8.9GB, 스왑 +4.8GB).
   - `train_session`은 마이크로배치 1로 완주(스텝 7.1초).
6. **모델 두 개 번갈아 쓰기** (1.5B 두 인스턴스)
   - 둘 다 올려 두면 **20분 넘어 중단**됐다(스왑 +7GB).
   - `del` 후 다시 불러오기 181초, β 102초, β에 캐시 끔 119초. 출력은 모두 같았다.
   - 그래서 제한 시간을 10분으로 줄이고, 한 번 제한 시간을 넘긴 방법은 이후 반복을 건너뛰기로 했다(시간과 스왑용 디스크 보호).

## 2. 설계 (`experiments/e014_usable/`)

- 모든 경우를 **새 프로세스**에서 돌린다(`workers.py`).
- 조율 스크립트(`run.py`)가 밖에서 세 가지를 잰다.
  - 작업 프로세스의 phys_footprint(0.2초마다, 최대값)
  - 시스템 스왑 사용량의 증가
  - **반응성 탐침**(`probe.py`): 256MiB 난수 데이터의 모든 페이지를 0.25초마다 한 번씩 읽는 데 걸린 시간. "다른 앱이 느끼는 체감"의 대용이다.
- 파트를 시작하기 전에 10초 동안 유휴 탐침 값을 잰다.
- 반복은 3회이고, 반복마다 방법 순서를 돌린다.
- 제한 시간은 10분이다. 넘기면 실패로 기록하고 그 방법의 이후 반복은 건너뛴다.
- 디스크 여유가 5GiB보다 작으면 그 경우를 건너뛴다(스왑 공간 보호).
- `caffeinate -is`로 잠자기를 막는다.

| 파트 | 경우 |
|---|---|
| reclaim | GPT-2 `source` 동면 직후 footprint 변화. {CPU 익명 가중치, MPS} × {캐시 켬, `MallocLargeCache=0`} |
| f4cost | CPU 학습(GPT-2, 배치 4×256, AdamW, 6스텝). 캐시 켬 대 끔의 스텝 시간 |
| infer | Qwen2.5-1.5B-Instruct(bf16 3.09GB), Qwen2.5-3B-Instruct(6.17GB). 방법 5가지(아래). 채팅 프롬프트 하나, 탐욕 생성. 예열 4토큰 → 첫 토큰 시간 → 64토큰 생성 속도 |
| train | GPT-2, MPS, 배치 8×512, AdamW, 6스텝: 일반 루프 대 `train_session` |
| alternate | 1.5B 두 인스턴스를 A, B, A, B … 8번 사용(각 32토큰): 둘 다 올려 두기 / `del` 후 다시 불러오기 / β(`hibernate.now`, 자동으로 깨어남) / β + `MallocLargeCache=0` |

추론 방법 5가지:
- `naive`: `AutoModelForCausalLM.from_pretrained(id, dtype="auto").to("mps")`
- `memopro`: `memopro.load(id)` 기본 설정
- `memopro_os`: `budget_basis="os"`
- `memopro_low`: `quality="low"`
- `memopro_4gb`: `budget="4GB!"`

## 3. 판정 기준 (실행 전 고정)

**"쾌적함"의 정의 (C2)**: 다음 네 가지를 모두 만족해야 한다(3회 중앙값).
- 생성 ≥ 초당 5토큰(읽는 속도)
- 불러오기 ≤ 120초
- 스왑 증가 ≤ 1GiB
- 탐침 p95 ≤ 유휴 p95의 2배

| # | 질문 | 기준 |
|---|---|---|
| C1 | 불러와지는가 | 3회 모두 성공 |
| C2 | 쾌적한가 | 위 정의 |
| C3 | memopro가 나은가 | 모델마다: `naive`가 C2를 만족하지 못하는데 memopro의 어떤 방법이 만족하면 "memopro가 쾌적하게 만든다". 둘 다 돌아가면 속도 비율을 보고한다 |
| C4 | 학습 | `train_session`은 완주하고 `naive`는 실패하면 "memopro가 가능하게 만든다". 둘 다 완주하면 스텝 시간 비율 ≤ 1.25를 "비용이 작다"로 본다 |
| C5 | 번갈아 쓰기 | β의 전체 시간이 둘 다 올려 두기와 다시 불러오기 모두의 0.8배 이하이고 출력이 같으면 "β가 낫다" |
| C6 | F1·F4 | CPU·캐시 끔의 반환 ≥ 0.8이면 F-E011-1이 F4로 해결된다. CPU·캐시 켬의 반환 > −0.2이면 F1이 증가를 줄였다(수정 전 −0.34). MPS는 보고만 한다(원인이 다르다, §1-2) |
| C7 | F4의 대가 | CPU 학습 스텝 시간이 캐시 끔 ≤ 1.1 × 캐시 켬이면 "대가가 작다" |

## 결론 규칙

- C3에서 두 모델 모두 memopro의 **기본 설정**이 C1을 실패하면, 기본값 문제로 결정 기록을 연다. 이 Mac과 같은 환경에서 memopro가 아무것도 하지 않거나 거부만 한다는 뜻이기 때문이다. 문제의 후보는 보수적 가용량 정의, 품질 기본값, 통합 메모리의 예산이다.
- C2를 만족하는 경우가 하나도 없으면, 이 기기에서 이 크기의 모델은 "memopro로도 쾌적하지 않다"고 적는다.
- C5가 성립하면 β의 첫 사용자 가치("한 커널에서 여러 모델")를 이 조건에 한정해 보고한다.
