# 0114. E026 사전 등록: 런타임 2단계 관문 G-R2 — 미리 읽기, 재계산, 느려짐 예측, 양자화 없는 LLM 추론·LoRA 학습을 필요 메모리의 1/4에서

- **날짜**: 2026-09-30
- **유형**: experiment (사전 등록) + design (2단계 범위)
- **상태**: 확정. 2단계 제작(0115) 뒤 실행한다
- **관련 기록**: 0109 (설계), 0110 (쓰기 없음, 다운로드 없음), 0113 (E025: 계산 주도, 입출력 미중첩), 0072·0071 (F 등급, E016 bf16 붕괴)

## 2단계 범위 (0110의 제약에 맞춘 조정)

| 기능 | 내용 |
|---|---|
| **P 미리 읽기** | 서비스 스레드(RS7 해제, 0110 N3)가 버퍼를 계산과 겹쳐 되돌린다. 순서는 두 가지로 안다: 고정 순서에서 배운 후속 버퍼, 또는 명시 힌트(`prefetch`). 미리 읽기는 더 먼저 쓸 버퍼를 내보내지 않는다 |
| **L 재계산** | `derive(fn, inputs)`: 입력 버퍼와 계산 함수로 만든 버퍼. 버리면 다시 계산한다. 처음 결과의 다이제스트로 재계산 결과를 확인하고(R1), 다르면 `IntegrityError`를 낸다 |
| **R 예측** | 한 주기의 고정 순서·크기·계산 시간을 기록하고, 예산과 실측 대역폭으로 다음 주기의 다시 읽을 바이트와 시간을 예측한다(R6) |
| **T PyTorch** | `memopro.rt.torch`. 모델 골격은 meta로 만들고, 가중치는 safetensors 원본 구간을 런타임 버퍼로 등록한다. 모듈 실행 직전에 고정해 텐서로 쓰고, 끝나면 푼다(복사 없음, CPU). 학습은 `saved_tensors_hooks`로 역전파가 저장한 가중치를 "버퍼 번호"로 바꿔 두었다가 필요할 때 다시 고정한다. 그래서 **원본이 고정된 베이스 가중치를 다시 읽으며 LoRA를 학습**할 수 있다(양자화 없음, QLoRA와 다름) |

- **학습 범위의 정직한 제한**: 쓰기 없이(0110)는 가중치 자체가 바뀌는 전체 학습을 1/4 메모리에서 할 수 없다. 원본이 무효가 되고, 옵티마이저 상태는 압축률이 낮다. 그래서 2단계 학습 목표는 **베이스 가중치가 고정된 학습(LoRA 등)**이다.
- **장치**: CPU. M1 CPU의 bf16 행렬-벡터곱은 약 54GB/s로 SSD 읽기(약 1.8GB/s)보다 훨씬 빨라, 한 토큰씩 생성할 때는 입출력이 시간을 정한다. MPS 복사 없는 연결은 이후 과제다.

## 환경

MacBook Air M1 8GB, 로컬 모델만(0110: 다운로드 없음). 사용하는 모델:
- GPT-2(fp32, 548MB)
- Qwen2.5-1.5B-Instruct(bf16, 3.09GB)
- Qwen2.5-3B-Instruct(bf16, 6.17GB)

경우마다 새 프로세스로 돌리고, `MallocLargeCache=0`, `caffeinate -i`를 쓴다. 스왑은 전후로 기록한다.

## 경우와 판정 기준 (실행 전 고정)

### A. 미리 읽기 (E025 작업 재사용)

- E025의 3회 통계를 `q15` 1GiB, `q3` 1GiB에서 미리 읽기를 켜고 돈다. 같은 세션의 `stream_nc`와 비교한다.
- **P1**: 두 경우 모두 `memopro`(미리 읽기) 시간 ≤ `stream_nc`의 0.95배. 결과는 E025와 비트 동일.

### B. 재계산

- E025 `derived`(q15 앞 256MiB bf16 → float32 512MiB)를 **원본 블록에서 넓히는 계산의 계보**로 정의하고, 예산 128MiB(1/4)에서 3회 통계를 돈다.
- **L1**: 끝까지 돌고, 결과가 `naive`와 같고, 재계산 ≥ 1회, 최대 계상 ≤ 예산, 스왑 증가 ≤ 64MiB.
- 보고만 하는 항목: 시간(압축 경우 E025 256MiB 3.4초, naive 1.7초와 비교).

### C. LLM 추론 (CPU, 탐욕 생성)

- **프롬프트**: 고정된 채팅 프롬프트(약 30토큰). 생성은 16토큰(GPT-2는 32토큰).

| # | 경우 | 기준 |
|---|---|---|
| **C0** 정확성 | GPT-2 fp32: 런타임 스트리밍(예산 W/4 ≈ 137MB) 대 HF 보통 불러오기 | 프롬프트의 마지막 로짓이 `torch.equal`로 같고, 생성 토큰이 같다 |
| **C1** 1.5B | 예산 768MiB(≈1/4)와 1.5GiB(≈1/2) | 둘 다 끝까지 돌고, 생성 토큰과 마지막 로짓이 두 예산에서 같고, RSS 증가 ≤ 예산 + 256MiB, 스왑 증가 ≤ 64MiB |
| **C2** 3B | 예산 1.5GiB(≈1/4)와 3GiB(≈1/2) | C1과 같은 조건 |

- **R1 예측**: C1·C2의 1/4 예산에서, 첫 토큰 뒤 런타임이 예측한 토큰당 시간과 실제 평균의 차이 ≤ 25%.
- **보고만 하는 기준선 S1**: HF 보통 불러오기(safetensors 메모리 매핑, OS 페이징)로 같은 생성을 돈다(1.5B·3B).
  - 가용 메모리보다 커서 OS가 파일 쪽을 버리고 다시 읽는다. 다른 앱의 스왑을 부를 수 있다(0110 N2).
  - 그래서 **감시자**를 둔다: 스왑이 64MiB 넘게 늘면 곧바로 멈추고 "중단: 스왑"으로 기록한다.
  - 끝까지 돌면 토큰당 시간을 memopro와 비교해 보고한다.

### D. LoRA 학습 (베이스 고정, 역전파가 가중치를 다시 읽음)

| # | 경우 | 기준 |
|---|---|---|
| **D0** 정확성 | GPT-2 fp32, LoRA r=8(`c_attn`, `c_proj`, `c_fc`), AdamW lr 1e-3, 배치 2 × 128토큰, 10단계: 런타임 스트리밍(예산 W/4) 대 HF 보통 불러오기 | 단계별 손실과 10단계 뒤 LoRA 파라미터가 `torch.equal`로 같다 |
| **D1** 1.5B | bf16 베이스, LoRA r=8(`q_proj`, `v_proj`, fp32 어댑터), 배치 1 × 128토큰, 5단계, 예산 768MiB와 1.5GiB | 둘 다 끝까지, 단계별 손실이 두 예산에서 같다, RSS 증가 ≤ 예산 + 512MiB(활성값), 스왑 증가 ≤ 64MiB |

- 데이터: WikiText-2(로컬 캐시, 0017의 판) 앞부분. 없으면 고정 텍스트로 바꾸고 기록한다.

## 실행 전 수정 (2단계 제작 중 확인, 결과를 보기 전, 같은 날; 5~8은 실험 스크립트 점검 중)

1. **C0·D0의 GPT-2 예산 W/4 → W/2(274MB)**
   - GPT-2의 가장 큰 가중치(묶인 임베딩 `wte`, 147MiB)가 W/4의 한도(약 133MiB)보다 크다.
   - 지금 구조는 **가중치 텐서 하나가 예산 안에 통째로 들어가야** 한다. 텐서를 행 단위로 나누면 행렬곱의 누적 순서가 바뀌어 비트 동일성을 잃을 수 있다.
   - Qwen은 가장 큰 텐서가 전체의 10~15%라 1/4 예산이 된다.
2. **C0·D0의 참조 = HF 보통 불러오기 + 가중치를 정렬된 메모리로 복사(`p.data = p.data.clone()`)**
   - HF 보통 불러오기는 가중치를 파일 매핑 그대로 두는데, 주소가 64바이트 경계에서 19만큼 어긋나 있다.
   - BLAS 결과는 정렬 상태에 따라 달라진다. 같은 HF 모델이라도 매핑된 채와 정렬 복사본의 로짓이 최대 9.2e-5 달랐다(제작 중 확인).
   - 런타임 가중치는 쪽 단위로 정렬되어 정렬 복사본과 비트 동일했다.
   - 매핑된 참조와의 비교(토큰, 최대 차이)는 따로 보고한다.
3. **R1의 시점**: "첫 토큰 뒤"를 "첫 디코딩 단계(두 번째 토큰) 뒤"로 명확히 한다. 첫 토큰은 프롬프트 전체를 처리해 계산량이 다르다. 예측은 그 뒤 나머지 디코딩 단계 평균과 비교한다.
4. **두 번째 예산**
   - C1 1.5GiB, C2 3GiB, D1 1.5GiB는 이 Mac의 보수적 가용 메모리(약 2GiB)에서 프로세스 전체가 가용량을 넘어 스왑(SSD 쓰기)을 부를 수 있다(0110 N2).
   - 그래서 **두 번째 예산을 1GiB로** 바꾼다: C1 768MiB·1GiB, C2 1.5GiB·1GiB, D1 768MiB·1GiB.
   - "예산이 달라도 결과가 같다"는 기준은 그대로이고, C2는 더 작은 예산(≈1/6)으로 확인한다.
5. **오염 규칙(0111과 같음)**: 한 경우에서 스왑이 64MiB 넘게 늘면 그 경우를 한 번 다시 돈다. 첫 시도의 기록도 함께 남긴다. 다시 돌아도 늘면 그대로 기록한다(다른 앱 영향과 구분할 수 없음). S1은 감시자가 멈추므로 다시 돌지 않는다.
6. **비교를 명확히 한다**(더 엄격한 쪽으로)
   - C1·C2의 "마지막 로짓"은 프롬프트의 마지막 로짓과 마지막 생성 단계의 로짓 **둘 다**로 본다. 둘 다 같아야 통과다.
   - D1의 판정은 적은 대로 단계별 손실이다. 학습된 어댑터가 같은지는 따로 보고한다.
   - C0의 매핑 참조 비교(수정 2)는 같은 프로세스에서 한다: 매핑된 채로 생성한 뒤 가중치를 정렬 복사해 다시 생성하고, 토큰과 로짓 최대 차이를 적는다.
7. **드롭아웃은 모든 경우에서 끈다**(`p = 0`). GPT-2 설정의 드롭아웃 0.1이 `train()`에서 켜지면 난수를 쓴다. 비교하는 두 쪽이 같은 계산을 하도록 모두 끈다. Qwen2.5는 드롭아웃이 없다.
8. **학습 데이터**: WikiText-2 raw train(0017의 판 `b08601e0…`, 로컬 캐시)의 앞 4,000줄을 빈 줄로 이어 토큰화하고, 앞에서부터 단계 × 배치 × 128토큰을 쓴다.

## 관문

- **G-R2 = P1, L1, C0, C1, C2, R1, D0, D1 모두 통과.**
- S1은 보고만 한다.
- 실패하면 멈추고 원인과 선택지를 보고한다(0110 N6).

## 한계 (미리 적어 둠)

- CPU에서 bf16 계산은 느리다(M1 bf16 행렬곱 약 120 GFLOPS). 긴 프롬프트의 첫 토큰 시간은 계산이 주도한다. 생성 단계는 입출력이 주도한다.
- 무손실의 증거는 두 가지다: 보통 불러오기와의 비트 동일(GPT-2, 전부 들어가는 모델), 그리고 예산이 달라도 같음(1.5B·3B). 1.5B·3B를 보통 방식으로 전부 올린 기준 출력은 이 Mac에서 만들 수 없다(스왑).
- 7B는 다운로드가 필요해 하지 않는다(0110).
- (실행 전 추가) M1 CPU에서 bf16 역전파의 `grad @ W`는 torch 2.14가 단일 스레드 일반 gemm으로 계산해 2.8 GFLOPS다(순전파의 1/40, 0115). 보통 불러오기에서도 같다. 그래서 D1은 한 단계에 몇 분이 걸린다. D1에는 속도 기준이 없어 그대로 둔다.
