# 0201. CUDA 흘려 쓰기 개선: GPU 캐시 층과 다음 모듈 미리 복사

- **날짜**: 2026-10-06
- **유형**: decision (사용자 지시) + implementation
- **상태**: 확정. E043(0202)로 검증
- **관련 기록**: 0199 (E042 1차: 7B 흘려 쓰기 생성 41~47초/토큰, 그냥 0.10초), 0195 (복사 경로)

## 사용자 지시

> "그럼 지금 memopro에 대한 테스트 결과를 보면 어쨋든 메모리 절약과 시간 비용을 트레이드한건가? 그 개선 지금 바로 진행해."

- 답(대화): 기본은 공간과 시간의 맞바꿈이다. 다만 품질은 내주지 않고(출력 비트 동일), OS 페이징·llama.cpp 같은 대안보다는 둘 다 낫다(E027·E039). 그런데 T4 결과는 **맞바꿀 필요가 없는데 비용을 낸 경우**였다. 7B가 GPU에 들어가는데도 토큰마다 14GB를 다시 복사했다. 이 구현 결함을 고친다.

## 제작 (`python/memopro/rt/torch.py`, `StreamedWeights`)

- **GPU 캐시 층** (`gpu_budget`)
  - 복사 경로(CUDA)에서 만든 장치 사본을 `gpu_budget` 바이트까지 남긴다. 다음 사용(같은 토큰의 다른 행, 다음 토큰, backward)은 복사 없이 쓴다.
  - 정책: **처음 쓰인 순서대로 예산이 찰 때까지 남기고, 내보내지 않는다.** 모델을 매번 같은 순서로 도는 작업에서 고정된 앞부분을 남기는 것은, 순환 접근에서 Belady 최적과 같은 성질이다. 그래서 단순한 정책으로 충분하다.
  - `stream_model(gpu_budget="auto")`: GPU 여유 메모리 − max(2GiB, GPU의 15%)(활성값·KV 캐시 몫). 0이면 이전처럼 한 모듈씩.
  - 예상: T4(15GB)에서 3B(5.75GiB)와 DINOv2-giant(4.2GiB)는 전부, 7B(14.2GiB)는 약 12GiB가 남는다.
- **다음 모듈 미리 복사**
  - 첫 forward에서 모듈 순서를 배운다.
  - 모듈의 forward가 끝나면(GPU는 아직 그 계산 중) 다음 모듈의 캐시에 없는 가중치를 보조 CUDA 스트림에서 복사한다.
  - 다음 모듈은 그 스트림을 기다린 뒤 쓴다(`wait_stream`, `record_stream`).
  - 페이지 고정되지 않은 호스트 메모리에서 복사하므로, 호스트 쪽 복사는 함수가 돌아올 때 끝난다. 그래서 런타임 버퍼의 고정을 바로 푼다.
- backward의 다시 꺼내기(`unpack`)도 캐시와 미리 복사를 거친다.
- `drop_gpu_cache()`로 사본을 돌려준다. `copy_stats`(복사 수·바이트, 캐시 적중, 미리 복사로 공급)를 남긴다.
- 정확성: 사본은 원본 바이트를 그대로 복사한 것이라 결과가 같다.

## 시험 (이 Mac에는 CUDA가 없어 CPU에서 복사 경로를 강제로 켬)

- `test_copy_path_cache_and_prefetch_keep_results`: 캐시 없음 / 일부(4MiB) / 전부의 세 경우 모두, 생성 글과 LoRA 손실이 제자리 경로와 비트 동일.
  - 전부 캐시이면 가중치마다 정확히 한 번 복사하고, 그 뒤로는 캐시 적중이다.
  - 캐시가 없으면 대부분 미리 복사가 공급한다.
- 흘려 쓰기 시험 25개 통과.

## 논문 매핑

- **System**: 분리 메모리 GPU에서 GPU 메모리를 런타임 위의 캐시 층으로 쓰고, 복사를 계산과 겹치기. 순환 접근에서 고정 앞부분을 남기는 정책.
