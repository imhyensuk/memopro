## 수정

| # | 결함 (0093) | 수정 | 위치 |
|---|---|---|---|
| D1 | `train_session` 사전 계획이 동결 파라미터(LoRA·peft)에서 `MemTracker` hook 오류로 건너뛰어짐 | `MemTracker`가 실패하면 CUDA에서는 샘플 하나의 실제 할당(최대 − 이전 − 만든 기울기)으로 활성값을 재서 계획한다. 다른 장치에서는 이전처럼 계획 없이 진행한다. 다시 돌리기 전에 기울기를 비워 두 번 세지 않는다. 가중치·기울기·옵티마이저 계산에서 **기울기와 Adam 상태는 학습하는 파라미터만** 센다 | `access/_train.py::_plan_first`, `_measure_first` |
| D2 | bf16 하드웨어가 없는 CUDA GPU(sm < 8.0, T4)에서 원본 bf16을 고름 → 긴 프롬프트 3.7~5.4배 느림 | 그런 GPU에서 원본이 bf16이면 "stored"의 속도 등급을 2(긴 입력이 느림)로 두고, fp16 후보(`half`, 근사 무손실)를 더한다. 기본(`prefer="speed"`, `quality="balanced"`)이면 fp16을 고르고, 보고에 이유와 fp16 범위 넘침 위험을 적는다. `quality="lossless"`면 bf16을 그대로 쓴다. Ampere 이상은 바뀌지 않는다 | `orchestrator/candidates.py::infer_candidates`, `SLOW_BF16_NOTE`, `quality_note` |
| D3 | bitsandbytes int8을 int4보다 빠르다고 봄(실제 T4 디코딩 0.27~0.41배) | bnb 백엔드의 int8 속도 등급을 1 → 2로 한다. `quality="low"`에서는 int4가 먼저이고, 기본(balanced)에서는 int8이 CPU 오프로드(3)보다 계속 앞선다. torchao 등 다른 백엔드는 그대로다 | `candidates._quant_speed`, `BNB_INT8_SPEED` |
| D4 | Linux γ가 모델을 불러오는 I/O를 압박으로 오판해 예산 절반 → `memopro run` 정책이 비켜남 | `memopro run`의 γ 기본값을 **모든 플랫폼에서** 끈다(0089 G1의 확대). `--elastic`으로 켜고, 꺼졌으면 보고에 이유를 남긴다. `enable()` 직접 호출과 켜진 뒤의 동작은 그대로다 | `_run.default_elastic`, `ELASTIC_OFF_NOTE`, CLI 도움말, `elastic` 설명 |

- **D2와 `run`의 원칙**: D2 때문에 계획이 속도를 이유로 fp16을 앞에 둘 수 있다. 그러나 `memopro run`은 **원본 그대로 들어가면 개입하지 않는다**(0052 E7). 그래서 정책은 "stored"가 사용 가능하면 그것을 고른 것으로 보고 비켜선다.
- **노트북(Colab) 쪽**
  - 회귀 검사 `platform_defaults`의 기대값을 "run의 γ 꺼짐"으로 바꿨다.
  - 번갈아 쓰기의 다시 불러오기 기준에서 앞 모델을 붙잡던 지역 참조를 없앴다(0093 †).
  - 노트북 3개를 다시 만들었다.

## 시험

- `tests/test_e021_fixes.py` 7개를 추가했다.
  - **D1**: 동결 파라미터와 `MemTracker` 실패를 흉내 냈을 때 결과가 plain SGD와 같다(기울기가 두 번 세어지지 않음). CPU에서는 측정하지 않는다.
  - **D2**: 구형 GPU + bf16이면 half를 고르고 이유 문구를 보고한다. lossless는 stored를 쓴다. Ampere 이상에는 half 후보가 없다. `_note`가 `from_pretrained`로 넘어가지 않는다.
  - **D3**: bnb면 int4 < int8 < 오프로드 순서다. 다른 백엔드는 속도 등급이 그대로다.
  - **D4·run**: 계획이 half를 앞에 두어도 원본이 들어가면 `run`은 bf16 그대로 둔다.
- `tests/test_elastic_run.py`: 모든 플랫폼에서 γ 기본 꺼짐, dry-run 문구.
- 전체 Python 261개 통과, ruff 통과.

## 한계

- **CUDA에서 다시 재지 않았다.**
  - D1의 측정 경로와 D2·D3의 속도 효과는 E021 수치에서 추정한 것이다. 다음 Colab 실행(노트북 재생성 완료)에서 확인해야 한다.
  - D1 측정 경로의 활성값에는 첫 샘플에서 만들어진 옵티마이저 밖의 임시 버퍼가 섞일 수 있다(보수적으로 큼).
- D2의 fp16은 bf16 범위를 넘는 값에서 넘침(inf)이 생길 수 있다. E021의 Qwen2.5에서는 PPL이 같았다(12.619 대 12.621).
- 사소한 결함 D5(고르지 않은 micro 분할, 약간 낙관적인 계획), D6(정적으로 불가능한 학습도 모든 단계를 시도), D7(동면 `source` 대조 비용)은 이번에 고치지 않았다.
