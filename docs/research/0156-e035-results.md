## 진단

1. **버퍼 유지·한꺼번에 울타리(0154의 1번)는 계산을 바꾸지 않는다.**
   - 3B는 새 코드에서도 체크포인팅이 켜진다. 이전과 단계별 손실이 **비트 단위로 같다**(10단계 모두).
   - 하지만 흘려 쓰기(예산 < 모델)에서는 속도 이득이 거의 없다(3B 1.01배, 생성 1.00배). 예산이 금방 차서, 이전처럼 버퍼가 계속 풀렸다 다시 감싸진다.
   - 0154의 큰 이득(4.12 → 3.22초)은 전부 상주(3GiB) 경우였다.
2. **체크포인팅 자동 끄기(0154의 2번)에는 세 가지 문제가 있다.**
   - **메모리**: 32토큰 조각으로 잰 활성값은 129토큰에서 512MiB 아래로 나왔다. 하지만 실제 footprint는 이전(체크포인팅)보다 약 600MiB 컸다. backward의 임시 텐서와 할당기 캐시가 측정에 들어가지 않았다.
   - **수치**
     - 첫 단계의 손실부터 다르다(새 2.7985 대 이전 2.8019).
     - 재진입 체크포인팅 아래의 forward(`no_grad` 안)와 일반 학습 forward가 MPS에서 다른 수치 경로를 탄다(추정: 어텐션 커널 선택).
   - **결정성**
     - 새 코드의 두 반복(같은 코드, 같은 입력)이 셋째 단계부터 서로 다르다(3.344 대 3.347 …).
     - 체크포인팅을 켠 경우는 두 반복이 비트 단위로 같다.
     - 체크포인팅 없는 MPS backward의 어떤 연산이 비결정적이다(원인 연산은 미확인).
     - 이것은 "예산과 무관하게 같은 결과"(G4-B, 0148)라는 원칙과 충돌한다.
3. **속도의 한계**
   - 저전력 모드가 꺼진 상태에서 흘려 쓰는 1.5B의 단계 시간은 약 3.6초(이전) → 3.3초(새)였다. PyTorch를 그냥 쓸 때의 체크포인팅 단계(0154: 3.17초)와 거의 같다.
   - 남은 격차는 PyTorch MPS 계산 자체다(mlx-tune 약 1.08초).
   - 커널 경쟁은 목표 밖이므로(0148) 지금의 범위에서는 더 줄일 여지가 작다.

## 선택지 (사용자 결정)

- **A. 정리하고 E2 닫기(추천)**
  - 버퍼 유지·한꺼번에 울타리는 남긴다. 결과가 같고, 전부 상주일 때 빠르다.
  - 체크포인팅 기본은 다시 "항상 켬"으로 한다. 결정성과 메모리 상한 때문이다. `checkpointing=False`는 명시적 선택으로만 남기고, 결과가 실행마다 다를 수 있다고 문서화한다.
  - E2의 결론으로 "학습 속도의 남은 격차는 PyTorch MPS 계산"을 기록하고 다음으로 넘어간다.
- **B. 자동 체크포인팅을 고쳐 재측정(E035b)**
  - 더 보수적인 메모리 추정, 비결정 연산 찾기. 결정성 문제가 풀리지 않으면 무의미할 수 있다.
- **C. Mac 계산 백엔드를 MLX로 감싸기(새 결정 필요)**
  - 런타임은 그대로 두고, Mac에서 계산을 MLX에 맡기는 선택형 백엔드다. 기존 기법을 감싸는 것이라 0010에 맞지만 큰 작업이다. 커널을 직접 쓰지는 않는다.
