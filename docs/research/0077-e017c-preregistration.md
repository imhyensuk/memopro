# 0077. E017c 사전 등록: Q1·Q2 적용, 쾌적 우선 모드를 기본으로 한 제어기

- **날짜**: 2026-09-28
- **유형**: experiment (사전 등록) + design decision (사용자 결정)
- **상태**: 확정 (결과는 다음 기록)
- **관련 기록**: 0076 (E017b 결과, 수정안 Q1~Q3), 0075, 0035 (보수적 가용량)

## 사용자 결정

> "Q1·Q2 적용, 쾌적 우선 기본으로 E017c 진행해"

- **Q1 채택**: 이웃 신호를 "최근 1초 이상 구간의 시스템 스왑 증가량 ≥ 64MB"로 바꾼다.
  - E017b의 "2토큰(0.16초) 창의 속도 > 20MB/s"는 쉴 때 몇 MB로도 켜졌다.
- **Q2 채택**: bf16으로 시작하거나 복귀할 여유를 memopro의 보수적 가용량(`available_bytes`, 0035)으로 판단한다.
- **Q3 결정**: 모드를 둘로 나누고 **쾌적 우선(`mode="comfort"`)을 기본**으로 한다.
  - 품질 우선(`mode="quality"`)은 E017b처럼 OS 추정 가용량(`kernel_available_bytes`)으로 판단한다. Q1은 두 모드에 모두 적용된다.

## 1. 구현 (`experiments/e017_controller/controller.py`, `workers.py --mode`)

- `Policy`: `swap_mb=64`, `swap_span_s=1.0`, `mode="comfort"`.
- 결정마다 (시각, 시스템 스왑) 표본을 남긴다.
  - 1초 이상 지난 표본 가운데 가장 최근 것과 비교해 증가량을 잰다.
  - 단계가 시작될 때(`reset`) 표본을 비운다. 그래서 단계 시작 후 1초 동안은 이웃 신호로 판단하지 않는다(압박 때 내리는 시점이 최대 약 1초 늦어진다).
- page-in 신호(②), 전환 직후 첫 읽기 무시, 예열 중 판단 안 함, 속도 조절, 복귀의 10초 평온 조건은 E017b와 같다.
- `analyze.py`에 E017c 판정(`verdicts_c`)과 A 단계의 시스템 스왑 증가(`A_swap_mib`)를 더했다.

**동작 확인 (판정에 쓰지 않음)**: 사전 등록 전에 압박 없이 A 단계만 한 번씩 돌렸다.
- 이때 보수적 가용량은 2.1GB였다. bf16 1.5B에 필요한 여유는 3.1GB × 1.2 = 3.7GB다.
- 1.5B: int4로 시작, 조치 없음, 10.7 tok/s.
- 3B: int4로 시작, 조치 없음, 6.5 tok/s.
- **즉 이 기기에서는 쾌적 우선 모드가 두 모델 모두 int4로 시작한다.** 이번 실험은 "그 선택이 쾌적한가, 제어기가 해를 끼치지 않는가, 압박 때 지켜 주는가"를 본다.

## 2. 설계

- **단계와 압박**: E017과 같다(A 64토큰, B 4GiB 압박 128토큰, C 64토큰). 새 작업 프로세스마다 돌리고 탐침을 쓴다.
- **방법**
  - 1.5B: `bf16`(제어기 없음), `int4`(제어기 없음), `bf16_ctl`(두 매핑 + 쾌적 우선 제어기).
  - 3B: `int4`, `bf16_ctl`.
  - 3B `bf16`(제어기 없음)은 붕괴가 4회 확인돼 돌리지 않는다(`--skip`).
- 반복 3회, 순서 회전, `caffeinate -is`. 예상 시간은 약 40분(15개 시행)이다.
- **명령**:

  ```
  caffeinate -is .venv/bin/python -m experiments.e017_controller.run --data e017c --cache-dir <E017 캐시> --arms bf16,int4,bf16_ctl --skip Qwen/Qwen2.5-3B-Instruct=bf16
  ```

  분석: `.venv/bin/python -m experiments.e017_controller.analyze docs/research/data/e017c/results.json`.

## 3. 판정 기준 (실행 전 고정, 중앙값, `bf16_ctl` 대상)

| # | 질문 | 기준 |
|---|---|---|
| C0 | 쉴 때 안정적인가 | A에 조치가 없는 반복이 3회 중 2회 이상(두 모델) |
| C1 | 쉴 때 쾌적한가 (E014 기준) | A tok/s ≥ 5, A 동안 시스템 스왑 증가 ≤ 1GiB, A 탐침 p95 ≤ 24.1ms(두 모델). 1.5B는 A 스왑 증가가 bf16(제어기 없음) 이하 |
| K2 | 압박 중 쓸 만한가 | 1.5B B tok/s ≥ bf16(제어기 없음). 3B B tok/s ≥ 3 × 0.24(이전 3B bf16) |
| K4 | 필요 없을 때 해가 없는가 | 시작 정밀도(다수)와 같은 제어기 없는 방법 대비: A에 조치가 없는 반복의 토큰이 같고, A tok/s ≥ 0.9배 |
| S | 3B 시작 | int4로 시작한 반복이 2/3 이상 |
| R | 보고만 | B 재정착·정상 상태의 스왑과 탐침, 복귀(올림) 횟수, 조치 목록 |

- **K1(정상 상태 이웃 피해)과 K3(복귀)을 보고 항목으로 돌린 이유** (결과를 보기 전에 적음)
  - K1은 E017·E017b 모두 실패했다. 정상 상태의 이웃 피해가 작고 방법 사이에 일관되지 않았기 때문이다(0074, 0076). 이는 제어기가 줄일 대상이 아니라고 이미 해석했다.
  - K3은 쾌적 우선 모드에서 이 기기의 여유로는 bf16 복귀가 일어나지 않을 것으로 예상된다(1절). 설계대로라면 조치가 없는 것이 맞다.

## 결론 규칙

- **C0·C1·K2·K4·S가 모두 성립하면**: 쾌적 우선 제어기를 memopro 기능으로 만드는 결정 기록을 연다.
  - 사용자가 이미 기본 모드를 정했으므로(위 결정), 그 기록에서 API 형태(`residency="file"`와 함께 쓰는 선택형 설정)를 제안하고 확인받는다.
- **C0이 실패하면**: 신호 문턱(64MB/1초)을 다시 본다.
- **C1이 실패하면**: int4조차 이 기기에서 쾌적하지 않은 원인(footprint 1.5GB 문제 등)부터 조사한다.
- **K2나 K4가 실패하면**: 기능화하지 않고 원인을 기록한다.

## 한계 (미리 적어 둠)

- 동작 확인을 위해 A 단계를 한 번씩 본 뒤에 사전 등록했다.
- 쾌적 우선 모드가 int4로 시작하므로, 이번 실험에서 bf16 전환 경로는 거의 시험되지 않는다. 품질 우선 모드의 Q1 효과는 따로 재야 한다.
- 기기 1대, 프롬프트 하나, 탐욕 루프. 보수적 가용량은 그때 켜져 있는 앱에 따라 달라진다.
