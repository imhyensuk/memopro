## 제작 (`python/memopro/rt/torch.py`)

- `_vocabulary_padding`: 어휘 크기가 다르면 두 토크나이저를 불러 비교한다.
  - 같은 토크나이저이면(어휘가 같고 초안 행의 90% 이상을 덮음) 차이만큼 채운다.
  - 실제 Qwen2.5 1.5B·3B·7B의 토크나이저는 모두 같다(151,665토큰).
  - 토크나이저가 다르거나 없거나(파일 없는 폴더는 토큰 1개짜리 기본값이 생긴다), 초안의 행이 더 많으면 `InvalidArgument`.
- `_padded(forward, pad)`: 초안 출력 머리의 로짓 끝에 −∞ 열을 붙이고 초안 `config.vocab_size`를 맞춘다. 초안은 제안만 하므로 출력은 대상의 탐욕 생성 그대로다.

## 진단: 또 하나의 MPS 결함

- 처음 구현은 `F.pad(..., value=-inf)`를 썼다. 그러자 7B 생성이 초안 없이보다 느려졌다(9.29 → 10.91초/토큰).
  - 32토큰에 검증이 31번이었다. 초안의 제안이 거의 매번 첫 자리에서 틀렸다.
- 같은 문장을 통째로 넣으면 int4 1.5B와 7B의 1등 토큰 일치율은 87.5%였다(bf16 1.5B는 96.9%).
- 초안 단독 생성으로 확인했다. 패딩이 없으면 "A hash table is an efficient…", `F.pad`를 쓰면 무작위 문자열이었다.
- 따로 떼어 확인: **torch 2.14의 MPS `F.pad`(상수)가 151,936 폭의 로짓 값을 바꾼다**(bf16·fp32 모두). CPU와 `torch.cat`은 정상이다.
- 그래서 `torch.cat`으로 바꿨다.

## 시험

- `test_draft_with_a_smaller_padded_vocabulary_keeps_greedy_output`(MPS): 작은 대상(8,064행)과 초안(8,000행)이 같은 토크나이저를 쓸 때, 보조 생성이 일반 생성과 같다.
