- **날짜**: 2026-10-04
- **유형**: assessment (사용자 요청)
- **상태**: 확정. 목표 문장은 0148에서 사용자 승인
- **관련 기록**: 0106 (직전 평가, 가중 약 58%), 0107 (목표 재정의), 0123 (G4), 0113·0121·0129 (G-R1~3), 0138 (G4-B1), 0141·0144 (G4-E4 실패 둘), 0146 (정리)

## 요청

> "현재까지의 라이브러리 완성도를 객관적으로 평가해. 그리고 라이브러리의 목표를 다시 한번 명시하고 나한테 승인받아."

## 평가 방법

- 판정 단계는 0095·0106과 같다: 입증됨 / 부분 입증 / 미입증 / 반증. 수치는 각 기록의 측정값이다. 달성률(%)은 그 근거에 따른 연구자의 판단이다.
- **영역과 비중을 바꿨다.** 0106 뒤 목표가 두 번 넓어졌기 때문이다: 0107 범용 Rust 런타임, 0123 Unsloth와의 경쟁.
  - 그래서 이번 합계는 0106의 58%와 **직접 비교할 수 없다.**
  - 0106의 세 영역(추론, 학습, 개발 편의)은 "G1 접근 계층" 하나로 묶었다.
- 측정 기기: M1 8GB(로컬), Colab T4(CUDA), GitHub Linux 실행기(2 vCPU, 8GB). 모델: Qwen2.5 0.5B~7B, GPT-2.

## A. G4-B — 메모리 제한 기기에서 손실 없는 LLM 학습·추론 (비중 30%)

| 근거 | 결과 | 판정 |
|---|---|---|
| E028c (0138) | 8GB M1 GPU에서 **3B bf16 LoRA를 예산 1GiB·768MiB(모델의 1/6~1/8)로** 완주, 예산 간 손실 비트 동일, 11.9~12.1토큰/초, 프로세스 메모리 예산 + 250MiB 안. 1.5B는 CPU 스트리밍의 46배 | 입증 |
| E033b (0144) | 무손실 3B 생성: 상주 int4 초안 + 행 불변 검증으로 일반 생성과 **비트 동일 4/4**, 3.52 → 1.09초/토큰(3.2배). 관문은 시스템 스왑 +70MiB(기준 64)로 실패, E033c 대기 | 부분 입증 |
| 미시험 | 7B 이상(디스크 공간 대기), 16GB Mac, 긴 시퀀스(1GiB 힙이 다시 생길 수 있음, 0136) | 미입증 |
| 미시험 | **Unsloth·mlx-tune과의 직접 비교 0건**(설치 허락 필요) | 미입증 |
| 미제작 | E2(계산 주도가 되도록 단계 크기), E5(무손실 상주 압축), E8(`memopro.finetune` 한 줄 API), C(CUDA에서 Unsloth 감싸기) | — |

- **판정: 부분 입증.**
  - "그 기기에서 남들이 못 하는 크기를 16비트 그대로"는 3B·8GB에서 보였다.
  - 하지만 속도와 사용성이 실용 수준에 못 미친다. 무손실 3B 생성은 약 1초/토큰으로, int4 양자화 추론(약 10토큰/초)보다 한 자릿수 느리다.
  - 경쟁자와 같은 과제로 잰 비교도 없다.
- **달성률: 약 40%.**

## B. G2′·G3 — 범용 런타임 C-R (비중 20%)

| 근거 | 결과 | 판정 |
|---|---|---|
| G-R1 (E025, 0113) | 2.9~5.9GB 숫자 배열을 0.5~1GiB에서, 쓰기 없이 비트 동일, 손으로 짠 스트리밍과 같은 속도 | 입증 |
| G-R2 (E026c, 0121) | 무손실 bf16 3B 추론을 1/4~1/6에서 OS 페이징의 5배, **느려짐 예측 오차 2~6%** | 입증 |
| G-R3 (E027, 0129) | **고치지 않은 NumPy 프로그램**을 1/2에서 비트 동일, OS 스왑의 2.1배, zswap의 2.3배(Linux) | 입증 |
| 제작 | 다섯 행동 중 넷(유지, 무손실 압축, 원본 재읽기, 계보 재계산). 다섯째(SSD로 옮기기)는 0110 결정으로 런타임에서 뺐다. C ABI `mp_*`, NumPy 연결, PyTorch 연결 | 입증 |

- **판정: 입증됨(핵심 관문 셋 모두 통과).** 남은 것은 적용 범위(macOS 투명, 예측의 학습 확장)다.
- **달성률: 약 65%.**

## C. G1 — 접근 계층 (`load`/`check`/`optimize`/`train_session`/`run`) (비중 15%)

- 0106의 판단 그대로다: 추론 약 65%, 학습 약 62%, 개발 편의 약 72%.
  - T4에서 결함 없이, 표준 방식과 같은 속도로 작동한다(fp16 TTFT 1.04~1.07배, int4 1.13배, QLoRA 0.97배).
- 그 뒤에 더해진 것: `load(fallback="stream")`(0124). 아무것도 들어가지 않으면 무손실 스트리밍으로 돌린다.
- 남은 것: D6(불가능한 학습을 바로 거절), 장치 2배 초과의 오프로드 추론.
- **달성률: 약 66%.**

## 다음 단계 (달성률을 가장 많이 올릴 순서, 제안)

2. **E8 한 줄 API + 빠른 시작**: `memopro.finetune(...)`/`memopro.generate(...)`가 기존 부품을 묶는다. 제품 준비와 G4 모두를 움직인다.
3. **7B**: 사용자가 디스크 공간을 확보하면 7B 16비트 LoRA와 생성을 8GB M1에서. "남들이 못 하는 크기"의 결정적 사례다.
4. **경쟁자 비교**(설치 허락 필요): mlx-tune/Unsloth(MLX)와 같은 기기·과제에서 메모리·속도·품질.
5. **첫 공개 배포**(0097 오픈소스 결정에 따라, 사용자 확인 뒤).

## 목표 재확인 (사용자 승인 대기)

이 절의 문장은 0107과 0123을 하나로 정리한 것이다. 바뀐 내용은 없고, 아래 "확인할 점" 두 개만 명시했다. 승인되면 CLAUDE.md의 목표 문단을 이 문장으로 바꾼다.

- **한 문장**: memopro는 메모리가 부족한 기기(8~16GB 노트북·Mac, 작은 GPU)에서, 그 기기 메모리를 넘는 작업을 **손실 없이, 보장된 메모리 상한 안에서, 쓸 만한 속도로** 돌리게 하는 오픈소스 라이브러리다(Rust 코어 + Python).
- **주 목표 1 — G4-B (AI)**
  - 기기 메모리를 넘는 LLM의 16비트 LoRA 학습과 추론.
  - 기본은 무손실이다. 출력이 일반 실행과 비트 동일하고, 예산이 달라도 결과가 같다.
  - 같은 기기에서 Unsloth·mlx-tune·HF가 돌리지 못하는 크기를 돌리는 것이 경쟁 지점이다. 커널 속도 경쟁은 하지 않는다.
- **주 목표 2 — G2′·G3 (범용)**
  - 큰 배열·영상·데이터프레임·시뮬레이션 같은 일반 작업을 필요 메모리의 1/2~1/4에서 돌린다.
  - 무손실, 상한 보장, 실행 전 느려짐 예측.
  - 엔진은 Rust 런타임 C-R이다. 버퍼마다 유지 / 무손실 압축 / 원본 재읽기 / 계보 재계산 중에서 측정 비용으로 고른다.
- **유지 — G1**: 접근 계층(`load`, `check`, `optimize`, `train_session`, `memopro run`)이 기존 기법을 감싸 OOM 없이 돌린다.
- **보조 — G4-C**: CUDA에서 Unsloth 류 백엔드가 있으면 선택적으로 감싸고, 메모리 초과분만 런타임이 맡는다.
- **범위 밖**: 코드를 쓰지 않는 최종 사용자, 외부 도구로 안내하기, Triton 커널 경쟁, 손실이 기본값인 방식.
- **확인할 점**
  1. **SSD**: 0107의 다섯째 행동("SSD로 옮기기")은 0110에서 런타임에서 뺐다. 목표 문장에서도 빼고 "디스크에 쓰지 않음"을 원칙으로 둔다.
  2. **성공 기준**(측정 가능하게)
     - S1 8GB M1에서 3B 16비트 LoRA(달성), 16GB Mac에서 7B 16비트 LoRA 완주.
     - S2 무손실 생성이 흘려 쓰기만 할 때의 2.5배 이상(E033c).
     - S3 mlx-tune 또는 Unsloth와 같은 과제로 직접 비교.
     - S4 한 줄 API와 첫 공개 배포.
