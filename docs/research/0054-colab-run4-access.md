## 1. 실행 전에 바뀐 것 (기록)

사용자가 첫 실행을 시도하기 전후에 세 가지를 고쳤다. 모두 판정 결과를 보기 **전**이다.

1. **노트북 오류**: `memopro.access`가 지연 이름으로 등록돼 있지 않아 첫 셀이 `AttributeError`로 멈췄다. 노트북이 하위 모듈을 명시적으로 불러오게 했고, 패키지에도 `access`를 지연 이름으로 추가했다.
2. **결함(원인 조사 중 발견)**: `load`가 한 구성에서 실패하면, fail-open 결과(`Outcome.error`)가 보관한 예외의 traceback이 **부분적으로 불러온 모델을 붙잡은 채** 다음 구성을 불러왔다. GPU에서 7B 로드가 중간에 실패하면 그 메모리를 안고 대체 구성을 시도해 다시 실패할 수 있었다.
   - 수정: 실패한 결과를 버린 뒤 캐시를 비운다.
   - `train_session`도 캐시 비우기를 `except` 블록 밖으로 옮겼다. 블록 안에서는 실패한 시도의 텐서가 아직 살아 있기 때문이다.
   - 회귀 테스트 2개를 추가했다. 할당 **후** 실패를 흉내 내며, 이전 코드에서는 실패한다.
   - 이전 테스트가 놓친 이유: 가짜 OOM을 할당하기 **전에** 던졌다.
3. **판정 변수 조정**: `train_capped`의 장치 한도를 고정 30%에서 "한도 없는 보통 스텝 최대치의 65%"로 바꿨다. T4의 SDPA 커널은 활성값이 작아서, 30%에서는 보통 스텝이 들어가 버려 memopro와 무관하게 판정이 실패할 수 있었다. 판정 기준(보통 스텝 OOM, SGD ≤ 1e-5)은 그대로다.

## 4. A2-3 원인 분석

**확인된 불일치 하나**: torch는 foreach 구현을 순수 `Tensor`/`Parameter`에만 고른다(`_default_to_fused_or_foreach`의 `type(p) in _foreach_supported_types`).
- 그래서 FakeTensor로 추적하면 "cuda" 장치여도 **단일 텐서 AdamW**가 쓰인다. 실제 CUDA는 **foreach**를 쓴다.
- foreach는 파라미터 크기의 임시 버퍼(예: `exp_avg_sq`의 제곱근 목록)를 만든다. 추적에서는 이것이 빠진다.

**수치로 뒷받침되는 것**: gpt2-medium 1×512의 측정값 7.12GB는 "파라미터 1.42 + 그래디언트 1.42 + AdamW 상태 2.84 + foreach 임시 1.42 = 7.1GB"와 거의 같다. 옵티마이저 스텝이 최대치인 경우다.

**설명되지 않는 것**: gpt2 2×512(−0.73GB)와 gpt2-medium 2×512(−1.48GB)는 foreach만으로 다 설명되지 않는다. 역전파 초반의 임시 텐서나 SDPA 커널 선택(가짜 추적과 실제의 차이)일 수 있지만 **추측이다.**

**조치**:
- `check`의 추적이 실제 장치에서 torch가 고를 옵티마이저 구현을 쓰게 했다(`_real_implementation`, CUDA면 foreach). 보정 계수는 넣지 않았다. 실제와 다른 조건을 실제와 같게 만든 것이다.
- 남은 차이는 5차에서 **단계별로 측정해** 찾는다.

## 5. Colab 5차 사전 등록 (`examples/colab_check_accuracy.ipynb`)

- **판정은 4차와 같다**: 같은 6개 경우가 모두 CUDA 정상 상태 최대치의 ±15% 이내.
- **진단(판정 아님)**:
  - 실제 스텝의 단계별 최대치(순전파, 역전파, 옵티마이저 스텝)와 최대치가 난 단계
  - 실제 텐서로 돌린 `MemTracker` 최대치: 추적기 자체와 할당자의 차이를 본다
  - 예측의 구성(파라미터, 그래디언트, 옵티마이저 상태, 활성값)
  - 실제로 선택된 옵티마이저 구현
- 5차도 불합격이면 기준을 바꾸지 않는다. 진단 결과로 원인을 확정한 뒤 다음 수정을 하고, 그때도 사전 등록한다.

## 결론

- `load`(7B·int8, 소형 4단계), `train_session`(실제 OOM, 정확도), 활성값 오프로드는 **실제 GPU에서 사전 등록 조건을 만족했다.**
- `check`는 추론은 정확했지만(±5%) 배치가 작은 학습을 과소 예측해 **기준에 미달했다.** 기존 도구보다는 모든 경우에 정확했다.
- 원인 조사 중 `load` 대체 경로의 메모리 누수를 찾아 고쳤다.
