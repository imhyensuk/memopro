- **날짜**: 2026-09-29
- **유형**: experiment (사전 등록) + tool (수집 도구 검증)
- **상태**: 확정. **데이터 수집은 사용자와 참여자(동료 3~5명)가 해야 한다.** 결과는 수집 뒤 다음 기록
- **관련 기록**: 0032 I1 (β 수요를 측정하는 E010, 관문 Gβ), 0036 (Gβ는 배포 전 검증), 0017·0020 (E006 계측 도구와 검증), 0031 H1 (`source` 우선의 전제 = 원본이 있는 유휴 메모리의 비율), 0064 (기본값 D-b·D-c는 E010 없이 바꾸지 않음)

## 1. 수집 도구 (`experiments/e010_demand/memopro_e010_probe.py`, 단일 파일)

- E006 도구(0020에서 검증)의 유휴 판정을 그대로 쓴다.
  - 이름이 셀의 변환된 코드나 원문(매직 포함)에 나오면 사용한 것으로 본다. 유휴를 부풀리지 않는 방향이다.
  - 유휴 기준은 3셀이다.
- **E006에 더한 것**
  - **이름은 세션마다 다른 소금값의 해시(12자)로만 남긴다.** `E010_NAMES=1`이면 이름을 그대로 남긴다(연구자 본인의 확인용).
  - `source_known`: 원본 가중치 파일이 이 기기에 있는 모델인지 여부(예/아니요)다. `config._name_or_path`가 무게 파일이 있는 로컬 폴더이거나 HF 허브 캐시에 있는 모델 id인 경우다. 셀마다 유휴 바이트 가운데 이런 모델의 몫을 `idle_source_bytes`로 남긴다.
  - OS 메모리
    - macOS: `hw.memsize`, `vm_stat`의 free + inactive + purgeable, `vm.swapusage`.
    - Linux: `/proc/meminfo`의 MemAvailable과 스왑.
    - 세션 시작 대비 스왑 증가를 기록한다.
  - GPU: CUDA 할당·예약·전체, MPS 할당·드라이버.
  - `oom`: 셀이 이름이나 메시지에 OutOfMemory나 "out of memory"가 들어간 오류로 끝났는지만 남긴다. 메시지는 저장하지 않는다.
  - 세션 기록: 플랫폼, 아키텍처, Python·torch 판, 전체 메모리.
- 기록하지 않는 것: 코드, 셀 내용, 값, 경로, 모델 이름, 오류 메시지.
- 참여자 안내는 `experiments/e010_demand/README.md`(한국어·영어)에 있다.

## 3. 수집 절차

- **참여자**: 사용자 본인과 동료 3~5명(0032 I1).
  - 평소 작업하는 PyTorch 노트북 세션을 사람마다 2~3개 모은다. 20셀 이상인 세션만 쓴다.
  - 기기와 GPU 종류는 제한하지 않는다. 세션 기록에 남는다.
- **전달**
  - 연구자가 참여자에게 직접 연락하거나 파일을 받지 않는다. 사용자가 도구와 안내를 전하고 파일을 모은다.
  - 파일은 저장소의 `docs/research/data/e010/sessions/<참여자 라벨>/`에 둔다. 라벨은 p1, p2 같은 익명이다. 원본 파일을 그대로 둔다.
  - 참여자가 원하지 않으면 저장소에 올리지 않고 로컬에서만 분석한다. 이 경우 결과 기록에 그 사실을 적는다.
- **마감**: 사용자가 정한다. 마감까지 최소 조건(참여자 3명, 작업 세션 8개)을 채우지 못하면 판정하지 않는다(4절).

## 4. 지표와 Gβ 판정 규칙 (수집 전 고정)

- 작업 세션: 셀 20개 이상.
- **세션별 지표**
  - **S2 의미 있는 유휴**: 어느 셀에서든 유휴 바이트 ≥ 1GiB, 또는 ≥ 장치 메모리의 25%다. 장치 메모리는 CUDA가 있으면 GPU 전체, 없으면 호스트 전체다.
  - **S3 압박 중 유휴**: 어느 셀에서든 유휴 ≥ 0.5GiB이면서 압박이 있다. 압박은 다음 가운데 하나다.
    - 그 셀의 OOM.
    - 세션 시작 대비 스왑 증가 ≥ 1GiB.
    - CUDA 예약 ≥ 전체의 90%.
    - OS 가용 < 전체의 10%.
  - **S4 원본 몫**: 유휴가 가장 컸던 셀에서 `idle_source_bytes` / `idle_bytes`.
- **판정** (`analyze.py`, 참여자 3명 이상이고 작업 세션 8개 이상일 때만)

| Gβ | 조건 | 조치(결정 기록을 열고 사용자가 정함) |
|---|---|---|
| strong | S3 세션 비율 ≥ 25% | β를 주요 기능으로 유지한다. 압박 중 큰 유휴를 보면 `%hibernate`를 제안하는 안내(γ·노트북)를 제안한다 |
| moderate | S3 < 25%이고 S2 세션 비율 ≥ 50% | β를 명시적 도구로 유지하고 문서화한다. 자동 안내는 하지 않는다 |
| weak | S2 < 50% | β를 좁은 용도로 문서에 적는다. README에서 비중을 낮추고 기본값은 그대로 둔다(0036) |

- **S4 중앙값에 따른 방식 순서**
  - ≥ 50%: `source` 우선 확정.
  - 20~50%: 유지.
  - < 20%: 방식 순서(host·compress 우선) 재검토를 제안한다.
- **자료가 모자랄 때**: 기술 통계만 보고하고 Gβ는 열린 채로 둔다. 배포 노트에 "수요 미측정"이라고 적는다.
- 0064의 기본값 D-b(예산 기준), D-c(품질 기본)는 이 결과를 보고 따로 다룬다.

## 한계 (미리 적어 둠)

- 참여자가 사용자 주변 사람이라 표본이 치우친다(노트북을 쓰는 연구자·개발자).
- 사용 판정은 이름의 등장 여부다. 간접 사용(다른 객체가 참조하는 텐서)은 "사용"으로 보지 않는다. 대신 이름이 셀에 나오기만 하면 사용으로 보므로 유휴는 과소 추정된다.
- `source_known`은 원본 파일이 있다는 뜻일 뿐이다. 가중치가 학습으로 바뀌었는지는 모른다. 바뀌었으면 β `source`는 다이제스트 대조에서 거절하고 다른 방식으로 넘어간다.
- 압박 신호는 OS마다 다르다. Windows에서는 OS 메모리 필드가 없다.
