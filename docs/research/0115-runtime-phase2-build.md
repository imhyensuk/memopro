# 0115. 런타임 C-R 2단계 제작: 미리 읽기 서비스 스레드, 재계산(계보), 느려짐 예측, PyTorch 가중치 스트리밍(`memopro.rt.torch`)

- **날짜**: 2026-09-30
- **유형**: implementation
- **상태**: 확정. 관문 E026(G-R2, 0114) 실행 전
- **관련 기록**: 0109 (설계), 0110 (쓰기 없음, RS7 해제), 0112 (1단계), 0113 (E025: 계산 주도, 입출력 미중첩), 0114 (E026 사전 등록)

## 배경

- E025(0113)는 관문 G-R1을 통과했지만 속도 이득이 없었다. 1단계에는 입출력과 계산을 겹치는 장치가 없었다.
- 2단계 범위(0114)는 네 가지다: 미리 읽기(P), 재계산(L), 느려짐 예측(R), PyTorch 연결(T).

## 무엇을 만들었나

### Rust (`crates/memopro/src/rt/`)

| 부분 | 내용 |
|---|---|
| **서비스 스레드** | `prefetch`가 켜져 있으면(기본) `Runtime::new`가 `memopro-rt` 스레드를 띄운다. 마지막 `Runtime` 복제가 사라지면 멈추고 합류한다. 런타임이 소유한 메모리만 만진다(R4, I6) |
| **순서 학습** | 고정(사용)할 때마다 직전에 고정한 버퍼의 "다음"을 지금 버퍼로 적는다. 고정 직후 그 사슬을 따라가며 상주하지 않은 버퍼를 줄에 넣는다. 최대 64단계, 창은 `min(lookahead, 한도/4)` 바이트다 |
| **미리 읽기의 자리 만들기** | 목표 버퍼보다 **늦게 쓰일 것으로 예측된 버퍼만** 내보낸다. 미리 읽었지만 아직 쓰지 않은 버퍼도 내보내지 않는다. 자리가 없으면 그냥 건너뛴다(`prefetch_skipped`). 힌트 `prefetch(id)`도 있다 |
| **재계산(계보)** | `derive(inputs, nbytes, elem, compute)`. `compute`는 `Fn(&[&[u8]], &mut [u8]) -> Result<()>`이다. 처음 결과의 다이제스트를 적어 둔다. 버리는 비용 = 계산 시간 + 버려진 입력을 되돌리는 비용. 되돌릴 때는 호출자 스레드에서 입력을 고정해 다시 계산하고, 다이제스트가 다르면 `Error::Integrity`를 낸다(다른 데이터를 돌려주지 않음) |
| **입력 보호** | 버려진 파생 버퍼가 필요로 하는 입력은 쓰기 고정과 `free`가 거절된다. 파생 버퍼가 쓰기 고정되면 그 계보는 잊는다(이제 계산 결과가 아니므로) |
| **고정 세 종류** | `pin`(배타, 안전한 Rust 슬라이스), `pin_shared`(unsafe, 원시 주소: Python 버퍼 프로토콜·C ABI), `pin_untracked`(unsafe, 사용으로 세지 않음: 재계산 입력, recipe에 주는 뷰) |
| **예측** `predict()` (`predict.rs`) | 고정 기록 고리(65,536개)에서 마지막 버퍼의 연속한 두 고정 사이를 한 주기로 본다. 그 주기를 세 번 반복하는 Belady(OPT) 모의로 정상 상태의 되돌림 바이트와 시간을 구한다. 용량은 "한도 − 미리 읽기 창"이다. 계산 시간 = 주기 경과 시간 − 고정에서 기다린 시간. 예측 초 = 미리 읽기면 max(계산, 되돌림), 아니면 둘의 합 |
| **통계** | `pins`, `recomputes`·`recompute_bytes`·`recompute_seconds`, `prefetches`·`prefetch_bytes`·`prefetch_hits`·`prefetch_wasted`·`prefetch_skipped` |

- 서비스 스레드는 계보 버퍼를 미리 계산하지 않는다. 계산 함수가 Python일 수 있어서, 서비스 스레드가 GIL을 잡지 않게 하려는 것이다. 재계산은 버퍼 잠금 밖(버퍼만 "작업 중")에서 돈다. 그래서 GIL을 쥔 다른 스레드가 `stats()`를 불러도 교착하지 않는다.

### Python 연결 (`crates/memopro-py`)

- `RtRuntime(..., prefetch=True, lookahead=64MiB)`, `prefetch`, `derive`, `predict`.
- `derive`의 계산 함수에는 입력을 `RtPin`(버퍼 프로토콜)으로, 출력을 쓰기 가능한 `memoryview`로 준다. 둘 다 호출 중에만 유효하다.
- 오류: `Budget` → `BudgetExceeded`, `Integrity` → `IntegrityError`, `InvalidArgument` → `InvalidArgument`.
- `_core.pyi` 형식 스텁도 맞췄다.

### Python `memopro.rt`

- `Runtime(prefetch=True, lookahead="64MiB")`, `derive(fn, *inputs, dtype=, shape=)`, `predict()`, `Buffer.prefetch()`.
- `report()`에 재계산·미리 읽기 줄을 더했다.
- `derive`는 함수가 입력 배열을 붙잡아 두면(약한 참조로 확인) `InvalidArgument`를 낸다. 붙잡힌 배열은 버퍼를 계속 고정시키기 때문이다.

### PyTorch `memopro.rt.torch` (새 모듈)

- **`stream_model(name_or_dir, budget=, ...)`**
  - safetensors 헤더만 읽어 가중치 구간 표를 만든다.
  - 모델 골격은 meta 장치에 만든다(`accelerate.init_empty_weights(include_buffers=False)`). dtype은 파일에 가장 많이 저장된 부동소수 형식이다.
  - 입력·출력 임베딩을 다시 묶는다. meta로 만들면 GPT-2의 `lm_head`가 풀린 채 남았다.
  - 서로 다른 파라미터마다 런타임 버퍼 하나를 원본 구간으로 등록한다(`add_file`). 파일에 저장된 작은 버퍼(persistent buffer)는 한 번 보통으로 읽는다.
  - 모듈마다 forward 앞 훅이 자기 가중치를 고정해 `torch.frombuffer` 텐서로 바꿔 끼운다(복사 없음, CPU). forward 뒤 훅이 meta 자리표시로 되돌린다. 고정은 텐서 수명을 따른다.
  - 모델 클래스를 바꿔 `device`가 CPU를 돌려주게 한다(`generate`가 meta를 보지 않게).
- **`saved_weights(model)`**: `saved_tensors_hooks`로, 역전파용으로 저장되는 스트리밍 가중치(또는 그 뷰)를 참조(버퍼, dtype, 크기, stride, offset)로 바꾼다. 역전파 때 다시 고정해 `as_strided`로 되살린다. 그래서 고정된 베이스 가중치 위에서 LoRA를 학습해도 가중치가 계산 그래프에 붙잡히지 않는다.
- 가중치의 저장 dtype을 바꾸지 않는다. 모델과 파일의 dtype·모양이 다르면 거절한다.

## 개발 중에 확인한 것

1. **정렬과 BLAS(0114 수정 2의 근거)**
   - HF 보통 불러오기는 가중치를 파일 매핑 그대로 둔다. 그 주소는 64바이트 경계에서 19만큼 어긋나 있다(safetensors 헤더 길이 때문).
   - CPU BLAS 결과는 정렬에 따라 달라진다. 같은 HF GPT-2의 로짓이 매핑된 채와 정렬 복사본 사이에서 최대 9.2e-5 달랐다.
   - 런타임 가중치는 쪽 단위로 정렬되어, 정렬 복사본과 비트 동일했다.
   - 즉 "무손실"의 기준은 "같은 바이트, 같은 정렬의 같은 계산"이다.
2. **가장 큰 텐서 제약(0114 수정 1의 근거)**: 텐서 하나가 한도 안에 통째로 들어가야 한다. GPT-2 `wte`(147MiB)는 W/4 한도보다 컸다. 행 단위로 나누면 행렬곱의 누적 순서가 바뀔 수 있어 나누지 않았다.
3. **`torch.frombuffer`의 수명**: 버퍼 객체(`RtPin`)는 참조로 붙잡지만, 버퍼 내보내기(export)는 곧바로 푼다. 그래서 torch 경로는 `release()`를 부르지 않는다. 고정은 텐서와 그 뷰가 모두 사라질 때 풀린다(4MiB 고정이 텐서나 뷰가 살아 있는 동안 유지되고, 사라지면 0이 됨을 확인).
4. **`np.frombuffer(memoryview)`는 내보내기를 붙잡지 않는다.** 그래서 `derive` 입력은 `memoryview`가 아니라 `RtPin` 객체로 넘긴다. 그러지 않으면 뷰가 매달릴 수 있었다.
5. **미리 읽기 낭비**
   - 처음 구현은 한 주기에 17~18개를 헛되이 읽었다. 미리 읽은 버퍼가 쓰이기 전에 다른 미리 읽기에 밀려났다.
   - 고친 것: 창을 한도의 1/4로 제한, 미리 읽기의 자리 만들기에서 미리 읽은 버퍼 제외, 미리 읽고 아직 안 쓴 버퍼의 거리 = 1.
   - 결과: 시험 작업에서 주기마다 8개 미리 읽기, 8개 적중, 낭비 0.
6. **비용 추정의 흔들림**
   - 1단계는 되돌리기 한 번마다의 속도(바이트/초)를 지수 평활(0.3)했다.
   - 작은 가중치(편향·정규화 3KB)와 큰 가중치가 섞이면, 추정이 마지막 읽기의 크기에 따라 흔들렸다. GPT-2에서 예측이 5배 틀렸다(0.297초 대 실제 0.060초/토큰).
   - 바이트와 초를 따로 감쇠 합(회당 0.98)으로 모아 그 비를 쓰도록 바꿨다. 큰 전송은 크기만큼, 작은 전송은 고정 비용만큼 반영된다.
   - 바꾼 뒤: 0.057초 대 실제 0.062초/토큰.
7. **M1 CPU의 bf16 역전파**
   - `grad @ W`(W가 [out, in] 연속)는 torch 2.14 macOS 판에서 mkldnn 없이 단일 스레드 일반 gemm으로 떨어진다. 2.8 GFLOPS로, 순전파(120 GFLOPS)의 1/40이다. fp32(Accelerate)는 492 GFLOPS다.
   - memopro와 무관하고 보통 불러오기에서도 같다. 1.5B bf16 LoRA의 한 단계가 몇 분 걸린다.
   - D1에는 속도 기준이 없어 그대로 둔다. 이후 과제: 역전파를 fp32 타일로 나눠 계산하는 경로(다만 누적 순서가 달라져 비트 동일은 잃음).

## 시험

- **Rust**: 2단계 시험 6개 추가 — 미리 읽기 적중, 힌트와 런타임 해제, 파생 버퍼 재계산의 정확성, 비결정 recipe → `Integrity`, 버려진 파생 버퍼의 입력은 바꾸거나 없앨 수 없음, 예측 ≈ 실제 재읽기. `predict.rs` 3개. 전체 53개 통과(1개 무시).
- **Python**: `tests/test_rt_phase2.py` 5개(재계산, 입력을 붙잡는 함수 거절, 비결정 함수, 예측, 미리 읽기 켜고 끄기), `tests/test_rt_torch.py` 5개(작은 GPT-2 9MiB 예산에서 추론·생성 비트 동일, 가장 큰 가중치보다 작은 예산 거절, LoRA 학습 비트 동일, `saved_weights` 오류, 파일 없음 오류). 전체 300개 통과.
- clippy·fmt·ruff 통과.

## 한계

- **CPU만**: 가중치는 런타임 메모리에 있는 그대로 쓴다. MPS·CUDA로 복사 없이 잇는 것은 이후 과제다.
- **텐서 하나가 한도에 들어가야 한다.**
- **재계산은 호출자 스레드에서만** 한다(미리 재계산 없음).
- **예측은 고정 순서가 되풀이되는 작업에만** 맞다. 한 주기가 기록되어야 한다.
- **가중치가 바뀌는 전체 학습**은 쓰기 없이는 1/4 메모리에서 할 수 없다(0114).
- `stream_model`의 기본 클래스는 `AutoModelForCausalLM`이다(`model_class`로 바꿈).

## 논문 매핑

- **주 논문 Design/Implementation**
  - 배운 순서로 미리 읽기: 나중에 쓸 것만 내보내 미리 읽기가 적중을 해치지 않는다.
  - 다이제스트로 확인하는 재계산.
  - Belady 모의로 한 주기 기록에서 느려짐을 예측한다.
  - 복사 없는 PyTorch 가중치 스트리밍과, 역전파가 가중치 대신 참조를 저장하는 방법.
- **Threats**: CPU BLAS는 정렬에 따라 결과가 달라진다. 무손실 비교는 같은 정렬끼리 해야 한다.
- **Discussion**: bf16 역전파의 CPU 경로 성능 절벽(하드웨어·라이브러리 한계).
