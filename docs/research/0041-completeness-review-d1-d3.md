# 0041. 완성도 평가(자기 비판 3차)와 결함 D1~D3 수정

- **날짜**: 2026-09-25
- **유형**: survey+milestone (자기 비판, 결함 수정)
- **상태**: 확정 — D1~D3 수정 완료
- **관련 기록**: 0040 (v0.1 개발판), 0036 (B1 정체성 유지 해제), 0039 (β), 0031 (자기 비판 2차), 0014 (1차)

## 배경

> "완성도를 평가해." → "그럼 우선은 D1~D3까지 개선을 진행해."

v0.1 개발판(0040)을 평가하면서, **테스트하지 않았던 경우 6가지를 직접 시험**했다. 그중 3개에서 결함이 나왔다.

## 평가 요약 (수정 전)

| 영역 | 완성도 | 근거 |
|---|---|---|
| 기능 구현 (v0.1 범위) | 90% | 기능 전부 동작. `idle_seconds`, CUDA 실기 경로만 빠짐 |
| 정확성 검증 | 60% | macOS CPU·MPS는 강함. 실제 CUDA·Linux는 실행 이력 없음 |
| 견고성 | 55% | 결함 D1~D3 |
| 사용성·문서 | 80% | 예제 노트북, `--plan`, 이유·대안 안내. API 문서 사이트 없음 |
| 연구 기록 | 95% | 0001~0040, 결과 낸 스크립트 해시 동결 |
| 배포 준비 | 50% | 로컬 빌드·설치·dry-run 통과. 원격 CI·버전 결정 남음 |
| 제품 가치 검증 | 10% 미만 | E010·E011 미실시 |

종합: **v0.1 기준 약 70%, v1.0 기준 약 25%.** 개발판으로는 완성, 제품으로는 미완성이다.

## 발견한 결함과 원인

| # | 상황 | 증상 | 원인 |
|---|---|---|---|
| **D1** | 뷰(view)가 가리키는 텐서, 또는 뷰 자체를 동면 | 깨운 뒤 원본과 뷰가 **메모리를 더 이상 공유하지 않음**. 원본을 수정해도 뷰에 반영되지 않는데 오류가 없다(조용한 오류). 동면 중에도 뷰가 저장공간을 잡고 있어 메모리가 줄지 않는다 | 0036 B1(`tensor.data` 교체)의 부작용. B1은 "다른 곳의 참조는 크기 0으로 크게 실패한다"고 가정했지만, **같은 저장공간을 가리키는 다른 텐서**는 교체 대상이 아니다 |
| **D2** | forward 후 backward 전에 모델을 동면 | backward에서 `size (0) must match (512)` 오류 | 역전파가 그래디언트를 크기 0이 된 파라미터에 누적하려 했다 |
| **D3** | meta 장치 텐서(accelerate 오프로드·빈 초기화) | memopro 오류가 아니라 torch `NotImplementedError`가 그대로 새어 나옴 | 데이터가 없는 텐서를 CPU로 복사하려 했다. 방법별 예외를 fail-open으로 잡지 않았다 |

정상으로 확인된 경우도 있다. `torch.compile` 모델(자동 복원·결과 동일), 같은 객체를 두 번 동면(같은 핸들 반환), 딕셔너리 입력(이유를 밝히고 거부).

## 수정

| # | 수정 | 구현 |
|---|---|---|
| D1 | **저장공간을 공유하는 텐서는 동면하지 않고** 이유를 기록한다(`handle.kept`). 판정 조건은 두 가지이다. ① 텐서가 뷰(`_base` 있음) ② 저장공간 참조 수가 텐서 자신과 확인용 참조를 합친 2보다 큼 | `_tensors.shared_reason()`. 참조 수는 torch 내부 API `torch._C._storage_Use_Count`로 센다. **이 API가 없으면 ①만 검사**한다(더 약한 보호). 사전 실험에서 일반 텐서 2, 뷰가 있으면 3, autograd가 저장했으면 3임을 확인했다 |
| D2 | 파라미터(와 grad가 필요한 텐서)에 **그래디언트 hook**을 달아, 진행 중이던 역전파가 도달하면 누적 전에 깨운다. autograd가 저장한 파라미터는 D1 규칙에 따라 깨어 있는 채로 남는다 | leaf 텐서 hook은 누적 전에 실행되며, forward 뒤에 등록해도 동작함을 확인했다 |
| D3 | meta 텐서는 건너뛰고 `"meta tensor: it holds no memory"`로 기록한다. 방법 실행 중 **예상하지 못한 예외도 해당 텐서만 깨어 있게** 하고 이유를 기록한다(fail-open). 복원도 텐서 하나가 실패해도 나머지를 계속 복원한 뒤 보고한다. `plan()`도 meta 텐서를 제외한다 | `now()` 텐서 루프, `Handle.wake()` |
| 부수 | `ModeUnavailable` 안내 문구를 "available"에서 "other modes to try"로 바꿨다. `auto`가 실패하면 다른 방법을 권하지 않는다(이미 모두 시도했으므로) | `_errors.py`, `now()` |

## 검증

| 검증 | 결과 |
|---|---|
| 재현 시험 | D1: 거부되고 공유 관계 유지. D2: 기준 모델과 그래디언트가 비트 단위로 동일. D3: `ModeUnavailable`, 섞인 모듈은 실제 텐서만 동면 |
| 회귀 테스트 5개 추가 | 원본·뷰 모두 거부 후 공유 유지, 모듈에서 공유된 파라미터만 깨어 있음, 역전파 도중 동면 후 그래디언트 동일, meta 텐서 처리, 예외 발생 시 텐서 유지 |
| 과잉 차단 여부 | 실제 GPT-2(HF 캐시)는 여전히 전부 `source`, 깨어 있는 텐서 0개 |
| 전체 | `pytest` **102 통과**, `cargo test` 21 통과, ruff·clippy 통과 |

## 수정 후 평가

- **견고성**: 55% → 약 70%. 여전히 시험하지 않은 경우가 남아 있다: 양자화 파라미터 클래스(bitsandbytes), FSDP·DDP, DataLoader 멀티프로세스, 큰 모델.
- **v0.1 종합**: 약 70% → 약 75%.
- **남은 배포 전 관문**(0040 V1~V5): 원격 CI, Colab CUDA, E010·E011·E009, 버전과 배포 결정.

## 교훈

- 설계 결정 B1의 위험 평가는 "참조하는 쪽은 크게 실패한다"는 가정에 기댔다. 그러나 **같은 메모리를 가리키는 다른 텐서**는 그 가정 밖이었다. 위험 가정은 "누가 이 메모리를 보는가"를 기준으로 전부 나열해야 한다.
- 직접 시험(탐색적 테스트)으로 **조용한 오류**를 배포 전에 찾았다. 0031에서 지적한 "메모리 도구는 한 번 문제가 나면 바로 제거된다"는 위험을 줄인 사례이다.
