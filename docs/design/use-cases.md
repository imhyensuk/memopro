## 1. 구성 요소별 역할 한눈에

| 구성 요소 | 계층 | 대상 단계 | 하는 일 |
|---|---|---|---|
| **`memopro.load` / `optimize(goal="infer")`** [v0.2] | 범용 접근 | 추론·서비스 | 내 기기 가용 메모리에 맞춰 **추론 후보 구성**(지연 로딩 → 반정밀도 → int8 → KV 캐시 양자화 → int4 → 오프로드)에서 들어가는 첫 구성을 자동 선택 |
| **`memopro.train_session` / `optimize(goal="train")`** [v0.2] | 범용 접근 | 학습·파인튜닝 | **학습 후보 구성**(혼합 정밀도 → 체크포인팅 → 활성값 오프로드 → 8비트 옵티마이저 → 마이크로배치 → 오프로드), LoRA는 제안만 |
| **`memopro doctor`** [v0.1] / **`check`** [v0.2] | 범용 접근 | 전 단계 | doctor: 풀별 예산 벡터(장치·호스트·디스크) 진단 / check: "이 PyTorch 모델이 내 예산에 들어가는가, 어떤 구성으로" |
| **census** [v0.1] | 연구 코어 | 개발·학습·추론 | 메모리가 어디에 쓰이고 **얼마나 중복(낭비)인지** 진단 |
| **β hibernate** [v0.1] | 연구 코어 | 개발 (대화형) | 노트북·REPL에 쌓인 유휴 텐서·모델을 제안하고 한 줄로 압축·방출 (자동 모드는 선택). 1순위 환경: CUDA VRAM, 스왑 없는 환경 |
| ~~α rfc~~ | — | — | **0018에서 기각** (비수축 블록 + 체인 오차 누적) |
| **γ elastic** [v0.4] | 연구 코어 | 학습·추론·서비스 | 실행 중 메모리 압박에 따라 구성을 바꾸며 OOM 대신 단계적 열화 |

## 1.1 사용자 유형별 진입점

| 사용자 | 수준 | 시작 방법 |
|---|---|---|
| Python 서비스 운영자 | L0 | `memopro doctor` → (v0.4) `memopro run app.py --budget auto` 또는 `memopro.toml` |
| 일반 사용자, 학생 | L1 | `model = memopro.load("모델ID")`, `%load_ext memopro` |
| 실무 개발자 | L2 | `memopro.load(id, budget="6GB", quality="lossless", prefer="speed")` |
| 연구자 | L3 | `memopro.census.record(..., mode="deep")`, `memopro.hibernate.now(...)` |
| 라이브러리·Rust 개발자 | L4 | `Technique` 플러그인, `memopro` 크레이트 |

## 2. 핵심 관찰: LoRA·QLoRA 이후 남는 병목은 활성값이다

> ⚠️ 0018 이후: 이 관찰(0009)은 **유효**하다. 다만 그 병목을 α로 줄이려던 계획은 기각되었고, 기존 기법(체크포인팅·오프로드)으로 대응한다. 아래 α 수치는 기록용이다.

학습 메모리는 크게 네 부분으로 나뉜다. **가중치 + 그래디언트 + 옵티마이저 상태 + 활성값**

- LoRA·QLoRA, 8비트 옵티마이저 같은 기존 기법은 **앞의 세 부분**을 줄인다.
- 그러고 나면 남는 병목이 **활성값**이다. 문장이 길어지거나 배치가 커질수록 이 부분이 전체를 지배한다.
- α는 바로 이 **남은 부분**을 겨냥한다. 즉 기존 도구와 경쟁하지 않고 **그 위에 얹어서 쓰는** 기법이다.

**예시 (Llama-3-8B 규모: 32층, 차원 4096, bf16, 체크포인팅 사용 시 저장 체크포인트만 계산)**

| 문장 길이 (배치 1) | 기존 체크포인트 | α (4비트 힌트 + 마지막 층 원본) |
|---|---|---|
| 4K 토큰 | 약 1.0 GB | 약 0.3 GB |
| 16K 토큰 | 약 4.0 GB | 약 1.2 GB |
| 32K 토큰 | 약 8.0 GB | 약 2.4 GB |

계산식: 층 수 × 토큰 수 × 차원 × 바이트. 4비트 힌트에는 블록 스케일 오버헤드를 포함했다.
실제 피크 메모리에는 이 밖에도 로짓, 층 내부의 일시적 텐서 등이 더해지므로, 전체 절감률은 E004 실험으로 측정해야 한다.

## 3. 환경별 시나리오

### ① 개인 노트북 — Apple Silicon 8~16GB (통합 메모리)
**상황**: 브라우저와 IDE가 메모리를 나눠 쓰고, Jupyter에서 이것저것 실험하다가 스왑 폭주나 커널 종료를 겪는다.

```python
%load_ext memopro                      # 유휴 객체와 회수 가능량 제안
%hibernate old_model                   # β: 제안받은 객체를 압축·SSD 방출 (다시 쓰면 복원)
import memopro
with memopro.census.record(model, opt) as c:   # 어디가 문제인지 진단
    train_step(batch)
print(c.summary())
# (α는 0018에서 기각 — 학습 메모리는 v0.2 train_session의 기존 기법으로 대응)
```
**효과**: 노트북 세션이 덜 죽고, 같은 기기에서 더 긴 문장으로 파인튜닝할 수 있다. (γ가 완성되면 다른 앱이 메모리를 가져갈 때 죽는 대신 속도를 늦춘다)

### ② 무료·저가 클라우드 노트북 — Colab, Kaggle (GPU 15~16GB, 시스템 RAM 약 12GB)
**상황**: GPU보다 **시스템 RAM 12GB**가 먼저 바닥나 세션이 재시작되는 경우가 많다(모델 로딩, 데이터 전처리 결과 누적).
**활용**: β로 셀 사이에 쌓이는 CPU 텐서를 회수하고(스왑 없는 환경에서 특히 유효), census로 OOM 원인을 파악한다.

### ③ 소비자 GPU 워크스테이션 — RTX 3060 12GB, 4090 24GB
**상황**: QLoRA로 7~8B 모델을 파인튜닝하는데, 문장 길이를 늘리면 OOM이 난다.
```python
model = get_peft_model(load_4bit(base), lora_cfg)   # 기존: 가중치·옵티마이저 절감
with memopro.train_session(model, opt, batch_size=8) as s: ...   # v0.2: 체크포인팅·오프로드로 남은 활성값 대응
```
**효과**: 같은 GPU에서 **더 긴 문장이나 더 큰 배치**로 학습할 수 있다(2절 표). 장문 파인튜닝이 대표 용도이다.

### ④ 연구실·교육 환경 — 여러 사람이 공유하는 GPU 서버
**상황**: 다른 사람의 작업 때문에 가용 메모리가 수시로 변하고, 학생들은 메모리 구조를 잘 모른다.
**활용**: γ로 경합에 적응하고, census 보고서를 **메모리 교육 자료**로 쓴다.

### ⑤ 기업·스타트업 — 클라우드 비용 절감
**상황**: 파인튜닝 때문에 80GB GPU 인스턴스를 빌린다.
**활용**: `train_session` + QLoRA로 **더 작은 GPU 인스턴스**에서 같은 작업을 시도한다. census로 필요 용량을 산정한다.

### ⑥ Rust 생태계 — candle, burn 개발자, 임베디드
**활용**: crates.io의 `memopro` 코어(부동소수 코덱, 텐서 원장, SSD 방출, OS 메모리 압박 신호)를 부품으로 쓴다.


### ⑦ 온디바이스 학습 (스마트폰·엣지에서 개인화 파인튜닝) — 장기
메모리가 극단적으로 작은 기기의 학습은 초기 범위가 아니다(α가 기각되어 이 영역의 고유 기법 후보는 현재 없음).

## 4. 적용 범위의 한계 (정직한 범위)

| 환경 | 상태 | 비고 |
|---|---|---|
| 추론·서빙 (PyTorch 코드) | ✅ 범용 접근 계층이 담당 (v0.2) | 기존 기법 연동. γ가 실행 중 적응을 더함 (v0.4) |
| 잔차 연결이 없는 구조 | ✅ | (α 기각으로 구조 제약 없음) |
| TensorFlow, JAX | ❌ 초기 미지원 | Rust 코어는 프레임워크와 무관 |
| 수천 GPU 규모 분산 학습 | ❌ 초기 목표 아님 | DeepSpeed, Megatron |
| 코드 없이 LLM 앱을 쓰려는 최종 사용자 | ❌ 대상 아님 (0012 S1) | 외부 도구로 안내하지도 않는다 (S2 기각) |
| 물리적 한계 | ⚠️ | 메모리보다 훨씬 큰 모델은 오프로드로 **실행은 되지만 매우 느리다**. `memopro check`가 먼저 알려준다 |
