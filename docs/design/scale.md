## 0. 결정: 목표는 비율로, 출시는 검증된 규모로

**목표 (G2′를 규모 무관으로 확장)**

> **작업이 요구하는 메모리가 보유한 메모리보다 클 때, 규모와 관계없이, 결과를 바꾸지 않고 상한 안에서 돌린다.**

8GB 노트북에서 32GB짜리 작업을 돌리는 것과 128GB 서버에서 512GB짜리 작업을 돌리는 것은 같은 문제다. 기준은 절대량이 아니라 **비율(요구량 ÷ 보유량)**이다. "제한적인 하드웨어"는 상대적인 개념이다.

**설계와 출시를 나눈다**

| | 기준 | 이유 |
|---|---|---|
| **설계** | 규모 무관(비율) | 핵심 구조(예산 형식, 1/2~1/4 목표, 대역폭 기반 예측)가 이미 비율 기준이라 비용이 작다. 절대 크기를 가정한 상수는 나중에 고칠수록 비싸다 |
| **출시·검증·문구** | 8~16GB (첫 검증 대상) | 측정 근거가 전부 8GB M1과 Colab T4에 있다. 대안이 가장 적은 사용자에게 가치가 가장 크다. 1인 개발 규모에 맞는다 |

대형 장비 관문(§5.2)을 통과하기 전까지 "규모 무관"은 **설계 원칙**으로만 말하고, 검증된 결과로 주장하지 않는다.

## 1. 원칙

| # | 원칙 | 의미 |
|---|---|---|
| S1 | **비율로 정의한다** | 성공 기준, 테스트, 느려짐 예측은 요구량 ÷ 예산으로 말한다. 같은 비율이면 규모가 달라도 같은 결정을 내려야 한다 |
| S2 | **상수는 규모에 비례한다** | 크기·창·여유분은 기기 메모리, 예산, 측정 대역폭, 코어 수에 비례하게 정한다. 고정 상수는 정확성에 필요한 최소값(코덱 청크, 스크래치 한 조각 등)에만 쓴다 |
| S3 | **검증한 규모만 주장한다** | README와 결과표는 측정한 기기와 규모를 밝힌다. 규모 무관은 §5의 두 겹 검증을 통과한 뒤에 결과로 올린다 |
| S4 | **규모와 무관한 벽을 숨기지 않는다** | 규모를 키워도 비율만 바뀌는 한계(§4)는 그대로 알린다. 예산이 모자라면 실행 전에 거절하는 기존 원칙(R2)을 유지한다 |
| S5 | **두 겹으로 검증한다** | CI에서는 같은 비율을 여러 절대 규모에서 돌려 행동이 같은지 본다. 릴리스마다 대형 장비에서 한 번 확인한다 |

## 2. 성공 기준 (비율)

| 대상 | 기준 |
|---|---|
| 작업 집합이 예산 안인 작업 | 요구량의 1/2, 1/4 예산에서 결과 동일(무손실), 상한 준수, 느려짐 예측 오차 ±15% 이내 (G2′ 그대로) |
| 규모 불변성 (CI) | 같은 비율에서 절대 규모를 1·2·4배로 바꿔도 패스당 복원 횟수가 같다(±1 버퍼). 상한과 결과 동일성은 모든 규모에서 지킨다 |
| 대형 장비 관문 (릴리스) | 보유 메모리 128GB 이상 기기에서 요구량이 보유량의 2배인 작업 하나를 결과 동일, 상한 준수로 끝낸다. 결과는 `docs/research/data/`에 남긴다 |

## 3. 규모 의존 지점 (2026-10-08 조사)

코드에 박힌 절대 크기를 찾아 분류했다.

| 위치 | 값 | 영향 | 상태 |
|---|---|---|---|
| `crates/memopro/src/rt/pager/macos.rs` 주소 공간 예약 | 64 GiB 고정 | macOS 투명 페이징이 pager 하나당 64 GiB를 넘는 영역을 만들지 못했다(`map`이 "address space is used up"으로 거절). 메모리가 큰 Mac에서 비율 목표가 깨진다 | ✅ **수정**: 물리 메모리의 8배, 최소 64 GiB, 청크 2^23개 상한(`rt::pager::arena_bytes`). 8~16GB 기기는 이전과 같다 |
| `python/memopro/_units.py` `format_size` | GiB까지 | 1 TiB 이상이 "1024.00 GiB"로 보인다 | ✅ **수정**: TiB 추가 |
| 두 pager의 `HOT_CHUNKS = 16`, `MIN_CHUNKS = 8` (1 MiB 청크) | 작업 창 16 MiB | 대역폭이 큰 기기에서 fault가 지나치게 잦을 수 있다 | 측정 필요. 지금은 `fits / 4`로 2~16 사이에서 비례하고 상한만 고정이다. 대형 장비 관문에서 fault 비율을 재고 정한다 |
| 두 pager의 `choose()` | 쫓아낼 때마다 모든 청크를 훑는다 | 1 TiB, 1 MiB 청크면 쫓아낼 때마다 약 100만 개를 훑는다. 한 패스 비용이 청크 수의 제곱으로 는다 | 측정 필요. 예측 거리 순 우선순위 큐나 표본 추출로 바꾸는 안을 실측 후 정한다 |
| `crates/memopro/src/rt/mod.rs` `Config::lookahead` | 64 MiB (한도의 1/4 이하) | 여러 NVMe(수십 GB/s)에서는 prefetch가 연산을 따라가지 못할 수 있다. 창을 키우면 쓸 수 있는 예산이 줄어든다 | 측정 필요. 측정 대역폭 × 한 버퍼 계산 시간에 비례하는 안을 검토한다 |
| `python/memopro/rt/torch.py` GPU 활성값 여유분 | `max(2 GiB, 15%)` | 80GB GPU에서 12GB를 남긴다 | 측정 필요. 15%는 T4 실측에서 왔다. 큰 GPU에서 다시 잰다 |
| macOS pager의 청크 상태 배열 | 청크당 1바이트, pager를 닫아도 반환하지 않음(신호 처리기 안전) | 주소 공간을 키우면서 pager 하나당 1 TiB 예약 기준 1 MiB가 남는다(이전 64 KiB) | 허용. 상한(2^23개 = 8 MiB)으로 묶었다 |

새 코드는 S2를 따른다. 절대 크기를 쓰려면 정확성상 왜 필요한지 주석에 밝힌다.

## 4. 규모와 무관한 벽

규모를 키워도 비율만 바뀌고 그대로 남는 한계다. 8GB와 128GB에서 같은 모양으로 나타난다.

| 벽 | 8GB에서 | 128GB에서 | 방향 |
|---|---|---|---|
| attention 점수가 길이의 제곱(`heads × T² × 4`)으로 커진다 | 7B, 8K 토큰 | 70B, 64K~128K 토큰 | 쿼리 행 단위로 나눠 계산한다. 행마다 계산 경로가 같으면 결과가 비트 단위로 같다(row-invariant 검증과 같은 원리) |
| 원본도 계보도 없는 데이터(옵티마이저 상태, 생성된 중간 결과) | 1B 전체 미세조정 | 30B 이상 전체 미세조정 | 압축만으로는 부족하다. **동의형 SSD 계층**이 필요하다(§7 결정 ①) |
| 텐서 하나가 보유 메모리보다 크다 | 3D 볼륨, 고해상도 conv | 거대 임베딩, 초대형 행렬 | 타일 단위 연산. 경계를 정확히 다루면 무손실 |

## 5. 검증

### 5.1 비율 시뮬레이션 (CI)
- `rt::tests::the_same_ratio_behaves_the_same_at_every_scale`: 버퍼 16개를 예산 약 60%에서 반복해 훑는다. 버퍼 크기를 1·2·4 MiB로 바꿔도 패스당 복원 횟수가 같고(측정 12/16), 상한과 결과 동일성을 지킨다.
- `rt::pager::portable_tests::the_arena_scales_with_the_machine`: 주소 공간 크기가 기기 메모리에 비례하고 하한·상한을 지킨다.
- 새 규모 의존 지점을 고칠 때마다 이 형식의 테스트를 더한다.

### 5.2 대형 장비 관문 (릴리스마다, 수동)
- 기기: 보유 메모리 128GB 이상(클라우드 대형 메모리 인스턴스, 또는 192GB 이상 Mac)
- 작업: (a) 보유량 2배의 NumPy 반복 스캔(`memopro run --transparent`), (b) 보유량을 넘는 가중치의 LLM 생성
- 판정: §2 기준. 실패하면 그대로 기록한다

## 7. 미결정 사항

| 항목 | 내용 | 권고 |
|---|---|---|
| ① SSD 계층 | "SSD에 쓰지 않는다"(runtime.md 0110)를 유지할지 | 기본은 끄고 `disk_writes="allow"`일 때만 켜는 계층을 다시 설계한다. 규모가 클수록 원본 없는 데이터의 비중이 커져 비율 목표에 필요하다 |
| ② 대상 범위 | architecture.md §0의 대상이 "PyTorch로 무언가를 만드는 사람"이다 | 비AI 작업(NumPy, scikit-learn, Python 서비스)을 대상에 명시한다. 런타임 C-R의 AI·비AI 목표(0107)와 맞춘다 |
| ③ 다중 장치 계층 | 128GB 이상에서 요구량이 보유량을 넘는 작업은 대부분 GPU 여러 장 환경이다 | GPU 여러 장 → 호스트 RAM(NUMA별) → 압축 → 원본 재읽기 → (동의 시) SSD 계층을 설계한다. 대형 장비 관문 뒤로 미룬다 |
| ④ 관문 장비 | 128GB 이상 기기의 확보 방법 | 릴리스마다 클라우드 인스턴스를 한 번 빌린다. 비용과 주기를 정한다 |
